Real GitHub Actions evidence (Windows leg of `.github/workflows/check.yml`, TK-006): configuring `src/backend/audio` with `cmake -G Ninja` on the `windows-latest` runner made CMake auto-detect `C:/mingw64/bin/cc.exe`/`c++.exe` as the compiler (GNU 15.2.0), not MSVC. JUCE hard-refuses to build under MinGW (`juce_TargetPlatform.h`: `#error "MinGW is not supported."`), so the native build failed at the very first compile step. Root cause: the Ninja generator resolves a compiler via `CC`/`CXX` env vars, then a `PATH` search — it has no built-in awareness of Visual Studio. GitHub's Windows runner image ships MinGW reachable on `PATH` by default, while `cl.exe` is only reachable after running Visual Studio's `vcvarsall.bat`-equivalent setup, which nothing in the workflow did.

The standard fix — `ilammy/msvc-dev-cmd` (injects `cl.exe`'s directory plus `INCLUDE`/`LIB` onto `PATH`) — was deliberately avoided: its own README documents that GitHub's `shell: bash` unconditionally re-prepends GNU paths at the start of every step, which is known to shadow MSVC's `link.exe` with `/usr/bin/link`. Since the root `Makefile` needs `shell: bash` (its recipes use `&&`/`cd`/`rm -rf`), that fix would trade one PATH-ordering failure for another.

Fix applied instead: dropped `-G Ninja` from the Makefile's `check-native` target entirely, letting CMake fall back to its own per-platform default generator — "Unix Makefiles" on macOS/Linux, the installed Visual Studio/MSBuild generator on Windows. The VS generator locates MSVC through Visual Studio's own installation metadata, independent of `PATH` or shell, sidestepping the whole class of PATH-ordering issues. Added `--config Release` to `cmake --build` and `-C Release` to `ctest`, since VS/MSBuild is a multi-config generator (Ninja/Unix Makefiles are single-config and silently ignore `--config`/`-C`). Re-verified locally on macOS with a fully clean `make check-all` — passes using "Unix Makefiles" instead of Ninja, confirming the generator switch doesn't regress the already-proven macOS path.

Not yet confirmed: whether MSVC itself successfully compiles Tracktion Engine + JUCE on Windows (a separate concern from compiler *selection*, which is what this fix addresses) — that requires an actual GitHub Actions run, which this session cannot trigger.
