Local validation (outside CI, macOS, `cmake` 4.4.3, `sccache` 0.17.0) while speeding up `check.yml`'s `check-native` job surfaced caching behavior specific to this project's `FetchContent`-based dependencies (JUCE, Tracktion Engine, protobuf/abseil):

- `GIT_SHALLOW ON` on the `juce` `FetchContent_Declare` (pinned by raw commit SHA `19edd538429c93d277bf95b55aaa7e3eb545f951`, not a tag) fails outright: `git clone` reports `fatal: unable to read tree (<sha>)`. Shallow-cloning an arbitrary commit SHA needs server-side `uploadpack.allowReachableSHA1InWant`-style support that this CMake/git combination doesn't successfully exercise here, confirmed by an actual failed configure. `GIT_SHALLOW ON` on `tracktion_engine` (pinned by the real tag `v3.2.0`) works cleanly and cut its clone from ~161s (full history, measured from real CI logs) to ~8s locally. Tag-pinned `FetchContent_Declare`s are safe to shallow-clone here; SHA-pinned ones are not — don't assume the same treatment applies to both without re-testing if `juce`'s pin ever moves to a tag/branch.
- Caching only `src/backend/audio/build/_deps/*-src` (the `FetchContent`-downloaded sources) across a from-scratch `cmake -S`/`cmake --build` at a stable path, with `CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER=sccache` set, produced almost no `sccache` reuse for the JUCE/Tracktion/protobuf/abseil compiles (0 additional hits across 371 compiles in one measured pass). Suspected cause: JUCE's CMake integration regenerates per-module wrapper/config content at each fresh `cmake -S`, and that regenerated content isn't guaranteed byte-identical run to run, which defeats `sccache`'s content-hash for exactly the translation units that matter. Caching the *entire* `_deps` tree instead — sources and already-compiled `-build` objects together, no exclusion — let Make's own mtime-based up-to-date check skip recompiling third-party code entirely: measured locally, configure dropped from ~92s to ~6.8s and the build step from ~110–150s to ~56s, with compile requests dropping from 371 to 133 (of which the 133 still-needed compiles got a 48% `sccache` hit rate on top). `check.yml`'s `native-deps` cache therefore caches the full `_deps` directory, not just `*-src`.
- `sccache` runs as a persistent background server; a client invocation's env vars (e.g. `SCCACHE_DIR`) only take effect if they were present when the server was first started — a later `export` in a new shell does nothing to an already-running server, and its cumulative stats/counters survive across unrelated test invocations. This only matters for local re-validation of `sccache` behavior (each real CI job is a fresh VM with no leftover server); anyone repeating this kind of test should `sccache --stop-server` between independent scenarios or the results will look like cache misses/hits that aren't real.
- Confirms and extends [[cmake-windows-generator]]: since Windows must stay on the default Visual Studio generator (Ninja there resolves MinGW instead of MSVC), `sccache`'s CMake hookup for Windows can't rely on a generator switch either. The currently-documented (`mozilla/sccache` `docs/`, checked directly rather than from memory) CMake≥3.25 MSVC recipe — `CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER=sccache` plus `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT=Embedded` and the `CMP0141` policy set to `NEW` — works with the VS generator directly, no generator change needed. Not yet confirmed on an actual Windows runner; only the macOS half of this (`CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER` alone, no MSVC-specific flags) has been locally proven end to end (clean build, `ctest` 100% pass, real cache hits).
- The full-tree `_deps` cache above is a real correctness hazard on its own, independent of `sccache`: Make's up-to-date check that lets it skip recompilation entirely is pure file-mtime comparison, with zero awareness of which compiler/toolchain produced the restored `.o`/`.a` files. `sccache` is self-protecting (its cache key already hashes compiler identity), but a bare cache *key* of `native-deps-${{ runner.os }}-${{ hashFiles('CMakeLists.txt') }}` is not — a GitHub-hosted-runner image update (Xcode/MSVC bump inside the same `macos-latest`/`windows-latest` label) would restore old-compiler objects that Make would treat as already up to date, silently skipping a real recompile. Fixed by widening the `native-deps` key to `runner.os`-`runner.arch`-`env.IMAGE_OS`-`env.IMAGE_VERSION`-a literal generator tag (`vs`/`make`)-a literal `release` tag-the `CMakeLists.txt` hash. `IMAGE_OS`/`ImageVersion` are real runner-VM environment variables (not part of the `github`/`runner` Actions contexts, so unreachable via `${{ }}` until copied into `$GITHUB_ENV` by an explicit step first) — confirmed via real-world usage, not memory: Microsoft's `microsoft/p4vfs` uses the identical pattern for its own OpenSSL build cache, and `hspec/setup-haskell`'s `fast/action.yml` uses the exact `echo "ImageOS=$ImageOS" >> $GITHUB_ENV` bash form across macOS/Linux/Windows with no OS conditional, confirming the mechanism (not just the Windows-`$env:`-flavored spelling) is cross-platform. Exact-key-only (no `restore-keys`) for this cache means any of these dimensions changing is a clean miss — `_deps` starts absent, `cmake -S`/`--build` does a genuinely correct fresh clone+compile — never a partial/stale restore. Known, deliberately undefended residual gap: `lukka/get-cmake` installs CMake `latest` independent of the runner image, so CMake's own version could drift between two runs on an unchanged image without moving the key; not addressed because CMake orchestrates the real compiler rather than emitting machine code itself (lower severity than the toolchain-identity gap this fix targets), the action exposes no version output to key on without adding a probe step, and pinning `lukka/get-cmake`'s `cmakeVersion` input would be a separate, out-of-scope hardening.
