Vendoring Protobuf via `FetchContent` in `src/backend/audio/CMakeLists.txt` (TK-009) surfaced two upstream CMake mechanisms worth knowing before touching this file again, both confirmed by reading protobuf's own `CMakeLists.txt` at the vendored tag (`v36.1`) rather than guessed, and both confirmed by a real Windows CI failure on `bef35c2` (`LNK2038` errors, 156 of them across 50 `libprotobuf.lib` objects):

- `protobuf_MSVC_STATIC_RUNTIME` (a `cmake_dependent_option`) defaults **ON** whenever `protobuf_BUILD_SHARED_LIBS` is off — i.e. whenever protobuf is built as static libs, which is the normal case for a vendored dependency. When ON, protobuf sets the directory-scoped `CMAKE_MSVC_RUNTIME_LIBRARY` to the static CRT (`/MT`) for every target in its own `FetchContent`-populated subdirectory. That `set()` never propagates up to a parent project's own directory scope, so any of the parent's own targets silently keep CMake's own default (`/MD`, dynamic) — a guaranteed MSVC `LNK2038` runtime-library mismatch the moment the parent links against the vendored static libs. Fix: explicitly `set(protobuf_MSVC_STATIC_RUNTIME OFF CACHE BOOL "" FORCE)` before `FetchContent_MakeAvailable`. This is a no-op on non-MSVC toolchains, so it's safe to always set.
- Wanting the `protoc` compiler at all (`protobuf_BUILD_PROTOC_BINARIES`, default ON) unconditionally forces `protobuf_BUILD_LIBPROTOC` on too (`if (protobuf_BUILD_PROTOC_BINARIES OR protobuf_BUILD_TESTS) set(protobuf_BUILD_LIBPROTOC ON) endif()`), and `libprotoc` bundles **every** language's codegen backend (java/kotlin/objectivec/php/python/ruby/rust/csharp/upb) as one inseparable CMake target — there is no supported from-source option to build a C++-only `protoc`. If only `--cpp_out` is ever needed, the from-source `protoc`/`libprotoc`/`libupb` build (confirmed via `libprotobuf.cmake`: `libprotobuf` itself has zero dependency on `libupb`) can be skipped entirely in favor of protobuf's own official prebuilt release binaries (`github.com/protocolbuffers/protobuf/releases/download/<tag>/protoc-<version>-<platform>.zip`), fetched via a separate `FetchContent_Declare(... URL ... URL_HASH SHA256=...)` — CMake preserves the Unix executable bit through its own zip extraction, confirmed empirically. Upstream's `tool_integrity.bzl` release asset (meant to carry official published hashes) was empty for this release, so hashes were self-computed from a direct download.
- Separately, `FetchContent`'s default git clone fetches full history — measured directly for `protocolbuffers/protobuf`: 2m35s/355MB full vs 12.5s/118MB with `GIT_SHALLOW TRUE` at the same pinned tag, a ~12x difference. `EXCLUDE_FROM_ALL` on the same `FetchContent_Declare` (CMake ≥3.28) additionally keeps `cmake --build`'s default `ALL` target from building every one of abseil's ~200 targets — confirmed by diffing the actual built-target list before/after, since `libprotobuf` only actually links a curated ~35-target subset (`protobuf_ABSL_USED_TARGETS` in `cmake/abseil-cpp.cmake`).

Together these cut a from-scratch `check-native` (configure + build + ctest) from failing after ~35 minutes on Windows CI to under 9 minutes locally on macOS. See `docs/project/tasks/TK-009.md`'s "Reopened" section for the full incident and `docs/project/risks.md`'s `RSK-002` for current status — this file holds only the reusable upstream-CMake mechanism, not the incident narrative.
