Any C++ translation unit that includes protobuf-generated code (`.pb.h`/`.pb.cc`) or otherwise touches protobuf internals must be compiled with the **same C++ standard** used to build the vendored `libprotobuf`, not merely "at least" some minimum. Confirmed by a real Windows/MSVC failure (TK-009): `proof_schema` was compiled at `cxx_std_20` while `libprotobuf` (forced to `cxx_std_17` by protobuf's own `protobuf_configure_target` CMake function) was built at C++17, producing `error LNK2001: unresolved external symbol "class google::protobuf::internal::GlobalEmptyStringConstexpr const google::protobuf::internal::fixed_address_empty_string"`.

Root cause, read directly from protobuf `v36.1`'s `src/google/protobuf/port.h`: `fixed_address_empty_string`'s actual type is chosen per-translation-unit via `std::conditional_t<GlobalEmptyStringConstexpr::HasConstexprDefaultConstructor(0), const GlobalEmptyStringConstexpr, GlobalEmptyStringDynamicInit>` — an SFINAE probe of whether `std::string`'s default constructor is usable in a `constexpr` context with a custom non-constexpr-friendly allocator. This probe's result depends on the standard library's `<string>` implementation *and* the active language standard, not just the library. Confirmed empirically with a standalone reproducer against Apple's libc++: the exact same probe returns `false` under `-std=c++17` and `true` under `-std=c++20`. So a TU compiled at C++20 expects the `GlobalEmptyStringConstexpr`-typed symbol; a TU (or library) compiled at C++17 defines/exports the `GlobalEmptyStringDynamicInit`-typed one instead — two genuinely different, non-interchangeable symbols.

Why this only broke on Windows and not macOS, despite the exact same `cxx_std_20`-vs-`cxx_std_17` split existing on both platforms (confirmed via `flags.make`: `-std=gnu++20` for our target, `-std=gnu++17` for `libprotobuf`, unchanged across platforms): this is a genuine ODR violation per the C++ standard on *both* platforms, but the two ABIs disagree on whether a plain namespace-scope `extern` **data** symbol's mangled name encodes its type. MSVC's decorated name for the unresolved symbol here explicitly embeds the type (`?fixed_address_empty_string@internal@protobuf@google@@3VGlobalEmptyStringConstexpr@123@B`), so its linker correctly refuses to resolve a `GlobalEmptyStringConstexpr`-typed reference against a `GlobalEmptyStringDynamicInit`-typed definition. The Itanium C++ ABI (used by Clang/GCC on macOS/Linux) does not encode a plain global variable's type in its mangled name — only functions get parameter-type mangling — so the same two mismatched definitions silently link together on macOS with no build-time symptom, leaving a real (if latent) ODR violation that just happens not to be caught. **Do not read a clean macOS/Linux build as evidence this kind of split is safe; MSVC's stricter symbol decoration is the one actually catching a real bug.**

Fix: match the C++ standard of any target that links against `protobuf::libprotobuf` (or otherwise includes protobuf headers alongside it) to whatever standard protobuf's own CMake build uses for that vendored version (`cxx_std_17` as of `v36.1`) — don't pick a target's language standard independently of the libraries it links against ABI-sensitively. This generalizes beyond protobuf: any vendored C++ library with its own forced/pinned language standard is a potential ABI boundary, and Itanium-ABI platforms won't necessarily surface a violation at link time the way MSVC will.
