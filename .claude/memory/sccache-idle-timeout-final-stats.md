TK-016 traced a `sccache --show-stats` all-zero result (compile requests, hits, misses — every field, on Windows `check` CI) that turned out not to be a caching failure at all: `SCCACHE_LOG=sccache=debug` plus `SCCACHE_ERROR_LOG=<path>` (both real, current sccache `Configuration.md` variables), captured via a temporary `cat`-the-log-file diagnostic step, showed the daemon had genuinely served hundreds of real compiles with a real ~86% Rust hit rate (`stats after compile result: ServerStats { compile_requests: 756, ..., cache_hits: {"Rust": 522}, cache_misses: {"Rust": 82} }`). The daemon then sat idle for exactly 10 minutes 5 seconds (`shutting down due to being idle or request`) — sccache's own documented default `SCCACHE_IDLE_TIMEOUT` (600s) — because nothing else in that job touched it after the Rust build phase ended. By the time `mozilla-actions/sccache-action`'s post-step finally calls `sccache --show-stats`, the client silently auto-spawns a brand-new, empty server just to answer the query, and *that* server — not the one that did the real work — is what reports zero.

General lesson: a `sccache --show-stats` (or any similar compiler-cache summary) showing an all-zero result at the very end of a long, multi-phase CI job is not proof the cache never worked — it can equally mean the daemon did real work earlier and then idled out before the final query, especially if a later phase of the same job (here: the native CMake build, which this repo's CI genuinely cannot route through sccache at all — see [[sccache-msvc-visual-studio-generator]]) generates no compiler-cache traffic of its own. Before concluding a compiler cache is broken from a zero final-stats reading alone, either set `SCCACHE_IDLE_TIMEOUT=0` (sccache's own documented way to disable the timeout) or capture `SCCACHE_LOG`/`SCCACHE_ERROR_LOG` for that one diagnostic run and read the daemon's own timeline directly, exactly as done here.
