Real Windows GitHub Actions evidence (TK-016, run `33564596456`, commit `7ebb101`) contradicts [[native-build-caching]]'s earlier, unconfirmed assumption: the documented CMake≥3.25 MSVC recipe (`CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER=sccache` plus `CMAKE_MSVC_DEBUG_INFORMATION_FORMAT=Embedded`/`CMP0141=NEW`, copied verbatim from `mozilla/sccache`'s own README) produces zero `sccache` compile requests of any kind on the Visual Studio generator — not just zero hits, `sccache --show-stats` reported all-zero across every field (requests, executed, hits, misses, non-cacheable, non-compile calls) for the entire job, despite the native build genuinely compiling hundreds of translation units through MSBuild.

Root cause, confirmed against real upstream sources rather than assumed: CMake's Visual Studio (MSBuild) generator has never wired `CMAKE_<LANG>_COMPILER_LAUNCHER` into the generated `.vcxproj` files at all — only the Makefile and Ninja generators do (tracked upstream at CMake's own `gitlab.kitware.com/cmake/cmake` issue #19326). This is reproduced identically by other users hitting the exact same symptom with the exact same flags (`mozilla/sccache` issues #957 and #1097, both open as of 2026-09). CMake silently accepts the flags (no error, no warning) and simply never uses them — "CMake accepted the flag" is not evidence it did anything; only observed `sccache --show-stats` activity is.

The wider ccache/clcache community's workaround for exactly this MSBuild limitation — `CMAKE_VS_GLOBALS` with `CLToolExe`/`CLToolPath` pointing at a copy of the cache binary renamed to `cl.exe`, plus `UseMultiToolTask=true` — does *not* transfer to sccache. `mozilla/sccache` issue #1063 (open) shows this exact attempt failing: sccache errors `cannot find binary path` when invoked without an explicit compiler path argument, because unlike ccache/clcache it has no mode to auto-detect the real compiler from its own invoked name/location. Conclusion, as of sccache 0.17.0 / CMake with the `lukka/get-cmake@v4.4.2`-installed version used in this repo's CI: there is currently no configuration that routes MSVC C/C++ compilation through sccache while using the Visual Studio generator. Anyone re-attempting this should check whether either upstream project has since closed the relevant issue before assuming otherwise.

Independently, this repo's own `-DCMAKE_POLICY_CMP0141=NEW` was already a no-op regardless — confirmed by the CI log's own `CMake Warning (unused-cli): ... CMAKE_POLICY_CMP0141` — because CMake's actual variable name is `CMAKE_POLICY_DEFAULT_CMP0141` (checked against CMake's own CMP0141 policy docs). The typo was copied verbatim from `mozilla/sccache`'s own current README, which carries the identical mistake — a reminder that even an official project's own docs can be silently wrong, and "the docs say so" is not itself proof a flag works.
