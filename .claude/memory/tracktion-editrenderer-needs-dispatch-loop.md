`tracktion::EditRenderer::render()` (v3.2.0) can hang indefinitely waiting for its completion callback even in a fully headless setup (`EngineBehaviour::autoInitialiseDeviceManager() = false`, no real audio device). Confirmed directly (EP-005/TK-013): a `materialize()` function called `EditRenderer::render()` from `main()` (the JUCE message thread) and waited on a plain `std::condition_variable` for the completion callback — the callback never fired, confirmed via temporary `std::cerr` instrumentation at each step (edit created, clips inserted, render started, then silence). The render's background thread was blocked on something needing the calling thread's JUCE message loop to be actively pumping — observed directly as a lazy MIDI-input-device scan (unrelated to the audio-device-manager gate, which only covers the *audio* device manager) that only completed once dispatch-loop pumping started.

Fix, matching the real working pattern in Tracktion Engine's own `modules/tracktion_engine/model/export/tracktion_Renderer.test.cpp` (`test_utilities::runDispatchLoopUntilTrue`) rather than a plain condition-variable wait: poll with `juce::MessageManager::getInstance()->runDispatchLoopUntil (10)` in a loop, checking an `std::atomic<bool>` completion flag set by the render callback, until it flips or a deadline passes. This is a real, load-bearing requirement to copy exactly from the vendored test — not an artifact of that test's own setup to reason past. Read `tracktion_Renderer.cpp`'s `EditRenderer::render`/`render_utils::createRenderTask` directly before assuming a `callBlocking`-based reasoning ("it happens synchronously before the background thread spawns, so no pumping is needed") is sufficient — it explains a *different* part of the mechanism and is not the whole story.

Separately, any code needing to construct a real `tracktion::Edit` and render it (not just construct a headless `Engine`, which toolchain_proof.cpp already proves is fast/pump-free) must expect this dispatch-loop-pumping requirement; a plain mutex/condvar wait (fine for `toolchain_proof`/`transport_proof`, which never touch `Edit`/`Renderer`) is not sufficient once real Tracktion rendering is involved.
