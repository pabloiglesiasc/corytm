Building `src/backend/audio/` against Tracktion Engine `v3.2.0` (TK-002) surfaced several integration gotchas, each confirmed by an actual configure/build failure:

- Tracktion Engine's `v3.2.0` tag root `CMakeLists.txt` unconditionally does `add_subdirectory(modules/juce)` and `add_subdirectory(examples)` — it has neither the `if(NOT TARGET juce::juce_core)` guard nor the `TE_ADD_EXAMPLES` option that exist on the `develop` branch's `CMakeLists.txt`. Declaring the FetchContent dependency with `SOURCE_SUBDIR modules` (add_subdirectory only `modules/`, which just calls `juce_add_modules(...)`) sidesteps this entirely and avoids depending on tracktion_engine's own root project logic or its version-specific guards.
- Tracktion Engine's `modules/juce` submodule is pinned via an SSH URL (`git@github.com:juce-framework/JUCE.git`, from `.gitmodules`). CMake's `FetchContent` attempts `git submodule update --init --recursive` by default and fails with "Permission denied (publickey)" in an environment without SSH keys for GitHub, even though the top-level repo itself clones fine over HTTPS. Fix: declare `GIT_SUBMODULES ""` on the tracktion_engine `FetchContent_Declare` (skips its submodule entirely) and fetch JUCE independently via its own HTTPS `FetchContent_Declare`, pinned to the exact commit tracktion_engine's submodule references (found via the GitHub Contents API on the `modules` path at the target tag/ref — it returns the submodule gitlink's pinned SHA).
- A project consuming JUCE via CMake must declare `project(... LANGUAGES C CXX)` — `CXX` alone fails CMake's generate step with "Error required internal CMake variable not set... Missing variable is: CMAKE_C_COMPILE_OBJECT", because JUCE bundles C sources (e.g. within harfbuzz).
- Despite the module/target being named `tracktion_engine`, and despite the shipped `examples/TestRunner/TestRunner.h` in this same tag using `using namespace tracktion_engine;`, directly including `<tracktion_engine/tracktion_engine.h>` in a standalone target exposes `Engine`, `UIBehaviour`, `EngineBehaviour`, `PropertyStorage`, `SettingID`, etc. under namespace `tracktion::`, not `tracktion_engine::` — confirmed via compiler diagnostics ("did you mean 'tracktion::UIBehaviour'?"). TestRunner's usage likely resolves through additional context (e.g. its generated `JuceHeader.h`, or another header it includes) not present when including the module header directly.

A headless-safe way to construct `tracktion::Engine` without opening real audio devices: pass an `EngineBehaviour` override whose `autoInitialiseDeviceManager()` returns `false` (mirrors `examples/TestRunner/TestRunner.h`'s `TestEngineBehaviour`) — this is what `src/backend/audio/toolchain_proof.cpp` does.

TK-016 confirmed empirically (both platforms' real build logs, then a genuine local attempt to fix it) that JUCE's own module-target design — not an authoring mistake in this repo's `CMakeLists.txt` — is why `toolchain_proof`/`materializer`/`materializer_proof`/`native_runtime` each independently compile their own copy of the same Tracktion/JUCE translation units (`tracktion_core.cpp`, every `tracktion_engine_*.cpp`, `tracktion_graph.cpp`, and whichever JUCE modules they touch): `juce_add_module` sets each module target's own `INTERFACE_SOURCES`, and CMake forwards those to *every* real (non-`INTERFACE`) target anywhere in a `PUBLIC`-linked dependency chain that actually gets built — not just the first thing that links them. Wrapping the JUCE/Tracktion targets in a new intermediate static library (tried locally: a `tracktion_runtime` target `PUBLIC`-linking `tracktion::tracktion_core`/`tracktion_engine`/`tracktion_graph`/`juce::juce_audio_devices`/`juce::juce_audio_utils`, consumed by the four targets above) does **not** stop this — a real local rebuild showed the wrapper itself compiled a genuinely-shared copy, but every consumer still separately compiled its own copy on top, one target's worth of compilation *worse* than the unwrapped original. The only way to stop the propagation (linking the JUCE/Tracktion targets `PRIVATE` inside such a wrapper) would also silently stop forwarding the include directories, compile definitions, and OS-framework link requirements (CoreAudio/CoreMIDI on macOS, WinMM/DirectSound on Windows, etc.) every consumer's own translation units still need — CMake has no built-in way to forward everything a linked target's usage requirements provide except specifically `INTERFACE_SOURCES`; doing so manually means enumerating and re-declaring every other property via `$<TARGET_PROPERTY:...>` per module, which is fragile and easy to silently under-specify on whichever platform's module needs a system framework not thought to re-export. Rejected as disproportionate complexity for a build-time cost that a working `sccache` mostly already absorbs (confirmed: macOS's real hit rate on this exact duplication is ~94% C/C++). If a future session revisits this, the actual lever worth pursuing first is reducing how many separate executables need to link Tracktion Engine at all (an architectural test-suite question, out of scope for a CI-only Task), not another CMake target-graph wrapper.
