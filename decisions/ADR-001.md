# ADR-001 — Canonical Python Musical Model; Tracktion Engine State as a Runtime Projection

Status: accepted

## Context

Tracktion Engine, the third-party technology inside the Native Audio Runtime, maintains its own internal Edit/Track/Clip model. Corytm's foundational architecture law is that Python knows what the project means musically and C++ knows how to make it sound. This requires deciding which model is authoritative for musical/project meaning when the two could diverge.

## Decision

The Python application core — Corytm Engine — owns Corytm's canonical musical/project state. Tracktion Engine's projected musical/project state is reconstructed from that canonical Python state; it is not maintained as an independent second canonical source. Bidirectional canonical-state reconciliation is out of scope unless a future decision changes this.

## Consequences

Edits are understood and validated against the Python model, not against Tracktion Engine's internal representation. Tracktion Engine's musical/project projection is expected to be reconstructable from canonical Python state rather than independently backed up as a second canonical copy. This decision governs canonical musical/project state specifically — it does not decide persistence, recovery, or caching semantics for other native-runtime state categories (for example plugin scanning, device configuration, or transient playback state) unless those categories participate in canonical musical/project meaning.

## Notes

This canonical/projection relationship is what the process separation in ADR-002 makes physically meaningful, and it targets Tracktion Engine as established in ADR-003.
