# ADR-006 — Tauri 2 as the Desktop Shell

Status: accepted

## Context

Corytm's desktop application (`docs/technical/architecture.md`) needed a technology to package the existing React 19 + TypeScript-strict frontend (`src/frontend/desktop/`) into an installable macOS/Windows application, provide OS integration (window chrome, file dialogs, drag-and-drop, menu bar, file associations, notifications, code signing/notarization, auto-update), and orchestrate the lifecycle of the separate Python application core and Native Audio Runtime processes (ADR-002). This was explicitly left unresolved by `docs/technical/architecture.md`, which noted "Tauri has been considered but is not yet accepted." Electron, Wails, Neutralino.js, and a hand-rolled CEF embedding were also evaluated.

## Decision

Corytm adopts Tauri 2 (a Rust-core framework rendering the frontend in the OS's native WebView — WKWebView on macOS, WebView2 on Windows) as the desktop shell technology. It hosts the existing React/TypeScript frontend unchanged, and uses Tauri's sidecar mechanism to spawn and manage the Python application core and Native Audio Runtime as child processes.

## Consequences

Rust is added as a build/toolchain language, scoped to shell and process-orchestration code, alongside the existing Python and C++ toolchains. Windows packaging must choose a WebView2 distribution mode (evergreen, embedded, or fixed-runtime bootstrapper) at install-build time. Rendering comes from two different native engines (WebKit on macOS, Chromium-via-WebView2 on Windows) rather than one bundled engine everywhere — a manageable but real cross-platform styling risk for future frontend work. Tauri's plugin ecosystem is smaller and younger than Electron's; some native integrations may require small platform-specific Rust/Swift/Kotlin code rather than an existing package. Killing a bundled Python executable via Tauri's sidecar `Child.kill()` is not reliable for a one-file frozen executable — the Python↔shell lifecycle contract needs an explicit shutdown protocol rather than relying on process-kill semantics.

## Alternatives considered

Electron — the credible runner-up: more mature, larger ecosystem, equally license-compatible (MIT), with turnkey signing/notarization/auto-update tooling. Not chosen because it ships a full Chromium+Node runtime per app (working against the footprint headroom the shell needs to leave for a real-time audio process sharing the same machine), and its permissive-by-default security model sits less naturally next to ADR-004's trusted-capability boundary than Tauri's deny-by-default capability system. Reopen this decision if Tauri's native WebView rendering proves inadequate for a canvas-heavy timeline/piano-roll UI, or if a required native capability has mature Electron/Node tooling with no Rust equivalent.

Wails — rejected: commits the shell to Go, a fourth language with no footprint elsewhere in the stack, for no capability Tauri lacks; its v3 was still pre-release and its native-API ecosystem narrower than Rust's.

Neutralino.js — rejected: deliberately thin native API surface, positioned for small utilities, not an app orchestrating two sibling native processes with notarized installers and deep OS integration.

Hand-rolled CEF embedding — rejected: would mean owning the entire packaging/signing/update/API-surface layer that Tauri or Electron already provide, with no offsetting benefit since Corytm's UI itself does no performance-critical rendering (that stays in the separate Native Audio Runtime process).

JUCE's own WebView-based UI hosting — rejected: would collapse the shell into the Native Audio Runtime process, contradicting the three-component shape already established and blurring the ADR-002 process boundary — a new foundational coupling with no identified need.
