# ADR-007 — Protobuf Schema Over a Local Loopback-Socket Transport (Python↔Native Audio Runtime)

Status: accepted

## Context

ADR-002 fixed the Python application core and the Native Audio Runtime as separate processes communicating through "a narrow, versioned local protocol," explicitly leaving the transport undecided. `docs/technical/architecture.md` further establishes that this boundary carries structured commands (Python → native) and events (native → Python) about musical/project edits — not bulk audio or MIDI data, which stays inside the Native Audio Runtime — and that shared serialized boundary contracts are intended to live under `src/schemas/` as a neutral schema distinct from both the Python model and the C++ model. Deployment is strictly local-first and single-machine (ADR-005), so this is a local IPC problem, not a distributed-systems one. gRPC+protobuf, raw sockets with protobuf/FlatBuffers/MessagePack/Cap'n Proto, ZeroMQ, nanomsg/NNG, Cap'n Proto RPC, D-Bus, Apache Thrift, and shared memory were evaluated.

## Decision

The Python↔Native Audio Runtime boundary has two independent parts, deliberately kept separable:

1. **Contract (durable):** commands and events are defined as Protocol Buffers messages under `src/schemas/`, the single neutral schema from which both the C++ (CMake-generated) and Python (uv-managed, generated) bindings are produced. Each message carries an explicit schema version, per ADR-002's "versioned protocol" requirement.
2. **Transport (durable category, replaceable mechanism):** the contract travels over a narrow, local-only, loopback-socket transport — not a general-purpose or distributed-RPC framework such as gRPC. The Python core, which owns the Native Audio Runtime process's lifecycle (ADR-002), spawns it and passes a loopback port and a random per-launch secret; the native process connects and authenticates with that secret before any command traffic is accepted (the same pattern Jupyter uses for its kernel subprocesses). Messages are length-prefixed frames carrying a serialized protobuf envelope.

The initial C++-side implementation of that framing uses JUCE's existing `InterprocessConnection` (already vendored per ADR-003). This is an **implementation detail, not the decision itself**: the application/domain boundary and the wire contract are defined by the protobuf schema and the framing semantics described above, not by that class. A future replacement of the concrete socket/framing implementation, on either side, must not require changing the schema or the commands/events the application layer depends on.

## Consequences

`src/schemas/` becomes a real, buildable artifact early: `.proto` definitions compiled via `protoc`/CMake on the C++ side and via a uv-driven codegen step on the Python side. The only new runtime dependency is the `protobuf` package on the Python side and vendored `protobuf` on the C++ side; the transport itself adds no new dependency (JUCE already provides the initial socket implementation; Python uses stdlib `asyncio`). The same transport mechanism (loopback TCP) is used uniformly on macOS and Windows, avoiding a Unix-domain-socket/named-pipe platform branch. Corytm gives up gRPC-style built-in call/response correlation, deadlines, and cancellation — any synchronous "act and wait for result" interaction needs a small correlation-id layer built on top of the envelope, on both sides, as application-level code rather than a framework feature. Process reconnection and lifecycle handling (native process restart per ADR-002) is Corytm's own code, not a library feature. Because the schema and the transport category are decided independently of the concrete framing implementation, swapping that implementation later (e.g. away from `InterprocessConnection`, or to a different local-socket library) is a transport-internals change, not a schema or application-boundary change, and does not reopen this ADR.

## Alternatives considered

gRPC + Protobuf — the natural single-tool alternative, retained only for its schema choice. Rejected as the transport: gRPC-core has no Windows named-pipe transport (open since 2015) and its Python client cannot use Unix domain sockets on Windows either (open since Feb 2024), so gRPC-on-Windows-with-a-Python-client degrades to plain TCP loopback anyway — it would not actually deliver better cross-platform parity than the chosen approach. Its C++ dependency tree (Abseil, BoringSSL, c-ares, zlib, re2) has documented multi-hour/multi-gigabyte build blowups, a real risk given Windows native CI was already a friction point (TK-006). Its feature set (load balancing, multi-service reflection, auth interceptors) targets distributed microservices, mismatched to one local, always-1:1, single-machine process pair with no network requirement.

ZeroMQ — rejected: libzmq core has been stagnant since its 4.3.5 release (Oct 2023), a maintenance risk for a foundational dependency.

nanomsg/NNG — rejected on the Python side specifically: `pynng`'s last release was Dec 2023, with missing wheels even for older Python versions — unacceptable for a Python 3.14 codebase, despite an otherwise elegant C++ core and transport model.

Cap'n Proto (serialization + RPC) — rejected: its RPC layer's capability-pipelining semantics are more machinery than a narrow command/event surface needs, and its Python binding (`pycapnp`) has a documented history of Windows-specific asyncio integration bugs.

FlatBuffers — rejected: its headline zero-copy benefit targets large/hot payloads; Corytm's payloads are deliberately small structured commands/events, not bulk data, so protobuf's simpler authoring/reflection/JSON-debugging story wins here.

MessagePack — rejected: no schema/IDL of its own; meeting the "narrow, versioned protocol" and "neutral schema generating both bindings" requirement would mean hand-building exactly the discipline protobuf already provides.

D-Bus — rejected: its Windows port is explicitly documented as not security-supported, disqualifying for a desktop-first, Windows-and-macOS product.

Apache Thrift — rejected as redundant: occupies the same niche as gRPC+protobuf without a clear advantage for this pairing.

Shared memory (e.g. Boost.Interprocess, a custom ring buffer) — rejected: solves a high-frequency bulk-data problem this boundary deliberately does not carry (audio buffers stay inside the Native Audio Runtime).

## Notes

Resolves the "Python↔C++ transport" item in `docs/technical/architecture.md`'s Unresolved section and gives concrete shape to that document's Python↔C++ Boundary section. JUCE's `InterprocessConnection` is recorded here as the initial implementation mechanism only, not as the protocol itself, per explicit clarification at approval time — a future implementation swap on either side does not require revisiting this decision as long as the protobuf contract and the local-loopback-socket transport category are preserved.
