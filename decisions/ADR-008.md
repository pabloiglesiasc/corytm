# ADR-008 — Pydantic as the Canonical Domain/Application Modeling Framework

Status: accepted

## Context

EP-005 introduced Corytm Engine's first canonical models — `Project`, `AudioTrack`, `AudioClip` — as frozen `dataclasses`, with one hand-written `__post_init__` on `AudioClip` enforcing a non-negative start time and a strictly positive duration. Canonical Corytm state (ADR-001) is designed to eventually cross the UI, Dorian, persistence, API/import, migration, and Native Audio Runtime-projection boundaries. At most of those boundaries the data arrives as untrusted external input (JSON from the frontend or a future API, a loaded project file, an LLM tool call), not as already-valid Python objects, so invariant enforcement needs to hold for data built from that untrusted shape, not only for values passed positionally by trusted in-process callers. Plain dataclasses only run `__post_init__` when constructed directly with Python values; they have no built-in way to parse and validate nested, dict/JSON-shaped input, so each future boundary would otherwise hand-rolled its own parsing and validation, duplicated per boundary and per nesting level.

## Decision

Pydantic (current stable v2 line) is the required modeling framework for Corytm's canonical/domain/application data — the models owned by Corytm Engine and, as they are introduced, by Runtime and Dorian's application-facing types. A canonical model is a `pydantic.BaseModel` with `model_config = ConfigDict(frozen=True)` (preserving the immutability the prior dataclasses already had) and invariants expressed as field constraints (for example `Field(ge=0)`, `Field(gt=0)`) rather than hand-written `__post_init__` checks. Nested canonical models compose as typed fields (for example `tracks: tuple[AudioTrack, ...]`); Pydantic validates nested models transitively by construction — no separate recursive-validation mechanism is introduced. This governs canonical/domain/application boundary data specifically; it is not a blanket replacement for every small internal implementation structure, which may still use a plain dataclass, `NamedTuple`, or similar when it never crosses a canonical boundary.

## Consequences

Invalid canonical state — a negative timeline position, a non-positive duration, or any future field-level or nested invariant — is rejected explicitly at construction, whether the caller builds the model directly from Python values or from an untrusted dict/JSON shape (`Model.model_validate(...)`), which future persistence, API/import, and Dorian tool-call boundaries can rely on without re-implementing validation. `pydantic.ValidationError` is a `ValueError` subclass, so existing `pytest.raises(ValueError)`-style tests kept working unchanged across this migration. Pydantic (`pydantic` + the compiled `pydantic-core`) becomes a runtime dependency of Corytm Engine; `pydantic-core` ships prebuilt wheels for the repository's supported platforms and Python version, so this adds no new build-toolchain requirement. A future dataclass reintroduced for canonical/domain/application data would silently regress this decision — reviewers should treat that as a defect against this ADR, not a stylistic choice.

## Notes

Applies to the models introduced by EP-005 (`src/backend/core/src/corytm/engine/{clip,track,project}.py`) as of this migration, and governs how future Engine/Runtime/Dorian canonical types are built going forward. `docs/technical/architecture.md`'s "Canonical State and Projection" section points here.
