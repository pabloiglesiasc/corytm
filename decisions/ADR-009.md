# ADR-009 — `corytm` Installable Package Root and Package-Qualified Python Imports

Status: accepted

## Context

`src/backend/core`'s Python code grew through EP-004/EP-005 with no `[build-system]` in `pyproject.toml`, so `uv` treated it as a "virtual" (non-package) project: nothing was ever actually installed. `engine`/`runtime` were reached as bare pseudo-top-level packages only because pytest's own `pythonpath = ["generated", "modules"]` ini option and Pyright's own `extraPaths = ["generated", "modules"]` setting each independently inserted `modules/` and `generated/` onto `sys.path` for their own tool run. Neither mechanism applies to real program execution, so the actual documented way to run the application (recorded in TK-014/EP-005) was `PYTHONPATH=modules:generated uv run python main.py`, run from inside `src/backend/core/` — a manual environment-variable/current-working-directory combination with no equivalent for a caller anywhere else, and no protection against a bare `engine`/`runtime`/`generated` import colliding with an unrelated same-named package. The repository's own Protobuf schema already declares `package corytm.schemas.project;` (`src/schemas/project.proto`), so `corytm` already names this project at its other serialization boundary; it was not otherwise used as the Python package name.

## Decision

`src/backend/core` becomes a real, installable Python package rooted at `corytm`, laid out as a standard `src/`-layout (`src/backend/core/src/corytm/`), built by `hatchling` (`[build-system]` added; `uv run`/`uv sync` build and install it in editable mode automatically, exactly as they already do for `dependency-groups`). `engine/` and `runtime/` become subpackages of `corytm` (`corytm.engine`, `corytm.runtime`); the Protobuf-generated bindings move from a bare `generated/` to `corytm.generated`. The application entry point is exposed as a `[project.scripts]` console script (`corytm = "corytm.main:main"`) instead of a bare `main.py` script.

Import rule: an import that crosses one of the architecture's named ownership boundaries (`docs/technical/architecture.md`'s Naming section — Corytm Engine, Runtime, Native Audio Runtime, and, as it is introduced, Dorian) is an absolute, package-qualified import (`from corytm.engine.project import Project`, `from corytm.runtime.session import materialize_project`, `from corytm.generated.project_pb2 import Project as ProjectMessage`). An import between tightly-coupled sibling modules inside the same one of those subpackages (for example `engine/track.py` importing `engine/clip.py`, or `runtime/session.py` importing its own `runtime/projection.py` and `runtime/transport.py`) is a relative import (`from .clip import AudioClip`). Deep relative traversal (`from ...` or higher) is not used; a module needing to reach outside its immediate subpackage uses the absolute `corytm.`-qualified form instead.

The nested `src/` layout (Python's own src-layout convention, inside the repository's pre-existing `src/backend/core/` path) is deliberate, not cosmetic: a flat `src/backend/core/corytm/` would sit directly under the same directory this project's tests and CI have historically been invoked from, so the pre-existing cwd-based import path this ADR eliminates could keep silently working — masking exactly the failure mode this decision fixes. Nesting `corytm/` one level deeper, under its own `src/`, means only the installed (editable) package resolves it.

## Consequences

`uv run <anything>` — pytest, pyright, ruff, or the `corytm` console script — resolves `corytm.*` imports the same way regardless of the caller's current working directory, because resolution goes through the venv's editable-install pointer rather than an ini-file-specific or tool-specific path hack. Running the application from outside `src/backend/core` no longer needs a manually-set `PYTHONPATH`; the supported invocation is `uv run --project src/backend/core corytm` (or, from inside `src/backend/core`, plain `uv run corytm`), proven cwd-independent by `src/backend/core/tests/test_entrypoint.py`. `pyproject.toml`'s `pythonpath`/`extraPaths` settings are removed as no longer needed; `testpaths`/`include` instead point at `tests` and `src/corytm` directly. `Makefile`'s `check-python` target generates Protobuf bindings into `src/corytm/generated` instead of a bare `generated/` (still gitignored, still never hand-edited, per `CLAUDE.md` §8); no other target changes. Any future Dorian Python code joins this same package as `corytm.dorian`, following the same absolute/relative rule above, rather than needing a new import-path decision.

## Notes

Applies to `src/backend/core`'s existing Python code as of this migration (`engine`, `runtime`, `main`, the generated Protobuf bindings) and governs how future `corytm.dorian` and any other Python subpackage are imported going forward. `docs/technical/architecture.md`'s Naming section is updated to the new paths; this ADR is the rationale for why they changed.
