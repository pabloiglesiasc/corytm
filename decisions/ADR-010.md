# ADR-010 — Protobuf Schema Over a Second, Independent Local-Loopback Transport (Desktop↔Python Core)

Status: accepted

## Context

MS-002's Outcome requires a user to create/edit a Corytm project through real Desktop UI, driving Corytm Engine/Runtime through the Python core. ADR-006 established Tauri as the desktop shell and its sidecar mechanism for spawning the Python core as a child process; FT-010/TK-011 proved that spawn/shutdown lifecycle (a stdout `READY` signal, a stdin `SHUTDOWN` message) against a throwaway proof script, but no channel exists yet for Tauri's Rust core to send the Python core real domain commands (create a project, move a clip) or receive results back. `docs/technical/architecture.md`'s Unresolved section still lists "frontend design-system, component, state-management, and rendering choices" as deliberately open, and no prior decision addresses how Desktop reaches Corytm Engine for the first time.

ADR-007 already solved the structurally identical problem one boundary over (Python core ↔ Native Audio Runtime): a narrow, versioned Protobuf command/event contract under `src/schemas/`, carried over a local loopback socket, with the process that owns the callee's lifecycle passing a port and a random per-launch secret that the connecting side authenticates with before any command traffic is accepted (the Jupyter-kernel pattern). That transport and its framing are already proven cross-platform twice (`transport_proof.cpp`/`test_transport_proof.py`, and `native_runtime.cpp`'s TK-018 long-lived multi-command session).

## Decision

The Desktop (Tauri/Rust) ↔ Python-core boundary reuses ADR-007's proven protocol discipline — a Protobuf command/event envelope over a local loopback socket, length-prefixed frames, per-launch-secret authentication — as a **second, independent** transport, deliberately not sharing a socket, port, secret, or schema/envelope with the Python↔Native Audio Runtime transport:

1. **Contract:** a new schema file under `src/schemas/` (distinct from `project.proto`'s native-facing `Command`/`Event` envelope) defines the Desktop-facing command/event messages. It may reuse existing message *types* (for example a future `MoveClipCommand`) by reference, but its own envelope and versioning are its own — a change to the native-facing envelope must not require a lockstep change here, and vice versa.
2. **Transport:** the Python core process — already spawned by Tauri via the sidecar mechanism (ADR-006/FT-010) — opens a second loopback listener (its own port and random secret, independent of whatever port/secret it later uses internally to spawn and authenticate the Native Audio Runtime) and prints that port and secret over its existing stdout lifecycle channel, the same mechanism that already carries the `READY` signal. Rust connects as a client, authenticates with the secret, then exchanges length-prefixed Protobuf frames — symmetric to how the Native Audio Runtime is a client of Python today.
3. **Sidecar stdio stays lifecycle-only.** The existing stdin/stdout channel (`READY`, `SHUTDOWN`, and now the port+secret handshake line) continues to carry only process-lifecycle signaling, never domain commands or events — those travel exclusively over the new socket.
4. **Python core remains the sole authority over the Native Audio Runtime.** Rust never opens a connection to `native_runtime` directly and never bypasses Python core to reach it; every Desktop-originated edit is authorized and executed by Python core exactly as Dorian's tools are (ADR-004), through Corytm Engine's existing operations and the existing `materialize_then_move_clips`-style live-session mechanism.

This keeps the two transports fully decoupled: either side's schema, port, secret, or concrete socket implementation can change independently, and a bug or protocol version bump on one boundary cannot corrupt or desynchronize the other.

## Consequences

Rust needs a Protobuf codegen toolchain for the first time (`prost`/`prost-build` in `src-tauri/build.rs`), a new build-time dependency alongside the existing Python (uv/grpcio-tools) and C++ (CMake/vendored protobuf) codegen paths. `prost-build` requires a `protoc` executable; rather than depend on an unverified third-party downloader crate (`protoc-prebuilt`, evaluated and rejected below) or couple `check-desktop`'s build order to `check-native`'s already-downloaded CMake artifact, the Rust build fetches and SHA256-verifies its own copy of the same official, already-pinned `protoc` release CMake uses (`src/backend/audio/CMakeLists.txt`'s `v36.1` URLs/hashes), keeping `check-desktop` self-contained and independent of `check-native`'s build order (`Makefile`'s `check` target runs `check-desktop` before `check-native`). Python core becomes a socket *server* on a second front (it already is one, internally, for the Native Audio Runtime connection per ADR-007) rather than only ever being a client of nothing — a straightforward extension of an already-proven `asyncio` pattern, not a new one. The two independent listener/secret pairs mean a compromised or buggy Desktop connection cannot inject traffic into the Native Audio Runtime connection or vice versa. Corytm gives up the simplicity of one shared schema/envelope for both boundaries, accepting some duplication of framing/auth code across two small transports in exchange for the decoupling explicitly requested at approval time.

## Alternatives considered

Extending the existing sidecar stdio channel (structured JSON-lines over the already-proven stdin/stdout pipe) with real domain commands — rejected at approval time: it would blur process-lifecycle signaling with application traffic on the same channel, and forgo Protobuf's schema/versioning discipline that the rest of the stack already relies on.

Sharing one socket/schema/envelope between Desktop↔Python and Python↔Native — rejected at approval time: couples two boundaries with different lifecycles and different trust levels (Desktop/Rust is a UI-facing process; Native Audio Runtime is Python-core-owned and never reached directly by Rust), and would make an envelope/version change on one boundary a forced lockstep change on the other.

`protoc-prebuilt` (a small third-party crate that downloads a `protoc` release for `prost-build`) — considered and rejected for the `protoc`-acquisition problem specifically: it performs no cryptographic verification of the binary it downloads (only a `--version` string check), a real step down from this project's established bar for exactly this artifact (SHA256-pinned in `src/backend/audio/CMakeLists.txt` since TK-009), and is a low-commit-count, single-maintainer crate. `protobuf-src` (vendors and compiles `protoc` from C++ source at Rust build time) was also considered and rejected: it would build a second, independent copy of protobuf/`protoc` from source purely for Rust codegen, duplicating build effort the CMake side already pays for a working, verified binary, with no offsetting benefit.

## Notes

Approved by the user 2026-09-02 after this session surfaced it as a foundational-architecture-boundary decision under `CLAUDE.md` §5 (a new channel establishing how two of the architecture's named primary components communicate for the first time), rather than deciding it silently — mirroring ADR-006/ADR-007's own precedent. The user's explicit constraints (reuse ADR-007's protocol discipline; keep sidecar stdio lifecycle-only; Python core stays the sole authority over the Native Audio Runtime; keep the Desktop channel unnecessarily uncoupled from the Python↔native one) are all captured as binding decisions above, not merely as options considered.

Resolves, for the Desktop↔Python-core boundary specifically, the "how does Desktop reach Corytm Engine" gap `docs/technical/architecture.md`'s Unresolved section left open; the broader "frontend design-system, component, state-management, and rendering choices" items remain open, unaddressed by this decision.
