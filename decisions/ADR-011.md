# ADR-011 — Local JSON File as Corytm's Alpha Project Persistence Format

Status: accepted

## Context

MS-002's Outcome requires a user to create or open a Corytm project through real Desktop UI. Corytm Engine's canonical `Project`/`AudioTrack`/`AudioClip` models (ADR-008) have no persistence surface today — every existing entry point (EP-005/EP-006/EP-010) constructs a project from a hardcoded Python fixture. ADR-005 established Desktop as local-first and explicitly left "persistence implementation... unresolved." `docs/product/strategy.md` §13 requires canonical project semantics to remain independent from storage and the architecture to enable the MVP "without prematurely building generalized cloud infrastructure."

## Decision

A Corytm project is durably represented as a single local JSON file: a versioned envelope — `{"schema_version": <int>, "project": {...}}` — whose `schema_version` is Corytm's own persistence-format version number, independent of `src/schemas/project.proto`'s own per-message wire-protocol versioning. The envelope's `project` payload is, today, produced from the canonical Engine `Project` model via Pydantic's `model_dump`/`model_validate` — the current implementation mechanism, not itself the permanent contract. The durable contract Corytm owns is the versioned JSON shape under `schema_version`; that shape currently mirrors the live Pydantic model exactly, but is free to diverge from it later (for example behind a dedicated persistence-schema/DTO layer) without requiring a new ADR, provided the versioned-envelope contract and the ownership rule below both hold.

Corytm Engine (a new `corytm.engine.persistence` module: `save_project`/`load_project`) is the sole reader and writer of this file's content. Rust/Tauri never parses or serializes project data — it resolves a filesystem path via a native OS file dialog and passes that path to Python core over the already-proven Desktop↔Python channel (ADR-010), which loads or saves the project and, for Open, re-materializes it through the already-proven Runtime/Native Audio Runtime path (reusing `MaterializeProjectCommand` unchanged).

New Desktop-facing commands (`CreateProjectCommand`, `OpenProjectCommand`, `SaveProjectCommand`, and their result events) are added to `project.proto`'s existing `Command`/`Event` oneof and carried over ADR-010's existing channel, per ADR-010 point 1 — no new schema file, transport, or architectural layer.

No project-bundle/directory format is introduced: `AudioClip` carries no external resource reference today, so there is nothing else to bundle.

Alpha project files are not yet guaranteed durable across format changes. `schema_version` exists so a future file can be distinguished from an older one, but no migration tooling, deprecation policy, or backward-compatibility guarantee exists yet for files written during Alpha — a later `schema_version` bump may simply fail to load an earlier file rather than convert it. Formal migration/support policy, along with cloud sync, collaboration, Web/Mobile storage representations, crash recovery, autosave, undo-history persistence, and encryption/compression, all remain exactly as unresolved as ADR-005 already left them.

## Consequences

Corytm Engine gains a small, flat persistence module with no new runtime dependency — Pydantic's existing `model_dump`/`model_validate` implements today's payload shape. Because the format's contract is the versioned JSON shape rather than "whatever Pydantic currently produces," a later need to decouple the on-disk shape from the in-memory model (for example if Engine's live model grows fields that shouldn't be part of the durable file, or vice versa) is an implementation evolution within this decision, not a reason to revisit it. `runtime/desktop.py` gains command handlers analogous to its existing `MoveClipCommand` handler. Tauri gains one standard first-party dependency (`@tauri-apps/plugin-dialog`) for native file dialogs. Because no backward-compatibility guarantee exists yet, early Alpha project files may need to be recreated rather than migrated if the format changes before a real migration policy exists — an accepted cost at this stage; formal persistence/recovery hardening remains a Beta-phase concern (`docs/project/plan.md`).

## Alternatives considered

Reusing `project.proto`'s `Project` message as the binary file format was rejected: it would conflate a live wire contract with a long-lived file format, and lose human-diffability during Alpha's own development. SQLite/embedded-DB storage was rejected as disproportionate to a canonical model this small and premature ahead of Beta's persistence/recovery hardening. A generic pluggable storage-backend abstraction (local today, cloud/collab later) was rejected as exactly the premature cloud-architecture investment `docs/product/strategy.md` §13 warns against.

## Notes

Approved by the user 2026-09-02 under `CLAUDE.md` §5, mirroring ADR-006/ADR-007/ADR-010's precedent of surfacing a foundational, expensive-to-reverse boundary decision rather than deciding it silently. Does not supersede ADR-005 — it narrows exactly the piece ADR-005 explicitly left open, changing nothing about ADR-005's own local-first direction. Two refinements were applied before acceptance: an explicit disclaimer against implying indefinite backward compatibility for Alpha-era files, and reframing the durable contract as Corytm's own versioned JSON format (Pydantic named only as its current implementation mechanism) rather than Pydantic's exact serialized shape.
