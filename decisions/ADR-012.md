# ADR-012 — Tailwind CSS as Corytm Desktop's Styling Authoring Layer; `@ladle/react` for Component-Catalog Preview

Status: accepted

## Context

`docs/product/design.md` §6 deliberately left "component library / headless primitive choices" and "detailed token values" open, to be decided "when the design system is first materialized against real UI work." FT-025 was that first materialization: `tokens.css` (semantic CSS custom properties, light/dark via `prefers-color-scheme`) plus hand-written `components.css` classes and two first catalog components (`Button`, `NumberField`). Human/manual validation of that first pass surfaced concrete, real defects — a control radius reading as dated/toolkit-like rather than Corytm's approved "low-to-medium-radius" direction, a primary-button hover state whose contrast collapsed into the background, and an overall screen reading as a developer/proof utility rather than the beginning of a professional Corytm surface — and, separately, the explicit observation that continuing to hand-write CSS for a growing catalog would not scale in iteration speed or consistency.

An evaluation was run against explicit criteria: Corytm's ownership of semantic tokens and visual language; dark/light theming; accessibility and interaction-state quality; consistency and ease of building Corytm-owned components; avoidance of a competing third-party visual identity; maintainability under AI-assisted development; integration cost with the current Tauri/React/Vite stack; portability of shared token foundations to a future Web surface without forcing an identical implementation; migration cost from the current codebase; and suitability for a professional, relatively dense music-production interface rather than generic SaaS UI. Candidates compared: staying on native CSS/CSS Modules; Tailwind CSS (utility-first); Panda CSS (typed, zero-runtime CSS-in-JS with first-class token "recipes"); runtime CSS-in-JS (styled-components/emotion). Headless/adaptable accessible-primitive libraries (Radix UI, Base UI) were considered separately, as an orthogonal question from the styling-authoring mechanism.

## Decision

Adopt **Tailwind CSS 4** as Corytm Desktop's utility-class *authoring* layer, with its own default theme entirely **replaced**, not extended, by Corytm's existing semantic tokens: Tailwind v4's `@theme` block maps its theme namespace directly onto the CSS custom properties already defined in `tokens.css` (`--color-*`, `--radius-*`, `--font-sans`), so Corytm's tokens remain the sole source of truth for value and for light/dark behavior (`prefers-color-scheme`-driven, unchanged) — Tailwind never introduces its own default palette, radius, or spacing scale. Components author styling by composing utility classes bound to these token names; an arbitrary one-off value or a Tailwind default-palette value that bypasses the token system is not a normal way to style a component.

Adopt **`@ladle/react`** as the component-catalog preview tool, scoped to exactly the components and interaction states FT-025 actually has (`Button`, `NumberField`) — not a speculative catalog built ahead of real components.

Headless/adaptable accessible-primitive libraries (Radix UI, Base UI, or similar) are **explicitly deferred**: nothing in the current UI needs a dialog, dropdown, slider, or other complex interactive widget yet. When one is needed, a headless/adaptable primitive is the default choice over hand-rolling accessible interaction behavior, per `docs/product/design.md` §4/§5's existing preference — this ADR does not decide which one, only that the question stays open until a real need exists.

## Consequences

`src/frontend/desktop/src/components.css`'s hand-written `.button`/`.field`/`.toolbar`/`.panel` classes are retired in favor of Tailwind utility classes; `tokens.css` remains unchanged in purpose (the durable value/theming source) and is now consumed by Tailwind's `@theme` mapping rather than by bespoke classes. Tailwind's own base-reset layer (`box-sizing: border-box`, margin resets) supersedes the equivalent hand-written rules that existed in `tokens.css`. Each catalog component gains a `*.stories.tsx` file for Ladle. Corytm's token values stay portable in principle to a future Web surface's own styling mechanism (whatever it turns out to be) without forcing an identical component implementation there — only the token *values*, not Tailwind itself, are the shared foundation across surfaces.

## Alternatives considered

**Panda CSS** — its typed "recipe" system is a genuinely stronger long-term consistency mechanism than utility classes, and it ships with no default theme at all (arguably a stronger structural guard against inheriting a "generic SaaS" look than Tailwind's opt-out-of-defaults approach). Rejected for now: its adoption cost (authoring a recipe/token config layer, an added build step) is not yet earned by a two-component catalog, and its smaller, newer API surface carries more risk of a subtly wrong AI-assisted edit than Tailwind's much larger, more standardized surface. Worth revisiting once the catalog and its variant surface genuinely grow.

**Plain CSS Modules** — the lowest-risk, lowest-migration-cost option (near-zero change from the current approach, just file-scoped). Rejected as the primary authoring mechanism because it does not address the actual problem raised — iteration speed and enforced consistency — it only reorganizes the same hand-written-CSS approach that produced the defects motivating this decision.

**Runtime CSS-in-JS (styled-components, emotion)** — viable and well-understood, but its runtime style-injection cost is a real concern for a dense, frequently-updating professional audio interface; zero-runtime approaches (Tailwind, Panda, vanilla-extract) are the better fit for that constraint.

## Notes

`docs/technical/architecture.md`'s Unresolved section is updated to reflect this decision: the frontend design-system's *styling mechanism* is now settled (this ADR); concrete component-catalog contents, icon library, and any future headless-primitive choice remain open, per `docs/product/design.md` §6.
