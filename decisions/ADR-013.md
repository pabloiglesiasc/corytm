# ADR-013 — Groq-Hosted GPT-OSS as Dorian's Alpha Model-Provider Proof, Behind a Provider-Neutral Boundary

Status: accepted

## Context

EP-008 built Dorian's trusted-tool boundary (ADR-004) — `corytm.dorian.tools.move_clip` validates and executes a proposed edit — but deliberately proved it with a hand-constructed `MoveClipProposal`, standing in for a model's output; no model or provider has ever called it. MS-002's Outcome explicitly still requires a real model to do so for Alpha's second end-to-end path (user → Dorian → Corytm Engine → Runtime → sound) to be real and demonstrable, not simulated. Selecting an actual provider/model is a Protected Product Decision: `docs/product/strategy.md` §18 lists "major provider-strategy changes" as requiring explicit human approval, and §19 lists "exact provider/model selected for Allegro/Virtuoso/Maestro" as an open strategic question not to be silently elevated to a permanent commitment. This was put to the user, who approved a specific, deliberately narrow and temporary choice.

## Decision

For Alpha's proof only, Dorian calls Groq-hosted GPT-OSS as its first real, live model provider, through a provider-neutral boundary so nothing outside that boundary depends on Groq's SDK, request/response shapes, or model identity:

- `corytm.dorian.providers.base` defines `ToolSpec`/`ToolCall` (a provider-neutral tool schema and result) and a `ModelProvider` protocol (`propose_tool_call`) — the only concepts any other Dorian module may depend on.
- `corytm.dorian.providers.groq.GroqProvider` implements `ModelProvider` against the official `groq` PyPI SDK (`AsyncGroq`), translating Groq's OpenAI-compatible tool-calling response into a `ToolCall`. It is the only module permitted to import `groq` or know its request/response shapes.
- `corytm.dorian.agent` orchestrates: it builds a `ToolSpec` from an existing tool's own Pydantic proposal model (`tool_spec_from_model`, applied to `corytm.dorian.tools.MoveClipProposal`), calls the configured `ModelProvider`, and validates the raw returned arguments through that same existing Pydantic model — reusing ADR-004's validate-then-execute boundary unchanged, not a new one. A proposal that fails validation is rejected the same way a hand-constructed one already was.
- `openai/gpt-oss-20b` is the default model. `openai/gpt-oss-120b` is an approved fallback, to be used only if a small, explicit evaluation (representative simple move-clip instructions, asserting correct tool selection and valid arguments) shows 20B does not meet the required reliability — not upgraded by intuition or general preference.
- `GROQ_API_KEY` is a dev-only environment variable, read by the `groq` SDK's own default resolution, never committed and never surfaced as a product-facing credential. No BYOK flow, no commercial credential UX, no usage/billing surface.

Explicitly not decided here, and unaffected by it: the general provider-agnostic routing/model-router architecture (`docs/technical/architecture.md`'s Model Routing section); the Allegro/Virtuoso/Maestro tier-to-model mapping; BYOK commercial policy (`docs/product/business-model.md` §4); provider exclusivity. `ModelProvider` exists precisely so a second, different provider is a second implementation of one method, not a rework of `agent.py` or any tool.

## Consequences

This is the first external network dependency, and the first place a third-party API secret enters this codebase. The evaluation that actually calls Groq requires a real key this session does not hold — it is a human-run acceptance step, mirroring this project's own established pattern for evidence automation cannot produce itself (EP-005's audible smoke test; EP-011/EP-012's real-UI confirmation). `groq` (the official SDK) is added as a new runtime dependency to `src/backend/core` — chosen over hand-rolled HTTP (more to build and maintain) and over the unrelated `openai` SDK (correct for an OpenAI-compatible API, but not the vendor actually being called, and a heavier, less direct dependency for this purpose). Because `agent.py` depends only on `ModelProvider`, a later real provider/routing decision does not require reworking Dorian's tool-calling internals — only a new adapter. This ADR's specific provider/model choice is expected to be revisited, not treated as Corytm's permanent AI-provider strategy.
