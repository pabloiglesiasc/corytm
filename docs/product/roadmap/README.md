# Corytm Product Roadmap

Status: canonical, human-approved product-roadmap direction — established 2026-09-03. This directory is direction, not a finished specification, an implementation backlog, or PMO's own execution record; it answers which product capability belongs to which lifecycle phase, on which surface.

`docs/product/roadmap/` is Corytm's canonical, capability-level map of what belongs to which lifecycle phase, on which surface — one canonical product-roadmap artifact for source-of-truth purposes, split across files by phase rather than kept in a single growing document. `docs/product/strategy.md` and `docs/product/business-model.md` remain canonical for *what Corytm is and why*; `docs/project/plan.md` remains canonical for *what evidence/quality is required to exit a lifecycle phase*; this directory is canonical for *which capability belongs to which phase, on which surface*. PMO (`docs/project/**`) realizes this roadmap rolling-wave — Epics and Features are created just-in-time against it, never pre-created wholesale to mirror it, and this directory is never itself a duplicate roadmap of PMO's own execution state.

## Directory structure

```
docs/product/roadmap/
├── README.md   — this file: purpose, authority, reading/mutation rules, high-level overview
├── alpha.md    — canonical entries for every capability whose first rollout, on any surface, is Alpha
├── beta.md     — canonical entries for every capability whose first rollout, on any surface, is Beta
└── stable.md   — canonical entries for every capability whose first rollout, on any surface, is Stable
```

A capability lives in exactly one file — the file matching the phase of its *first* rollout on any surface — even when its `Rollout:` line also names a later phase on a second surface (e.g. a capability first shipping `Desktop — Alpha` and later `Web — Beta` lives only in `alpha.md`; `beta.md` does not repeat it). This mirrors `docs/project/epics/`, `docs/project/features/`, and `decisions/`'s own established pattern in this repository: a growing catalog of many discrete records gets a directory, not one file that grows without bound — `CLAUDE.md` §4 already treats `specs/` and `decisions/` as single canonical artifacts despite being directories, and this follows the same precedent. It also lets a session working a given lifecycle phase read only that phase's file (`CLAUDE.md` §7's "discover only what the Feature needs," applied to the roadmap itself) instead of loading the whole roadmap to work on Alpha alone.

## How to read this roadmap

- A capability appears **exactly once** across this roadmap, in the file matching the lifecycle phase in which it first ships on any surface — never repeated in a later phase's file. Its `Rollout:` line is the complete record of every surface and phase it reaches; the same capability reaching a second surface at a later phase is recorded by adding that surface to the *original* entry's `Rollout:` line, in its home file — not by writing a new row anywhere else. The same surface never appears twice within one capability's `Rollout:` line. An omitted surface means that capability is not currently planned there.
- A same-surface maturity progression — a foundation at one phase, a materially deeper version of the same underlying idea at a later phase — is **not** the same capability reaching a second surface, and is not written as one entry spanning two phases/files for one surface. It is two genuinely distinct, sequential capabilities at roadmap granularity, each with its own single entry in its own first-phase file (e.g. "Recent projects (basic list)" in `alpha.md` and "Recent-project browser" in `beta.md` are two entries, not a duplicate of one another).
- Not every capability is user-facing. Some are enabling/infrastructure capabilities — versioned persistence formats, provider-neutral boundaries, migration frameworks, realtime-safety hardening, and similar — that exist to make other, user-facing capabilities possible, without a surface interaction of their own. A lifecycle assignment means the capability must be **realized and validated for that surface by that phase's exit**. When the capability is user-facing, its corresponding surface interaction must also exist; backend/infrastructure realization alone does not satisfy a user-facing roadmap capability. An enabling/infrastructure capability's own realization is satisfied by its backend/infrastructure existing and being validated — it has no separate surface-interaction bar to clear. `docs/technical/architecture.md`'s Vertical Delivery & Surface Authority section states the same rule for user-facing capabilities at the Feature-delivery level; this roadmap decides *which* capabilities are user-facing versus enabling, not that section.
- Entries begin terse — normally title plus `Rollout:` only. Detail (scope, acceptance shape) is added progressively, directly inside that capability's one canonical entry, as it nears implementation — the same way Epic/Feature detail is filled in just-in-time. Category grouping within a phase file is for readability only; category order does not imply implementation order. This applies uniformly through `stable.md` — Stable's entries stay terse and their detail is deferred furthest, but they remain at approximately the same Feature/capability granularity as `alpha.md` and `beta.md`, not collapsed into broader objective-level statements.
- Every entry is **Committed** by default and carries no explicit `Commitment:` line: it participates in its assigned phase's lifecycle-exit criteria once assigned. A small number of entries instead carry `Commitment: Conditional` — genuinely optional long-term product hypotheses this roadmap still wants to represent, but that do not participate in lifecycle-exit criteria until an explicit Product Decision activates them. Used sparingly, only where an existing product-strategy document already hedges the capability this way (`docs/product/strategy.md`'s own "optional long-term vision, not a roadmap commitment" framing) — not a general escape hatch for merely uncertain scope. Conditional is independent of Protected: a capability can be Committed roadmap intent yet still require a `CLAUDE.md` §5 Protected Product Decision before implementation (BYOK, the Web billing/subscription capabilities in `beta.md` all stay Committed — expected roadmap scope — while still gating on their own Protected Decision). Conditional means the capability's very inclusion is not yet a commitment at all, independent of whatever Protected-Decision gate its eventual implementation might separately carry.
- This roadmap carries no status/done markers and no FT/TK cross-references by design — that is PMO's job (`docs/project/status.md` and the Epic/Feature/Task records), not this directory's. Historical FT/TK record granularity is not a sizing precedent for the entries in `alpha.md`/`beta.md`/`stable.md`.
- A handful of entries are marked **⚠ Flag** — each is explained in Flags below, and none is resolved by this roadmap's mere existence.

## Mutation & Authority

This roadmap is normative but mutable. It sits beside `docs/product/strategy.md`/`docs/product/business-model.md` in `CLAUDE.md` §4's source-of-truth order. Two kinds of change are treated differently:

- **Progressive refinement** — turning a terse entry into fuller scope/acceptance detail as it nears implementation, re-categorizing for readability within its phase file, fixing an inaccurate description, or consolidating/splitting an entry to match a materially clearer understanding of the same underlying capability — is ordinary PMO work, done autonomously as part of normal Feature/Epic discovery.
- **Material reassignment** — moving a capability's lifecycle-phase or surface assignment (which, when the phase changes, means physically moving its entry to a different file), changing major capability scope/family, or changing an entry's Commitment between Committed and Conditional — is a product decision at the appropriate governance level, never a silent edit to match whatever implementation happened to do. Where the reassignment would itself touch a `CLAUDE.md` §5 Protected Product Decision (platform commitments/sequencing, major capability families, major lifecycle-definition changes, major BYOK/monetization changes, etc.), it requires explicit human approval before this roadmap changes. Where it doesn't reach that bar but is still a material scope change, it is proposed explicitly rather than decided silently, mirroring the CPO Mandate's (`CLAUDE.md` §3) proposal-not-authority posture.

Completed historical Feature/Task PMO records are never rewritten to match a later revision of this roadmap.

## Lifecycle Relationship

`docs/project/plan.md`'s Lifecycle Model defines Pre-alpha → Alpha → Beta → Stable and each phase's evidence/quality exit bar. This roadmap's phase files are that same four-phase structure applied to product capability: `alpha.md`'s entries are exactly what `plan.md`'s Current Phase: Alpha section means by "every capability this roadmap assigns Desktop — Alpha." Each phase file opens with its own short framing paragraph connecting it back to `docs/product/strategy.md` §14's phase rationale and, for Alpha, `plan.md`'s exit-criteria conditions that the capability list alone doesn't guarantee (real-time audio, a credible Desktop foundation in aggregate, vertical Dorian integration) — read there, not duplicated here.

## Flags

Items marked ⚠ Flag in `alpha.md`/`beta.md`/`stable.md`, listed once here rather than repeated inline:

1. **Real audio-file import / project external-resource references (`alpha.md`)** — `docs/technical/architecture.md`'s Unresolved section and ADR-011 deliberately left the project-bundle/external-resource format open (`AudioClip` today carries no external-resource field at all). Assigning these to Alpha does not itself decide that format; it means a new ADR resolving how a clip references external audio is needed before implementation, mirroring ADR-011's own precedent for a narrow, concrete decision. Not automatically a `CLAUDE.md` §5 Protected Product Decision by its enumerated categories, but touches persistence-strategy-adjacent territory closely enough that surfacing it for explicit confirmation before that ADR is written is recommended rather than deciding it as routine implementation.
2. **Project resource bundling/portability (`beta.md`)** — the same open question, at the point it must actually support moving a project between machines (packaging/directory format). Same treatment as (1).
3. **BYOK configuration (`beta.md`, Dorian)** — Committed roadmap intent, not Conditional. `docs/product/business-model.md` §4 and `CLAUDE.md` §5 name "major BYOK commercial-policy changes" as a Protected Product Decision; implementing this capability requires that Protected Decision first, possibly coordinated with (but not necessarily identical to) the coherent commercial decision set in (4) below.
4. **Subscription plans/entitlements, usage/credit balance, checkout/subscription management, upgrade/downgrade/cancel, billing history/invoices, credit top-ups, usage-limit enforcement (`beta.md`, Web Commercial)** — Committed roadmap intent, not Conditional. Collectively enter `CLAUDE.md` §5's "monetization model," "subscription architecture," and "major pricing/entitlement boundaries" Protected Product Decision territory, and `docs/product/business-model.md` §8's Open Commercial Questions. This does **not** mean each row needs its own separate Protected Decision: the minimum coherent commercial decision set — likely covering tier/pricing structure, entitlement boundaries, and credit/usage accounting together, since they're interdependent — must be resolved and shaped as a coherent whole before any of this category's implementation begins, not decided piecemeal per UI row. This roadmap does not pre-approve any of it.
5. **Remix/fork shared project, Optional publishing/discovery foundation (`stable.md`)** — marked `Commitment: Conditional`. `docs/product/strategy.md` §14 names social/community capability as "optional long-term vision only, not a roadmap commitment." Conditional entries are visible in this roadmap but do not participate in Stable's lifecycle-exit criteria unless and until an explicit Product Decision activates them; strategy.md §14 has been reworded to point at this mechanism rather than assert "not a roadmap commitment" in a way this roadmap's own inclusion of them would otherwise contradict (see governance diffs).
6. **Audio-to-Project category, all four entries (`stable.md`)** — marked `Commitment: Conditional`, same mechanism as (5). `docs/product/strategy.md` §12 explicitly frames this as "not an Alpha commitment, current roadmap item, or implementation requirement," and §19 keeps "whether and when it is pursued" as an open strategic question; §12's wording has been reworded for the same reason as (5).
7. **Organization/team accounts, team billing/shared usage (`stable.md`)** — Committed roadmap intent, same Protected Decision territory as (4); governed by whatever coherent commercial decision set is in place by the time this Stable-phase work approaches, not necessarily a new separate decision per row.

None of these seven items is resolved, decided, or pre-approved by this roadmap's existence — each still requires its own decision (or, for (5)/(6), an explicit activation decision) at the appropriate governance level when it nears implementation.

## Explicitly excluded from this roadmap

Marketing campaigns, SEO, content marketing, and sales operations are not product capabilities and are not tracked here, even though `docs/product/strategy.md` §3 mentions "landing/marketing" as an eventual *business* responsibility of the Commercial Web Platform — that is a go-to-market/business-operations concern (`CLAUDE.md` §3's CoS universe), not a product capability this roadmap maps to a surface and phase.
