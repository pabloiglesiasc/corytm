# EP-005 — First Sound: Minimal Track and Clip Through Tracktion

Status: active
Milestone: MS-002

## Objective

Prove the first real, minimal slice of MS-002's Outcome end to end: a real Corytm Python application entry point owns a minimal canonical project (one audio track, one audio clip), that state crosses the ADR-007 Protobuf/local-loopback boundary into the Native Audio Runtime, Tracktion Engine materializes it as its runtime projection (a real `Edit` with a real `AudioTrack` and `WaveAudioClip`), and the project produces actual sound — genuinely exercising the whole `user → desktop → Python core → Corytm Engine → Runtime → Native Audio Runtime → Tracktion Engine → sound` path for the first time, at the smallest scope that proves it for real rather than on paper.

## Scope / Out of scope

In scope: a deliberately minimal Corytm Engine domain model (`Project` containing one `AudioTrack` containing one `AudioClip`, timing only — no MIDI, plugin references, or automation on the model); a real Protobuf schema for this domain (`src/schemas/project.proto`) plus one command (send the whole project once) and one event (the render outcome), generated into both C++ and Python bindings exactly as FT-008 established; a real Python-core application entry point (not another placeholder proof script) that constructs one in-memory `Project` and drives it through the Runtime module and the already-proven ADR-007 transport/ADR-002 process-lifecycle mechanisms; Native Audio Runtime code that turns the received command into a genuine `tracktion::Edit` (via `Edit::createSingleTrackEdit`, `insertWaveClip`) and renders it deterministically offline via `Renderer::Parameters`/`EditRenderer::render` — no real audio device, so it runs in headless CI — using a deterministic, natively-generated sine-wave WAV file as the clip's source audio (the sound path goes through Tracktion's real project/timeline/render model; nothing bypasses it by playing that WAV directly); an automated, cross-language test proving the whole round trip; a documented, human-executed local audible smoke test as a distinct acceptance boundary automation cannot substitute for.

Out of scope (revisit only with concrete implementation evidence a slice this small cannot avoid it): MIDI, plugins, automation, mixing/bus routing, Dorian, any production UI, persistence of the project across runs, more than one track or clip, real user-imported audio assets (the fixture is synthetic, generated by the Native Audio Runtime itself as an internal implementation detail — the Corytm Engine domain model does not model "where the audio came from"), and a generalized incremental command/event synchronization framework (this slice sends one full-snapshot command once per run; ADR-002's "versioned protocol" and `docs/technical/architecture.md`'s "commands express intentions, events express facts" are both satisfied by two concrete message types, not by CQRS/event-sourcing/bus infrastructure). This Epic reuses EP-004's Tauri shell, schema/codegen pipeline, transport framing, and sidecar spawn/shutdown mechanisms exactly as proven — it does not reopen or modify any of them.

## Acceptance criteria

A real Python entry point constructs an in-memory `Project` (one `AudioTrack`, one `AudioClip`) via the Corytm Engine domain model, spawns the Native Audio Runtime process, and sends the project across the ADR-007 transport as a single command. The Native Audio Runtime materializes that command as a real Tracktion `Edit` — one `AudioTrack`, one `WaveAudioClip` backed by a deterministically-generated sine-wave fixture matching the clip's duration — and renders it offline to a WAV file with no real audio device, then sends back an event describing the render (at minimum: the output file path and a measure proving real, non-silent signal content, e.g. sample count and peak/RMS). An automated, cross-language test exercises this whole round trip locally and passes, and the render is shown to be deterministic (not merely "the job succeeded") without needing CI audio hardware. Separately, a human can run the entry point locally and listen to (or otherwise directly verify) the rendered output as an audible smoke test — recorded as a distinct, explicitly non-automated acceptance step.
