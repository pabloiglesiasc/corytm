# EP-007 — CI Build-Performance Follow-Up

Status: active

## Objective

Diagnose and resolve the two concrete inefficiencies the prior CI Optimization work's own post-optimization real GitHub Actions evidence exposed on the `check` workflow — Windows compiler caching being completely inactive, and redundant native compilation of shared Tracktion/JUCE translation units across multiple Corytm targets — without touching product functionality or any in-flight product Epic (EP-006).

## Scope / Out of scope

In scope: `.github/workflows/check.yml`, `src/backend/audio/CMakeLists.txt`, and any other CI/build-only file needed to diagnose or fix Windows sccache routing (MSVC C/C++ and Cargo/Rust) and native target-graph duplication; updating `docs/project/risks.md`/`.claude/memory/` with the empirical findings.

Out of scope: any change to Corytm product behavior, Corytm Engine, Runtime, Native Audio Runtime product code, Dorian, or EP-006 (First Edit); switching the Windows CMake generator away from Visual Studio/MSBuild (preserved per prior established precedent unless this Epic itself finds and the user approves decisive evidence to the contrary); any new CI quality gate weakening.

## Acceptance criteria

- The Windows-specific root cause(s) of zero observed sccache compiler-cache activity (both native MSVC C/C++ and Cargo/Rust) are diagnosed from real GitHub Actions evidence (not assumed), and each half is either fixed with observable compiler-cache requests on the next real Windows run, or left with the fix/mitigation applied plus a documented, evidence-based account of why it could not be conclusively resolved from CI logs alone.
- The native CMake target graph's actual duplicate compilation of shared Tracktion/JUCE translation units is measured, and — only where doing so is genuinely safe (no change to linkage semantics, compile definitions, JUCE/Tracktion requirements, or test coverage) — reduced via an idiomatic CMake target-graph restructuring, with any rejected consolidation opportunity documented with its reason.
- macOS's already-confirmed CI improvement (~6 minute wall time, ~91% overall / ~94% C/C++ sccache hit rate) is not regressed.
- No existing quality gate is weakened and no product/EP-006 code is touched.
