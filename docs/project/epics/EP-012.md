# EP-012 — Real Track/Clip Authoring

Status: done
Milestone: MS-002

## Objective

Prove genuine user-driven track/clip authoring — not merely moving the one hardcoded fixture clip every prior Desktop Feature has relied on — advancing MS-002's still-unmet "a user can create or open a Corytm project and produce actual sound through the full real stack via direct manual editing" Outcome. Surfaced by the broadened Next-Work Selection Priority (`docs/project/plan.md`) once EP-011/FT-024 exhausted its own recorded scope: `docs/technical/architecture.md`'s own Unresolved section already named "any track/clip authoring UI beyond the existing move-clip fixture trigger" as open, and a freshly created project has zero tracks and no way to add one through today's UI.

## Scope / Out of scope

In scope, as one Feature (see Notes on why this doesn't split further):

1. Corytm Engine gains two real editing operations alongside the existing `with_clip_moved`: adding an empty track to a project, and appending a clip (specified only by duration) to a track.
2. `project.proto`'s `Command`/`Event` oneofs gain `AddAudioTrackCommand`/`AudioTrackAddedEvent` and `AddAudioClipCommand`/`AudioClipAddedEvent`. Both are dispatched entirely by re-sending the whole mutated project through the already-proven `MaterializeProjectCommand`/`materialize_project` path — no native/C++ change, since `wire_codec.cpp`'s `toProjectSpec` already converts every track/clip generically.
3. The Desktop channel's persistent connection (established by FT-024) gains `add_track`/`add_clip` Tauri commands.
4. A minimal Desktop UI lets a human add a track and append one or more clips to it, observing genuine non-fixture render evidence. This is the first real materialization of `docs/product/design.md`'s design-system direction against real UI work (semantic tokens, dark/light theming, a first small component catalog), reviewed via the `ui-ux-review` skill.

Out of scope, deliberately:

- **Multi-track materialization.** `materializer.cpp`'s `buildEdit` only ever reads `project.tracks[0]` (`Edit::createSingleTrackEdit`) — a real, pre-existing native-runtime limitation, confirmed by reading the code, not assumed. Reworking it to a genuine multi-track `Edit` is a distinct native-runtime surface deserving its own isolated proof (mirroring this project's own "prove one increment, then the next" precedent), not folded into this Epic. This Epic's UI disables "Add Track" once a track already exists, so no realistic path exercises the limitation.
- **Any audio-source/import/external-resource reference on `AudioClip`.** `AudioClip` today carries only `id`/`start_seconds`/`duration_seconds`; a new clip is rendered exactly like the existing fixture, as another natively-generated sine-wave region. Adding a real external-audio reference would newly implicate the project-bundle/external-resource question ADR-011 explicitly left unresolved — not decided here, silently or otherwise.
- Arbitrary clip placement, dragging, resizing, or deletion — a new clip is placed automatically after the track's existing content.
- Track/clip renaming or deletion.
- Multiple concurrent projects or windows.
- Dorian/provider wiring.
- Any change to the local JSON persistence format (ADR-011 unchanged — clips remain timing-only, nothing new to persist).

## Acceptance criteria

A human can launch the real Desktop app, create a new (zero-track) project, add a track to it, add one or more clips to that track (each specified only by a duration), and observe genuine, non-fixture render evidence (sample count, peak amplitude) proving the Native Audio Runtime actually rendered the user-authored content — proven by automated tests plus a human confirmation step for the real running UI (the first real interactive input and first real dark/light-themed surface this project has shipped), mirroring EP-011's own acceptance pattern of combining automated proof with a human look at what automation can't exercise.

## Dependencies

EP-011/FT-024 (`validating`) — the persistent Desktop-channel connection and `Command`/`Event` envelope this Epic extends. Per `CLAUDE.md` §6's corrected dependency-safety check, this Epic does not wait on FT-024's own pending Windows evidence: it reuses the already-locally-validated persistent-connection/command-send/event-decode pattern (the same shape `RSK-014`/`RSK-015` already closed cross-platform for `move_clip`/`create_project`/`save_project`/`open_project`) rather than depending on FT-024's own new, still-unconfirmed surfaces (`tauri-plugin-dialog`, `RSK-016`) — this Epic touches no file dialog at all.
