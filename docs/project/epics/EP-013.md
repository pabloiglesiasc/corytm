# EP-013 — Dorian's First Live Model Call

Status: done
Milestone: MS-002

## Objective

Complete MS-002's second, still-unmet Outcome half: Dorian performing a real semantic edit through the same governed application path, driven by an actual live model rather than a hand-constructed proposal standing in for one. EP-008 built and proved the trusted tool boundary (ADR-004: `corytm.dorian.tools.move_clip`); this Epic wires a real model to actually call it, per the user's explicit, protected provider-selection decision (`decisions/ADR-013.md`).

## Scope / Out of scope

In scope:

1. A provider-neutral model-provider boundary (`corytm.dorian.providers`): `ToolSpec`/`ToolCall` and a `ModelProvider` protocol, so no other Dorian code depends on any specific provider's SDK or response shape.
2. A Groq-hosted GPT-OSS adapter (`corytm.dorian.providers.groq.GroqProvider`) implementing that protocol — Alpha's only concrete provider, per ADR-013.
3. Orchestration (`corytm.dorian.agent`) that builds `move_clip`'s tool schema from its own existing `MoveClipProposal` model, calls the configured provider, and validates the raw response through that same model — reusing ADR-004's boundary unchanged.
4. A small, explicit evaluation harness proving GPT-OSS 20B reliably selects the tool and produces valid arguments for representative simple move-clip instructions — this Epic's human-run acceptance step (a real `GROQ_API_KEY` and live network call, which this development session does not hold), mirroring this project's established pattern for evidence automation cannot produce itself (EP-005's audible smoke test; EP-011/EP-012's real-UI confirmation).

Out of scope, deliberately (per ADR-013 and the user's own framing):

- Any general routing/model-router architecture, provider registry, or fallback matrix — one `ModelProvider` protocol plus one Groq adapter is the whole shape for Alpha.
- The Allegro/Virtuoso/Maestro tier-to-model mapping.
- BYOK, commercial credential UX, usage tracking/billing.
- Any Dorian tool other than the existing `move_clip`.
- Any Desktop UI surface for Dorian (conversational or otherwise).
- Upgrading to GPT-OSS 120B except as the evaluation's own documented fallback path, if 20B's reliability bar isn't met.

## Acceptance criteria

A natural-language move-clip instruction, passed to `corytm.dorian.agent.propose_move_clip` together with a configured `GroqProvider`, results in a real Groq API call that selects `move_clip` and returns arguments validated into a genuine `MoveClipProposal` — provable by an automated unit-level harness (a fake `ModelProvider`, no network) for the orchestration/validation logic, plus a human-run live evaluation (a real `GROQ_API_KEY`) confirming GPT-OSS 20B does this reliably for representative instructions. A validated proposal, passed to the already-existing `corytm.dorian.tools.move_clip`, continues to authorize and execute exactly as EP-008 already proved — no change to that trusted path.

## Dependencies

EP-008 (done) — the trusted tool boundary and `MoveClipProposal`/`move_clip` this Epic's model call feeds into, reused unchanged.
