# FT-012 — Native Audio Runtime Materializes and Renders a Project via Tracktion

Status: active
Epic: EP-005
Milestone: MS-002

## Objective

Prove, in relative isolation (no sockets, no protobuf yet — that is FT-013's concern), that the Native Audio Runtime can turn a minimal in-memory project description into a real Tracktion `Edit` (one `AudioTrack`, one `WaveAudioClip` backed by a deterministically-generated sine-wave fixture) and render it offline to a WAV file with no real audio device, deterministically and with genuine, verifiable signal content. This is EP-005's highest-risk, most novel piece — everything else in the Epic is wiring around it.

## Acceptance criteria

A new `materialize()` function takes a plain (protobuf-free) `ProjectSpec` describing one track and one clip (id, start, duration) and a headless `tracktion::Engine`, builds a real `Edit` via `Edit::createSingleTrackEdit`, generates a deterministic sine-wave WAV fixture matching the clip's duration purely as an internal implementation detail (not part of any domain model), inserts it via `insertWaveClip`, and renders the Edit offline via `Renderer::Parameters`/`EditRenderer::render` — no `DeviceManager`, no real-time playback. The render succeeds, produces a WAV file with the expected sample count for the requested duration, and a peak amplitude consistent with genuine, non-silent sine content (not silence, not noise). Calling `materialize()` twice with identical input produces the same sample count and peak amplitude (a real, repeatable measurement, not merely "the job succeeded"), with single-threaded rendering forced (`EngineBehaviour::getNumberOfCPUsToUseForAudio() = 1`) to remove the graph's default multi-threaded scheduling as a source of run-to-run variation. Proven via a new ctest exercising `materialize()` directly against a real headless `Engine` — no mocking of Tracktion.

## Dependencies

None (does not depend on FT-011's schema — that is deliberately deferred to FT-013, where the wire format and the Tracktion-facing code must first be kept in separate translation units anyway, see TK-013's Notes).

## Notes

Deliberately excludes anything protobuf- or socket-related (FT-013's job): `materialize()`'s only public types are plain C++ structs, with zero dependency on `project.proto`'s generated code, so this Feature's code can freely use whatever C++ standard Tracktion Engine's headers need without any risk of TK-009's protobuf/C++-standard ABI bug recurring here.
