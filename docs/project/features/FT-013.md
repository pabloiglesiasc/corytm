# FT-013 — Real Entry Point and End-to-End First Sound

Status: active
Epic: EP-005
Milestone: MS-002

## Objective

Wire everything EP-005 built into one real, working path: a real Python-core application entry point constructs the minimal canonical `Project`, spawns the Native Audio Runtime, sends it across the ADR-007 transport (FT-011's schema/projection), the Native Audio Runtime materializes and renders it via Tracktion (FT-012's `materialize()`), and an event carrying the render outcome flows back — proven by one genuine, automated, cross-language end-to-end test. Also establishes the local, human-executed audible smoke test as a distinct, explicitly non-automated acceptance boundary.

## Acceptance criteria

`src/backend/core/main.py` is a real application entry point (not a proof script): it constructs an in-memory `Project` (one `AudioTrack`, one `AudioClip`), spawns the Native Audio Runtime process it needs (per ADR-002, mirroring FT-009/TK-010's established Python-spawns-native pattern), sends the project as a `MaterializeProjectCommand` over the already-proven ADR-007 transport, receives a `ProjectRenderedEvent`, and reports the rendered output path. A new native `native_runtime` executable receives that command, calls FT-012's `materialize()` unchanged, and sends the resulting event back — its own protobuf-facing code lives in a separate translation unit from anything touching Tracktion Engine headers, preserving the `cxx_std_17`/Tracktion-C++-standard boundary TK-012 already established. An automated, cross-language test (spawning the real `native_runtime` binary, not a mock) exercises the whole round trip via the same production `modules/runtime` code `main.py` itself uses — not a separately hand-rolled test client — and passes locally. Separately, a documented, human-executed local audible smoke test (running `main.py` and listening to, or otherwise directly verifying, the resulting WAV file) is recorded as a distinct acceptance step this session cannot perform itself.

## Dependencies

FT-011 (active — schema/projection); FT-012 (active — materialize/render).

## Notes

The human audible smoke test needs no additional code: the automated path already produces a real, playable WAV file via Tracktion's real render pipeline (FT-012), so "listen to the file `main.py` reports" is sufficient distinct human evidence without building a separate real-time-playback code path — which would be exactly the kind of scope this Epic's "unless concrete implementation evidence proves it's required" bar rules out for now.

**Human audible smoke test — confirmed (2026-09-01):** the user ran the real path on macOS and audibly confirmed the rendered tone (see TK-014's Notes for the full report). This closes out this Feature's one non-automatable acceptance criterion; the automated round trip was already independently verified. FT-013 stays `active`, not `done` — real Windows CI confirmation is still required (see `RSK-007`).
