# FT-014 — Corytm Engine's First Edit Operation and Wire Command

Status: done
Epic: EP-006
Milestone: MS-002

## Objective

Prove, in isolation from the Native Audio Runtime (no process/session wiring yet — mirrors FT-011's own precedent exactly), that Corytm Engine can express a real edit — moving a clip's start position — as (a) a pure Engine operation on the canonical `Project` model producing a new, fully validated `Project`, and (b) an independent `MoveClipCommand`/`ClipMovedEvent` wire message pair describing that same edit intention, projected via a pure function with no I/O.

## Acceptance criteria

`AudioTrack.with_clip_moved` and `Project.with_clip_moved` each return a new, immutable instance with the targeted clip's `start_seconds` updated, leaving the original instance and all other tracks/clips unchanged; both reject an unknown track/clip id with a `ValueError` naming which lookup failed; the new start time is rejected via `AudioClip`'s own existing validation (not a separate, duplicated check) when invalid. `project.proto` gains `MoveClipCommand` (`project_id`, `track_id`, `clip_id`, `new_start_seconds`) and `ClipMovedEvent` (`project_id`, `track_id`, `clip_id`, `start_seconds`). A pure `to_move_clip_command` function projects a move intention into a `MoveClipCommand` with no I/O. A C++ round-trip test (`project_schema`) proves both new messages serialize/deserialize correctly, mirroring the existing `MaterializeProjectCommand`/`ProjectRenderedEvent` round trip in the same file.

## Dependencies

EP-005 / FT-011 (done) — extends the same `project.proto` and Engine domain model FT-011 established, unchanged in shape.

## Notes

`ClipMovedEvent` is defined and round-tripped in isolation (C++ only) but not yet produced by any native code or consumed by any Python code — nothing in this Feature's scope needs it to be. Wiring an actual edit to a live `native_runtime` session, and having it emit a real `ClipMovedEvent`, is later Feature-level work under EP-006, refined once this Feature closes.
