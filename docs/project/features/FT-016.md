# FT-016 — Native Audio Runtime Applies a Move to a Live Edit

Status: done
Epic: EP-006
Milestone: MS-002

## Objective

Prove, in isolation from wire/socket transport (no protobuf, no `native_runtime` process wiring yet — mirrors FT-012/`materializer_proof`'s own precedent of proving the native-behavioral surface before the transport layer), that the Native Audio Runtime can keep a materialized `tracktion::Edit` alive across multiple operations and apply a clip-move mutation — the native counterpart of `MoveClipCommand` — directly to that still-live `Edit`, with the effect verified by a subsequent deterministic offline re-render of the same `Edit` object (not a freshly rebuilt one). This is EP-006's second increment: FT-014 proved the Engine/wire-schema half in isolation; this Feature proves the native half the same way, before EP-006's third increment wires them together over the real transport.

## Acceptance criteria

A new function builds a live `tracktion::Edit` from a `ProjectSpec` (mirroring `materialize()`'s existing Edit-construction behavior) and returns it still alive — not rendered-and-discarded. A second new function, given that live `Edit` plus a track id and clip id, locates the matching clip and moves its start position, leaving its duration unchanged, returning a clear failure (no crash, no partial mutation) when the track or clip id doesn't exist. A third function renders an already-built, live `Edit` to a WAV file and reports sample count/peak amplitude, computed from the `Edit`'s own current clip positions (not a stale snapshot) — so it correctly reflects a move applied after the `Edit` was first built. A new ctest builds one `Edit`, renders it once as a baseline, moves its one clip forward in time, re-renders the *same* `Edit` object, and asserts the second render's measurable output (silence before the new start, genuine signal after it) reflects the move — proving the mutation happened against the live in-memory `Edit`, not by rebuilding from scratch. The existing `materializer_proof` ctest continues to pass unchanged, proving the refactor that introduces these three functions preserves `materialize()`'s existing external behavior exactly. Confirmed by real, independently-verified cross-platform CI evidence (macOS and Windows), consistent with every prior native-behavioral surface this project has proven (RSK-005/006/007).

## Dependencies

FT-012 (done) — extends `materializer.h`/`.cpp`'s existing `ProjectSpec` → `Edit` → render pipeline, splitting it into reusable build/move/render steps rather than replacing it.
