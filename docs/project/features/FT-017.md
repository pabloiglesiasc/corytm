# FT-017 — Wire a Clip Move Into a Long-Lived Native Audio Runtime Session

Status: active
Epic: EP-006
Milestone: MS-002

## Objective

Prove EP-006's Outcome end to end over the real ADR-007 transport: a real Python entry point sends a sequence of two commands — materialize, then move — to one long-lived `native_runtime` process over one connection, and an automated cross-language test proves the move's effect is reflected in a subsequent deterministic re-render of the same live `tracktion::Edit`, not a freshly rebuilt one. This is EP-006's third and final increment: FT-014 proved the Engine/wire-schema half in isolation, FT-016 proved the native half in isolation, and this Feature wires both together over the real transport, replacing `native_runtime`'s current single-command-then-exit lifecycle with a genuinely long-lived one.

## Acceptance criteria

`native_runtime` accepts more than one command over a single connection before exiting, keeping the `tracktion::Edit` built by the first (materialize) command alive in memory for a second (move) command to mutate, rather than rebuilding it. The wire carries both `MaterializeProjectCommand` and `MoveClipCommand` distinguishably over the same connection via a minimal envelope sized to exactly these two known command types (no generalized N-command dispatch framework). A real Python entry point drives this sequence — materialize, then move — over one connection and receives a response event for each. An automated cross-language test (`pytest -m transport`) proves the move's effect: the post-move render's measurable output (sample count/peak amplitude) genuinely differs from the baseline render in the way the move implies, and a follow-up move with an unknown track/clip id fails clearly (no crash) without corrupting the still-live session — a subsequent valid move in the same session still succeeds. Every existing transport-marked test (`test_first_sound.py`, `test_entrypoint.py`) continues to pass with externally unchanged behavior, proving the envelope introduction didn't regress the already-proven single-command materialize path. Confirmed by real, independently-verified cross-platform CI evidence (macOS and Windows), consistent with every prior native-behavioral surface this project has proven (RSK-005 through RSK-008).

## Dependencies

FT-014 (done) — reuses its `MoveClipCommand`/`ClipMovedEvent` schema and `to_move_clip_command` projection unchanged.
FT-016 (done) — reuses its `buildEdit`/`moveClip`/`renderEdit` split unchanged; this Feature only changes how `native_runtime.cpp` calls them (in a loop, keeping the `Edit` alive) and how commands/events cross the wire.

## Notes

Feature/Task-level detail is refined now, at the point EP-006's third increment begins, per `docs/project/plan.md`'s Rolling-Wave Planning. This closes EP-006 once done: both this Milestone's still-unreached Outcome halves (manual Desktop editing, Dorian's semantic edit) depend on exactly this shared mechanism — Corytm Engine expressing an edit as an incremental command against a live session, not resending the whole project.

Whether introducing a `Command`/`Event` envelope counts as "changing the Python↔C++ protocol" under `CLAUDE.md` §5 was explicitly considered before starting implementation. Conclusion: it does not require fresh approval — ADR-007's own Decision text already states messages are "length-prefixed frames carrying a serialized protobuf envelope," and its Consequences section already anticipates "a small correlation-id layer built on top of the envelope, on both sides, as application-level code" for exactly this kind of multi-command interaction; EP-006's own already-approved Scope/Out-of-scope text ("not a generalized command-dispatch/oneof envelope beyond what two concrete command types require") only makes sense if a minimal two-case envelope is already implicitly in scope. This Feature realizes what ADR-007 already decided rather than opening a new architectural boundary — routine implementation inside an already-accepted shape, mirroring TK-015's identical "no new ADR" reasoning for the same ADR-007/ADR-001/ADR-008 shapes.
