# FT-021 — Production Sidecar Spawn and Shutdown

Status: active
Epic: EP-010
Milestone: MS-002

## Objective

Make the real, shipped Tauri application — not only `cargo test` — spawn the Python core sidecar on startup, complete EP-009's Desktop-channel handshake, and shut the sidecar down cleanly when the app exits. Closes the one remaining gap between FT-010/FT-020's proofs and a real running app: production `run()` has never itself spawned anything; only tests have.

## Acceptance criteria

Production `run()` registers the shell plugin and spawns `corytm serve` via a function shared with (not duplicated from) its own automated test, so the same code path is what both `cargo test` and the real app actually execute. The spawned child and its captured port/secret are held in Tauri-managed state. On `RunEvent::ExitRequested`/`Exit`, the app writes `SHUTDOWN` to the child's stdin (mirroring the existing lifecycle protocol) rather than leaving it running as an orphan. The handshake half is proven by an automated test (extending FT-020/TK-021's own proof to call the now-shared production function instead of duplicating its logic). The shutdown-on-exit half — real OS process lifecycle tied to a real GUI event loop — is confirmed by a human running `npm run tauri dev`, quitting the app, and independently checking (for example via `ps`) that the spawned Python process is no longer running, as a distinct, non-automatable acceptance boundary mirroring EP-005's own human audible smoke test precedent.

## Dependencies

FT-010 (done) — the sidecar spawn/shutdown protocol this Feature wires into production for the first time. FT-020 (done) — the Desktop-channel handshake this Feature's production code completes for real.

## Notes

Feature/Task-level detail is refined now, at the point EP-010 begins execution, per `docs/project/plan.md`'s Rolling-Wave Planning. Deliberately does not yet send any domain command over the connection once spawned (EP-010's second Feature) and does not add restart-on-crash or reconnection logic — ADR-007's Consequences name process lifecycle handling as Corytm's own code to write deliberately, not a default to assume; a bare spawn-once/shutdown-on-exit is the smallest correct increment, and anything more is deferred until a real need is demonstrated.
