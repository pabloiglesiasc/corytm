# FT-022 — Desktop Move-Clip Command and UI Trigger

Status: done
Epic: EP-010
Milestone: MS-002

## Objective

Realize EP-010's remaining scope (increments 2 and 3 of 3, sized as one Feature under the current delivery model — see EP-010's own Sizing note): a real `MoveClipCommand`/`ClipMovedEvent` pair travels over EP-009's proven Desktop channel, exercising Corytm Engine's already-proven `with_clip_moved` operation and EP-006/EP-008's live-session native mechanism against an in-memory fixture project — no longer `DesktopProofMessage` for this purpose — and a minimal real Tauri UI control lets a human trigger it and see the result in an actual running Desktop window.

## Scope / Out of scope

In scope:

- A shared Python execution path (Engine `with_clip_moved` + `materialize_then_move_clips`) usable by both Dorian's existing tool (EP-008) and the Desktop channel's new command handler, so the Desktop-originated edit goes through the same governed Engine/Runtime operations Dorian's tool uses (ADR-010 point 4), without `corytm.runtime` depending on `corytm.dorian` (`docs/technical/architecture.md`'s Dependency Direction: "Runtime never depends on Dorian").
- `serve_desktop_channel()` reads a real `MoveClipCommand` (project.proto's existing message, reused by reference per ADR-010 point 1) against a hardcoded one-track/one-clip in-memory fixture project, applies the move through that shared path, and returns a real `ClipMovedEvent`.
- Rust gains the ability to encode/decode `project.proto`'s messages (compiling it alongside `desktop.proto`) and a production `#[tauri::command]` that connects to the already-spawned sidecar's Desktop channel, sends one hardcoded `MoveClipCommand`, and returns the resulting `ClipMovedEvent` fields to the frontend.
- A minimal Desktop UI control (one button) invokes that command and displays its result.

Out of scope (mirrors EP-010's own Epic-level Out of scope): real project creation, opening, or persistence; any track/clip authoring UI beyond triggering one hardcoded move; multiple concurrent projects, windows, or repeated/reconnecting invocations beyond the one round trip the existing Desktop channel server already supports (mirrors FT-021's own "anything more is deferred until a real need is demonstrated" precedent — `serve_desktop_channel()` keeps accepting exactly one client connection for exactly one command, unchanged in shape from today); Dorian/provider wiring; any visual/UX design investment beyond function.

## Acceptance criteria

- A real, independently-verified passing Windows GitHub Actions run confirms the new cross-language round trip (Rust `project.proto` codegen, the real command/event pair, the new `#[tauri::command]`) — this project's established practice for a genuinely new cross-platform combination.

- Human confirmation, distinct from and in addition to automated evidence (mirrors EP-005/FT-021's own precedent for what automated tests can't exercise — a real GUI click in a real window): launch `npm run tauri dev`, click the UI control, and observe the real moved-clip result displayed in the running app.

**Root cause diagnosed and fixed (2026-09-02), two distinct real defects, both genuinely reproduced in isolation before any production file was touched:**

1. **Makefile target order.** `check: check-python check-frontend check-desktop check-native check-transport` ran `check-desktop`'s `cargo test` *before* `check-native` built `native_runtime` — harmless for every prior Desktop-channel test (none of them touched the Native Audio Runtime), but this Feature's new test is the first to exercise `move_clip_in_session` → `materialize_then_move_clips` from a Rust-driven `corytm serve` sidecar, which needs the compiled `native_runtime` binary to exist. On a genuinely fresh CI checkout nothing restores that compiled binary (only `src/backend/audio/build/_deps` is cached) — reproduced locally by hiding the built binary and re-running the exact test. Fixed by reordering to `check-python check-frontend check-native check-desktop check-transport`, so the dependency this Feature's own test acquired is honored.
2. **A genuine `asyncio` teardown deadlock, not platform-specific.** Since Python 3.12.1, `asyncio.Server.wait_closed()` waits for the listening socket to close *and* for every accepted connection to drop (previously it only tracked the socket — see the function's own docstring/historical note). `serve_desktop_channel()` (`runtime/desktop.py`) and `_connected_native_runtime()` (`runtime/session.py`) both `server.close(); await server.wait_closed()` in a bare `finally`, without unconditionally closing the accepted connection's `writer` first — closing it only ever happened on the success path. Any exception raised after a client connects but before that explicit close (exactly what the missing-`native_runtime` case above produces, but any failure in this window triggers it identically) leaves the writer open, so `wait_closed()` blocks forever waiting for a connection nothing will ever close — while the peer (Rust's `move_clip()`, itself with no timeout on that read) is symmetrically blocked waiting for a response that will never be written. Confirmed with a minimal, isolated repro (a bare `asyncio.start_server` + a raise-after-connect handler) before touching either production file, and independently confirmed present in *both* functions. This explains every observed feature of the hang: identical on both OSes (pure Python stdlib semantics, no OS dependency), genuinely indefinite rather than bounded by any of the surrounding `asyncio.wait_for` timeouts (it sits outside all of them), and newly exposed by this Feature specifically because it is the first Desktop-channel path where a real post-connection failure is reachable at all.

Fixed via TDD in both functions: track the accepted `writer` in a `| None` local, close it unconditionally in `finally` before waiting on the server, and set it back to `None` once the success path's own explicit close already ran (avoiding a redundant close). Two new regression tests were written first and confirmed failing (15s timeout) against the unfixed code, then passing (sub-second) after the fix: `tests/test_desktop_channel.py` (an unknown clip id fails `serve_desktop_channel` after its one client has connected) and `tests/test_move_clip_in_session.py::test_a_caller_error_mid_session_does_not_deadlock_teardown` (patches `to_materialize_command` to fail once `_connected_native_runtime` has already connected to a real `native_runtime`). As defense in depth, `src-tauri/src/lib.rs`'s own test was also hardened: a `SidecarGuard` RAII wrapper kills the spawned sidecar on any early return (`CommandChild` has no `Drop`-based cleanup of its own, confirmed against `tauri_plugin_shell`'s source, so a bare local variable leaks the process tree on a panic), and the previously-unbounded `move_clip(app.state()).await` gained the same `tokio::time::timeout` pattern already used by its sibling awaits in the same test.

Validated: the exact previously-hanging test run repeatedly (13+ times across variants, with and without `native_runtime` present) with zero hangs and zero leaked processes; a full clean `make check` (all five targets, from a state with `native_runtime` genuinely absent beforehand to prove the Makefile fix) passes end to end with zero new warnings.
