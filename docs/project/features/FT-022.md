# FT-022 — Desktop Move-Clip Command and UI Trigger

Status: active
Epic: EP-010
Milestone: MS-002

## Objective

Realize EP-010's remaining scope (increments 2 and 3 of 3, sized as one Feature under the current delivery model — see EP-010's own Sizing note): a real `MoveClipCommand`/`ClipMovedEvent` pair travels over EP-009's proven Desktop channel, exercising Corytm Engine's already-proven `with_clip_moved` operation and EP-006/EP-008's live-session native mechanism against an in-memory fixture project — no longer `DesktopProofMessage` for this purpose — and a minimal real Tauri UI control lets a human trigger it and see the result in an actual running Desktop window.

## Scope / Out of scope

In scope:

- A shared Python execution path (Engine `with_clip_moved` + `materialize_then_move_clips`) usable by both Dorian's existing tool (EP-008) and the Desktop channel's new command handler, so the Desktop-originated edit goes through the same governed Engine/Runtime operations Dorian's tool uses (ADR-010 point 4), without `corytm.runtime` depending on `corytm.dorian` (`docs/technical/architecture.md`'s Dependency Direction: "Runtime never depends on Dorian").
- `serve_desktop_channel()` reads a real `MoveClipCommand` (project.proto's existing message, reused by reference per ADR-010 point 1) against a hardcoded one-track/one-clip in-memory fixture project, applies the move through that shared path, and returns a real `ClipMovedEvent`.
- Rust gains the ability to encode/decode `project.proto`'s messages (compiling it alongside `desktop.proto`) and a production `#[tauri::command]` that connects to the already-spawned sidecar's Desktop channel, sends one hardcoded `MoveClipCommand`, and returns the resulting `ClipMovedEvent` fields to the frontend.
- A minimal Desktop UI control (one button) invokes that command and displays its result.

Out of scope (mirrors EP-010's own Epic-level Out of scope): real project creation, opening, or persistence; any track/clip authoring UI beyond triggering one hardcoded move; multiple concurrent projects, windows, or repeated/reconnecting invocations beyond the one round trip the existing Desktop channel server already supports (mirrors FT-021's own "anything more is deferred until a real need is demonstrated" precedent — `serve_desktop_channel()` keeps accepting exactly one client connection for exactly one command, unchanged in shape from today); Dorian/provider wiring; any visual/UX design investment beyond function.

## Acceptance criteria

- A real, independently-verified passing Windows GitHub Actions run confirms the new cross-language round trip (Rust `project.proto` codegen, the real command/event pair, the new `#[tauri::command]`) — this project's established practice for a genuinely new cross-platform combination.
- Automated evidence: a Rust test drives the real Desktop channel end to end (spawning the real `corytm serve` sidecar) sending a real `MoveClipCommand` and asserting the returned `ClipMovedEvent` reflects a genuine clip move (`moved = true`, the new start time, real render evidence); Python tests prove the shared Engine/Runtime execution path directly.
- Human confirmation, distinct from and in addition to automated evidence (mirrors EP-005/FT-021's own precedent for what automated tests can't exercise — a real GUI click in a real window): launch `npm run tauri dev`, click the UI control, and observe the real moved-clip result displayed in the running app.
