# FT-023 — Engine Persistence and Desktop Channel Create/Open/Save Commands

Status: active
Epic: EP-011
Milestone: MS-002

## Objective

Implement ADR-011's local JSON persistence format as a real `corytm.engine.persistence` module, and extend the Desktop channel (ADR-010) to carry real `CreateProjectCommand`/`SaveProjectCommand`/`OpenProjectCommand` commands and their result events — backed by that module and, for Open, the already-proven `MaterializeProjectCommand`/native-render path — proven entirely by automated tests. No native file dialog or new UI: this Feature's Desktop channel changes are exercised by a Python test driving the real channel directly, and by updating the one existing Rust caller (`move_clip`) to the new wire shape it now requires.

## Scope / Out of scope

In scope:

- `src/backend/core/src/corytm/engine/persistence.py` (new): `save_project(project, path)`/`load_project(path)` implementing ADR-011's versioned envelope (`{"schema_version": 1, "project": {...}}`, the `project` payload produced via `Project.model_dump(mode="json")`/`Project.model_validate`). A file that isn't valid JSON, isn't an envelope with both keys, or names an unsupported `schema_version` raises a clear, typed error before any `Project` is constructed.
- `src/schemas/project.proto`: `CreateProjectCommand`/`ProjectCreatedEvent`, `SaveProjectCommand`/`ProjectSavedEvent`, `OpenProjectCommand`/`ProjectOpenedEvent` added; `Command`/`Event`'s existing oneofs extended with all three new pairs alongside the two that already exist.
- `src/backend/core/src/corytm/runtime/desktop.py`: `serve_desktop_channel()` restructured from "accept one connection, handle exactly one hardcoded `MoveClipCommand`, close" into a per-connection loop that reads a `Command`-enveloped frame, dispatches on its oneof, writes back the corresponding `Event`, and repeats until the client closes the connection — mirroring the multi-command session `native_runtime.cpp` already implements (FT-017/TK-018) — holding one in-memory "current project" slot across that loop, seeded with the existing hardcoded fixture so the already-shipped move-clip behavior is unchanged in outcome. `CreateProjectCommand` replaces that slot with a fresh empty project; `SaveProjectCommand` persists whatever is currently in it via `persistence.save_project`; `OpenProjectCommand` loads a project via `persistence.load_project`, replaces the slot, and re-materializes it via the existing `materialize_project` to produce real render evidence for `ProjectOpenedEvent`.
- `src/frontend/desktop/src-tauri/src/lib.rs`: the existing `move_clip` `#[tauri::command]` and its test updated to send/receive `project_proto::Command`/`Event` (wrapping the same `MoveClipCommand`/`ClipMovedEvent` it already used) instead of a bare `MoveClipCommand` — the minimal, mechanical follow-on this Feature's protocol change requires so the one already-shipped Rust caller keeps working; `MoveClipResult`'s JSON shape returned to the frontend is unchanged.
- `docs/technical/architecture.md`'s "Local Project Persistence" and "Desktop↔Python Boundary"/Unresolved sections synchronized to reflect the module and commands as real, not merely decided.

Out of scope: any native OS file dialog (`@tauri-apps/plugin-dialog`); any new `#[tauri::command]` or UI control (deferred to EP-011's next Feature); project-bundle/directory formats; multiple concurrent projects/windows on the same connection beyond the sequential session this Feature adds; migration tooling or backward-compatibility guarantees for the JSON format; cloud/sync persistence; any change to `native_runtime.cpp`, `wire_codec`, or Dorian.

## Acceptance criteria

- `persistence.save_project`/`load_project` round-trip a multi-track/multi-clip `Project` through a real file unchanged; loading a file that is not valid JSON, is missing `schema_version`/`project`, or names an unsupported `schema_version` raises before constructing any `Project`.
- An automated Python test drives the real Desktop channel end to end over one connection (spawning the real `corytm serve` sidecar): authenticate, send `CreateProjectCommand` → `ProjectCreatedEvent`; send `SaveProjectCommand` naming a real temp-file path → `ProjectSavedEvent`, and the file independently round-trips via `persistence.load_project`; send `OpenProjectCommand` naming a distinct, separately-prepared fixture file → `ProjectOpenedEvent` carrying the correct track count and genuine native render evidence (non-zero sample count and peak amplitude); send the existing `MoveClipCommand` (now enveloped) → `ClipMovedEvent`, confirming the pre-existing move-clip capability is unchanged in observable behavior; then the connection closes and the session ends cleanly.
- The updated `move_clip` Rust command and its test pass, sending/receiving the enveloped message with no change to the JSON shape returned to the frontend.
- `make check-python`, `make check-native`, and `make check-transport` pass; `cargo build`/`cargo test` under `src/frontend/desktop/src-tauri` pass with zero new warnings; a full local `make check` passes end to end.
- A real, independently-verified passing Windows GitHub Actions run confirms the new cross-platform surface (see Notes) before this Feature closes `done` — this project's established practice for a genuinely new combination.

## Dependencies

EP-009 (done) — the Desktop channel this Feature extends. EP-010 (done) — the existing `MoveClipCommand` behavior this Feature's protocol change must not regress. ADR-011 (accepted) — the persistence format this Feature implements.

## Notes

Decomposed into two Tasks per the Task-creation Threshold: **TK-025** (the Engine persistence module — a self-contained decision boundary: the file envelope's exact error handling for a corrupt or version-mismatched file, with no protocol or channel change) and **TK-026** (the Desktop channel's new commands, its single-command-to-multi-command restructuring, and the Rust `move_clip` wire-format follow-on — a meaningful independently resumable package building on TK-025).

Reusing `project.proto`'s `Command`/`Event` oneof for the Desktop channel's new commands — rather than TK-023's original choice to send `MoveClipCommand` bare — is not a reversal made lightly: TK-023's own Notes reasoned explicitly that a wrapper was premature "before a second Desktop command type exists" and predicted this project's own precedent (`project.proto` itself only gained its oneof at FT-017, once a second native-facing command type existed) would apply "once ≥2 real command types exist." This Feature adds three more Desktop-facing command types at once, so that threshold is now met; the existing `move_clip` caller is updated alongside rather than left on an inconsistent bare-message wire format.

Risk `RSK-015` opened (see `docs/project/risks.md`): the Desktop channel's session loop, and Rust's first decode of a discriminated `Event` oneof response (rather than a single known message type) over that channel, are a genuinely new combination, exercised only via local `cargo test`/`make check` this session — this project's own repeated history (RSK-002 through RSK-014) is direct precedent against assuming a clean local pass predicts real Windows CI behavior for a new combination.

**Implementation complete, both Tasks' local validation passing (2026-09-02):** TK-025 and TK-026 were both implemented via TDD and validated locally — see each Task's own Notes for full detail. A full clean `make check` (all five targets) passed end to end, including a from-scratch native rebuild (`ctest` 5/5, unaffected by the additive `project.proto` messages), `make check-desktop` (release build, `.app`/`.dmg` bundling, `cargo test` — all 3 Rust tests passing with zero new warnings on both `cargo build --lib` and `cargo build --release --bin app`), `make check-python` (38 passed, pyright 0 errors, ruff clean), and `make check-transport` (10 passed, including this Feature's three new tests). `git status` confirmed only this Feature's own named files changed — no file under `src/backend/audio/` was touched.

During Review, a dead-code path was found and removed (see TK-026's Notes): `_dispatch_command`'s originally-planned `current_project is None` guards for `save_project`/`move_clip` could never actually trigger, since `_run_session` always seeds the session's project slot before dispatching — simplified to a plain `Project` parameter, not `Project | None`.

`docs/technical/architecture.md`'s "Local Project Persistence", "Desktop↔Python Boundary", and Unresolved sections were synchronized to reflect the persistence module and Desktop channel commands as real, not merely decided.

This Feature stays `active`, not `validating`: this session cannot push (`CLAUDE.md` §10). It reaches `validating` once the delivery commit is confirmed pushed, and `done` once a real, independently-verified passing Windows GitHub Actions run confirms `RSK-015`.
