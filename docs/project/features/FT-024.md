# FT-024 — Native File Dialog and Create/Open/Save UI

Status: done
Epic: EP-011
Milestone: MS-002

## Objective

Realize EP-011's last remaining increment: a real native OS file dialog (`@tauri-apps/plugin-dialog`) resolving a real filesystem path, and a minimal Desktop UI letting a human create a new project, save it to a real file, and reopen a previously-saved file — driving FT-023's already-implemented `CreateProjectCommand`/`SaveProjectCommand`/`OpenProjectCommand` over the Desktop channel (ADR-010).

## Scope / Out of scope

In scope:

- `src/frontend/desktop/src-tauri/Cargo.toml`/`package.json`: add `tauri-plugin-dialog` (Rust) and `@tauri-apps/plugin-dialog` (JS) at the same `2`/`^2` major version this project's other Tauri plugins already use; register the plugin in `run()`; add `"dialog:default"` to `capabilities/default.json`.
- `src/frontend/desktop/src-tauri/src/lib.rs`: the Desktop channel currently accepts exactly one client TCP connection for the life of the sidecar process (`serve_desktop_channel`'s single `connection_future`, unchanged since ADR-010/FT-020) — `move_clip` has only ever gotten away with opening its own fresh `TcpStream` per call because it is invoked at most once per session today. Adding three more command types invoked by independent, arbitrarily-ordered button clicks requires that connection to genuinely be held and reused, not reopened. This Feature opens the Desktop channel connection once (after `spawn_desktop_sidecar`'s handshake completes) and stores the authenticated reader/writer pair in `Manager`-based state behind an async mutex; a shared `send_command` helper (send one `Command`, read back one `Event`) replaces `move_clip`'s own one-shot connect/authenticate/send/receive block; `create_project`, `save_project(file_path)`, and `open_project(file_path)` are added as `#[tauri::command]`s using that same helper; `move_clip` is migrated onto it unchanged in observable behavior.
- `src/frontend/desktop/src/App.tsx`: New Project / Save / Open controls. Save and Open call `@tauri-apps/plugin-dialog`'s `save()`/`open()` directly from the frontend to resolve a real path (no Rust-side dialog code needed — the plugin's JS API is itself permission-gated), then invoke the corresponding Tauri command with that path.
- `docs/technical/architecture.md`'s Desktop↔Python Boundary/Unresolved sections synchronized to reflect the channel now genuinely carrying a sequence of independent, human-triggered commands over one held connection, and the frontend design-system direction (`docs/product/design.md`) still deliberately not materialized here — this Feature stays function-only, per EP-011's own Out-of-scope.

Out of scope (per EP-011's own Out-of-scope, restated): any track/clip authoring UI beyond the existing move-clip fixture trigger; project-bundle/directory formats; multiple concurrent projects or windows; autosave/crash-recovery/undo persistence; migration/backward-compatibility tooling; cloud/sync persistence; Dorian/provider wiring; any visual/UX design-system investment beyond function (no typeface/color/component-library decisions — mirrors FT-022's own precedent of a plain functional control).

## Acceptance criteria

- `cargo test` (mocked-app, known paths — no real OS dialog invoked) proves: `create_project` returns a real `project_id`; `save_project(path)` against a real temp path returns `ProjectSavedEvent` fields, and the file independently round-trips via `corytm.engine.persistence.load_project`; `open_project(path)` against a distinct, separately-prepared fixture file returns the correct `track_count` and genuine non-zero `rendered_sample_count`/`peak_amplitude`; `move_clip` still passes against the same shared connection, unchanged in observable JSON shape; all four commands share one Desktop-channel connection within a single test, proving the persistent-connection refactor genuinely lets them coexist (a regression a one-shot-per-command design would fail immediately).
- `cargo build --lib` and `cargo build --release --bin app` are clean with zero new warnings; `make check-desktop` and a full local `make check` pass end to end.
- `tsc -b`/`vite build`/`oxlint`/`vitest` pass on the frontend changes.
- A human, running the real `npm run tauri dev` app, creates a new project, saves it through a real native save dialog to a real file, quits and relaunches, and opens that file through a real native open dialog — observing the reopened project's genuine re-render (sample count, peak amplitude) — since a real OS-level file-picker dialog cannot be exercised headlessly; this is a distinct confirmation step, in addition to (not instead of) the automated evidence above.
- A real, independently-verified passing Windows GitHub Actions run confirms the new cross-platform surface (see Notes/`RSK-016`) before this Feature closes `done`.

**Root cause diagnosed (2026-09-02), not assumed — traced end to end through real reproduction:** the saved file held a genuinely empty project (`create_project` produces `Project(id=..., tracks=())`, and this is the first time anywhere in this project that a zero-track project has been sent through the real materialize/render path — every prior Feature always used a hardcoded one-track/one-clip fixture). `native_runtime.cpp`'s `materialize()` correctly detects an empty project (`project.tracks.empty()`) and still sends a valid `ProjectRenderedEvent` back (zero sample count/peak amplitude) — but the *process's own exit code* also reflects that render as unsuccessful (`sessionSucceeded = false` → exit code 1), a convention established back at EP-005/EP-006 to signal render outcome to whatever spawns the process. `corytm.runtime.session._connected_native_runtime` (used by `materialize_project`, which `_dispatch_command`'s `open_project` handler calls) treats *any* non-zero exit code as a hard failure and raises `RuntimeError("native_runtime exited with code 1")` — even though the `Event` carrying the real, accurate outcome had already been successfully read moments earlier. That `RuntimeError` is raised as the `async with` block unwinds, *before* `materialize_project`'s own `return event.project_rendered` line runs, so it always wins over the already-successful read. Nothing in `_run_session`/`serve_desktop_channel` catches it, so it propagates out and crashes the whole `corytm serve` process before any `Event` frame is written back for that command — exactly producing the "early eof" the Rust side (and, independently, a Python client) observed. Confirmed real, not theoretical: reproduced directly via `asyncio.run(materialize_project(Project(id=..., tracks=()), ...))`, which raised the identical `RuntimeError: native_runtime exited with code 1`; and reproduced end to end via the exact New→Save→quit→relaunch→Open path at the Python level (two independent `serve_desktop_channel()` sessions, mirroring a real quit/relaunch), which raised the client-side mirror of the same symptom, `asyncio.exceptions.IncompleteReadError: 0 bytes read on a total of 8 expected bytes`.

Every other reachable failure mode in `native_runtime.cpp` (an unrecognized command, a command that never arrives) already surfaces at the caller's own event/authentication read, independent of this exit-code check — so for every currently-reachable case where the caller has already successfully read every `Event` it expects, the exit code carries no information the `Event` stream didn't already deliver, and treating it as an unconditional hard error is simply wrong. Fixed accordingly in `corytm.runtime.session._connected_native_runtime` (the shared helper both `materialize_project` and `materialize_then_move_clips` use) — still awaits and reaps the process (so it doesn't linger, and a genuine hang after the connection closes still surfaces as `TimeoutError`), but no longer raises based on the exit code itself; both callers' docstrings corrected to match (the `RuntimeError: ... or exited with a non-zero return code` clause removed — now only "failed to authenticate"). This is a fix to `corytm.runtime.session` (CTO/AI & Sound ownership, outside TK-027/TK-028's own declared Rust/frontend scope) — touched directly, as the smallest necessary change, per `CLAUDE.md` §7, since it is the genuine root cause of a real FT-024 product-path failure (Open), not an unrelated opportunistic fix.

Fixed via TDD: `tests/test_first_sound.py::test_materialize_project_with_no_tracks_returns_a_zero_render_event` (confirmed failing first with the exact `RuntimeError: native_runtime exited with code 1`) isolates the root cause directly against `materialize_project`; `tests/test_desktop_channel_session.py::test_open_project_after_relaunch_with_no_tracks_succeeds` (confirmed failing first with the exact `IncompleteReadError`) reproduces the full real user path — create_project → save_project in one `serve_desktop_channel()` session, then a **second, independent** `serve_desktop_channel()` session opening that same file — as closely as this project's existing in-process test harness allows to a genuine quit-and-relaunch.
