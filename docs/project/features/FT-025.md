# FT-025 — Add Audio Track and Add Audio Clip Commands and UI

Status: active
Epic: EP-012
Milestone: MS-002

## Objective

Implement EP-012's full scope: real `with_track_added`/`with_clip_appended` Engine operations, `AddAudioTrackCommand`/`AddAudioClipCommand` (and their events) over the Desktop channel's existing persistent connection, the matching Rust commands, and a minimal Desktop UI that materializes `docs/product/design.md`'s design-system direction for the first time against real UI work.

## Scope / Out of scope

In scope — see EP-012 for the full rationale; as implemented here:

- `src/backend/core/src/corytm/engine/track.py`: `AudioTrack.with_clip_appended(*, clip_id, duration_seconds)` — appends a new clip immediately after the track's existing clips (start position computed, not caller-supplied), mirroring `with_clip_moved`'s "rebuild through full construction" validation pattern.
- `src/backend/core/src/corytm/engine/project.py`: `Project.with_track_added(*, track_id)` and `Project.with_clip_appended(*, track_id, clip_id, duration_seconds)`, mirroring `with_clip_moved`'s track-lookup/delegate/raise-on-unknown-id pattern.
- `src/schemas/project.proto`: `AddAudioTrackCommand`/`AudioTrackAddedEvent`, `AddAudioClipCommand`/`AudioClipAddedEvent` added to the existing `Command`/`Event` oneofs (fields 6/7). Track/clip ids are always server-generated (`uuid4`), matching `CreateProjectCommand`'s existing convention — neither command carries a `project_id` input field, since the session already scopes to one current project and neither Rust nor the frontend has a real value to put there (unlike `MoveClipCommand`'s existing, already-vestigial `project_id`, not replicated here). Both events echo `project_id` for display/debugging, matching `ProjectCreatedEvent`/`ProjectSavedEvent`/`ProjectOpenedEvent`.
- `src/backend/core/src/corytm/runtime/session.py`: `add_clip_in_session(project, *, track_id, clip_id, duration_seconds, output_directory)` — mirrors `move_clip_in_session`'s "mutate, then materialize" shape, returning the new `Project`, the appended `AudioClip` (to read back its computed `start_seconds`), and the `ProjectRenderedEvent`.
- `src/backend/core/src/corytm/runtime/desktop.py`: `_dispatch_command` gains `add_track` (pure mutation, no render — mirrors `create_project`) and `add_clip` (mutation + full re-materialize via `add_clip_in_session` — mirrors `move_clip`'s render-and-report shape) branches.
- `src/frontend/desktop/src-tauri/src/lib.rs`: `add_track`/`add_clip` `#[tauri::command]`s on the existing held `DesktopConnection`, following `create_project`/`save_project`'s parameterized-command shape; registered in `generate_handler!`.
- `src/frontend/desktop/src/`: a minimal but real design-system materialization — semantic CSS custom-property tokens (color, spacing, radius, typography) with both light and dark values (`prefers-color-scheme`), a first small component catalog (`Button`, a labeled number input), and "Add Track"/"Add Clip" controls wired to the new commands, with "Add Track" disabled once the current project already has one (the single-track materialization limit EP-012 names) and "Add Clip" disabled until a track exists.
- `docs/technical/architecture.md`: "Engine Services and Incremental Updates" and Unresolved sections synchronized to reflect track/clip authoring as real (narrowly) rather than illustrative-only/open.

Out of scope: everything EP-012 names as out of scope (multi-track materialization, any audio-source field, arbitrary placement/deletion, persistence-format changes, Dorian/provider wiring).

## Acceptance criteria

- `AudioTrack.with_clip_appended`/`Project.with_track_added`/`Project.with_clip_appended` are covered by colocated tests proving: correct append placement (including after existing clips), immutability (original unchanged), and `ValueError` on an unknown `track_id`.
- An automated Python test drives the real Desktop channel end to end (spawning the real `corytm serve` sidecar): `CreateProjectCommand` → `AddAudioTrackCommand` → `AddAudioClipCommand` (twice, proving the second clip is appended after the first, not overlapping) → genuine non-zero render evidence (sample count, peak amplitude) from the Native Audio Runtime.
- The new `add_track`/`add_clip` Rust commands and a `cargo test` driving `create_project` → `add_track` → `add_clip` over one held connection pass, matching the existing multi-command-sequence test's shape.
- The Desktop UI's "Add Track" control is disabled once the current project already has a track; "Add Clip" is disabled until a track exists.
- The `ui-ux-review` skill is applied to the new UI against `docs/product/design.md`, with findings addressed before Close.
- `make check` (all five targets, including `make check-desktop`'s release build) passes end to end with zero new warnings.
- A human confirms the real running UI (`npm run tauri dev`): New Project → Add Track → Add Clip (more than once) → genuine render evidence shown, in both light and dark OS theme settings.
- A real, independently-verified passing Windows GitHub Actions run, once pushed — this project's established practice for any Feature touching Rust/native-adjacent code (see Notes on why no new Risk beyond that standing practice is warranted).

**Third real product-path bug found on continued human validation (2026-09-02): a Desktop-channel lifecycle defect, not a transient networking error.** After leaving the real app open for a while, every backend-dependent control except Open/Save began failing with `failed to send command: Broken pipe (os error 32)`. Root-caused, not assumed, and not papered over with a blind reconnect-on-error: `corytm.runtime.desktop._run_session`'s command-read wrapped `read_frame` in a 30-second `asyncio.wait_for`, whose `TimeoutError` was never caught (only `IncompleteReadError` was) and propagated uncaught through `serve_desktop_channel()`/`main()`, silently killing the entire `corytm serve` process on any real idle gap longer than 30 seconds — while Rust's held connection kept believing it was still live. This directly contradicted `docs/technical/architecture.md`'s own already-stated intent that the channel is genuinely persistent for the app's whole session. See TK-030's own Notes for the full diagnosis (including why Open/Save appearing unaffected could not be tied to any real structural difference — most plausibly a test-sequencing artifact, not a distinct code path) and fix trace.

**Decided and documented the connection contract, per explicit instruction:** genuinely persistent for the app's session; reconnection is explicitly not supported (`docs/technical/architecture.md`'s Desktop↔Python Boundary section). Fixed via TDD (a monkeypatched-timeout reproduction confirmed failing first, then the timeout wrapper removed entirely — the existing clean-disconnect path already handles the one case that should end a session); a focused stress/repetition test (10 real command round trips with idle gaps over one connection) added per instruction. Rust-side defense in depth: `send_command` now clears the stored connection on any I/O failure so `desktop_channel_ready` stays honest — proven by a new test using a throwaway TCP peer, confirmed failing first against the pre-fix code. The frontend's readiness poll now continues indefinitely (at a slower steady interval once ready) rather than stopping at the first `true`, so a later connection loss is detected and every control is disabled again — never by reconnecting, only by observing the backend's own state honestly.
