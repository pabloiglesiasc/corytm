# FT-027 — Real-Time Device Playback Proof (Native)

Status: active
Epic: EP-014
Milestone: MS-003

## Objective

Prove, in relative isolation from the Desktop-channel command protocol, that the Native Audio Runtime can open a real audio output device via Tracktion Engine's `DeviceManager` and drive an already-materialized `Edit`'s real-time transport (play, stop) through it — with a readable live play/stop state and position — for the first time anywhere in this codebase. Mirrors FT-012/FT-016's own precedent of proving a genuinely new native mechanism against a dedicated ctest proof before any wider wiring into `native_runtime`'s command protocol.

## Scope / Out of scope

In scope: `buildEdit` (`materializer.h`/`.cpp`) gains an optional `Edit::EditRole` parameter, defaulting to its current `forRendering` value so every existing caller is unaffected — required because Tracktion Engine's own `EditRole` enum documents `forRendering` as `playDisabled` ("Creates an Edit for rendering, not output device playback"), confirmed directly against the vendored `tracktion_Edit.h`; a caller wanting real-time playback must pass `Edit::forEditing` instead. New production functions in `materializer.h`/`.cpp`: `openRealtimeOutputDevice(Engine&)` (calls `DeviceManager::initialise` explicitly and reports whether a real device is now open), `startPlayback(Edit&)`/`stopPlayback(Edit&)` (`TransportControl::play`/`stop`), `isPlaying(const Edit&)`, `getPlaybackPositionSeconds(const Edit&)`. A new `tests/playback_proof.cpp` ctest exercising all of the above against a fixture Edit, defensively skipping/soft-passing when no real device is available rather than hard-failing (confirmed research finding: Windows GitHub Actions runners commonly expose no usable audio device; macOS runners are real Apple hardware and are expected to expose one, silent to nobody). A human-only local audible confirmation, as this Feature's acceptance boundary automation cannot substitute for, mirroring EP-005's own precedent.

Out of scope: wiring this mechanism into `native_runtime.cpp`'s real command/event protocol, the Desktop channel, Rust, or any UI (FT-028, this Epic's next Feature); everything EP-014's own Out-of-scope list already states (seek, loop, pause-as-distinct-from-stop, metronome, device configuration/hot-plug, metering, multi-track materialization, workspace redesign).

## Acceptance criteria

A new ctest builds a playback-enabled (`Edit::forEditing`) fixture `Edit`, opens a real audio output device through `DeviceManager`, starts real-time playback, and confirms — while a device is genuinely open — that the transport's own state (`isPlaying()`, an advancing `getPosition()`) reflects real-time progress over a short bounded window, then stops it and confirms `isPlaying()` becomes false; the test passes locally and defensibly skips/soft-passes (not hard-fails) when no real device is available rather than asserting on a codepath that never runs. Separately, a human runs this locally on a real machine and confirms genuine audible output through actual speakers/headphones — the one thing this proof's own automated assertions cannot themselves establish, exactly mirroring EP-005's WAV-file audible smoke test but for a live device instead of a rendered file.

## Dependencies

EP-005 (done) — reuses `buildEdit`'s existing fixture-generation logic (`materializer.cpp`) unchanged aside from the new optional role parameter.

## Notes

Implemented directly against this Feature's own record, without a Task decomposition: this is one coherent native mechanism (mirroring FT-016/TK-017's own shape), not a subproblem the Task-creation Threshold (`docs/project/format.md`) judges worth separating out on its own.

Every API used here was confirmed directly against the real vendored Tracktion Engine/JUCE source (`src/backend/audio/build/_deps/tracktion_engine-src/`, `juce-src/`) before writing any code, not assumed from general knowledge — including one real correction to an initial research pass: `DeviceManager::initialise(int, int)` returns `void`, not a `juce::String` error — success is instead read from `DeviceManager::deviceManager.getCurrentAudioDevice() != nullptr` (`deviceManager` is `DeviceManager`'s own public `TracktionEngineAudioDeviceManager` member, itself a `juce::AudioDeviceManager` subclass) after calling `initialise`.

This is a materially new, higher-risk native surface than any this project has proven before — real audio-device I/O, not offline rendering or transport-agnostic command handling. `RSK-018` was opened alongside this Feature's implementation.

**Implemented (2026-09-03).** A real, non-obvious bug was found and fixed via direct empirical diagnosis (temporary `std::cerr`/`juce::ChangeListener` instrumentation, not guessed — full mechanism in `RSK-018`): `DeviceManager::initialise()` triggers its wave-device-list rebuild and its MIDI device scan asynchronously and independently; starting playback before either settles races it and the transport gets silently stopped out from under the caller. `openRealtimeOutputDevice` now blocks (bounded, 5s timeout) until both settle before returning, closing the race. Locally verified on macOS: `playback_proof` passed 21/21 consecutive runs after the fix; a full clean `make check` (all five targets) passes end to end with zero new warnings; `git status` confirms only this Feature's own declared files changed.

Two items remain genuinely open before this Feature can close, deliberately distinct (see `RSK-018`): a real, independently-verified passing Windows GitHub Actions run for this new native surface, and the human-only local audible confirmation this Feature's own Acceptance criteria calls for — this session cannot supply either (`CLAUDE.md` §10 for the push; a human's own ears for the audible check). FT-027 stays `active`, not `validating`, since its delivery commit is not yet confirmed pushed.
