# FT-028 — Canonical Testing Policy, Python Test Layout Migration, and Local Validation Tooling

Status: done
Epic: EP-015

## Objective

Implement the user-approved testing-architecture review's decisions end to end: write the canonical tiered testing/validation policy and cross-reference it from `CLAUDE.md`; migrate Python's test layout to a structural production/test separation (subsystem-owned tests under `tests/{engine,dorian,runtime}/`, genuinely cross-boundary tests under `tests/integration/`); wire local `sccache`/CMake compiler-launcher reuse and a lockfile-stamp-gated frontend install; exclude `live_llm` from normal `check-python`; and author a narrow testing-review skill that operationalizes the policy without duplicating it.

## Scope / Out of scope

Mirrors EP-015's own scope, applied at Feature level (see `docs/project/epics/EP-015.md`).

## Acceptance criteria

- `docs/technical/testing.md` exists and states: the four-tier validation model (inner loop / affected-subsystem / Feature-close / CI-external-manual); the per-subsystem invalidation input-set table, including the cross-subsystem edges (`check-desktop`/`check-transport` are invalidated by `check-native`'s own inputs, not only their own); the clean-build trigger list. `CLAUDE.md` §7's Validate bullet carries a one-sentence pointer to it — no other `CLAUDE.md` wording changes.
- `check-python`'s default pytest `-m` filter excludes `live_llm` in addition to `transport`; `test_agent_live_eval.py`'s tests remain reachable only via an explicit opt-in invocation (`pytest -m live_llm`); the existing `skipif(GROQ_API_KEY)` guard is unchanged.
- `make check-native` and `make check-desktop`, run locally, route through `sccache` using the same `RUSTC_WRAPPER`/CMake-compiler-launcher mechanism `.github/workflows/check.yml` already proves works — verified via `sccache --show-stats` showing real, non-zero activity across a rebuild that has genuine compilation to do.
- `make check-frontend`'s install step performs no install when the currently-installed dependency state is already known to correspond to `package-lock.json`; runs `npm ci` when the lockfile changed, the install is absent, or that correspondence cannot be established; achieved via a Make/lockfile-stamp dependency mechanism, not bespoke cache logic. `.github/workflows/check.yml` is unchanged — CI keeps running `npm ci` unconditionally.
- Every test file currently colocated under `src/corytm/**` is inspected individually (not classified mechanically by filename) and relocated to `src/backend/core/tests/{engine,dorian,runtime}/` when its guarantee belongs exclusively to that subsystem, or to `src/backend/core/tests/integration/` when it crosses a subsystem/application/process boundary; relative imports are rewritten to absolute `corytm.`-qualified imports where the move requires it; the existing files already under `src/backend/core/tests/` are relocated into `src/backend/core/tests/integration/` unchanged in content. No test is dropped, weakened, skipped, or behaviorally altered. No Hatchling packaging exclude is added solely to compensate for the old layout.
- `pyproject.toml`'s `testpaths` and Ruff per-file-ignore globs are updated to match the new layout (no stale glob referencing the old `src/corytm/**/test_*.py` location); `pyright`'s existing `include` needs no change since it already covers `tests` recursively.
- After the migration, `pytest -m "not transport"`, `pytest -m transport`, `pyright`, `ruff check`, and `ruff format --check` all pass with the same pass/skip/deselect counts as immediately before the migration (module identity aside).
- `.claude/skills/testing-review/SKILL.md` exists, is narrow, does not restate `testing.md`'s content (points to it instead), and instructs Claude on: test placement; selecting appropriate fidelity; TDD/targeted inner-loop execution; recognizing complementary versus duplicate guarantees; updating invalidation inputs when a new dependency edge is introduced; deciding which subsystem validations have been invalidated; avoiding ritual duplicate execution; preserving real IPC/process/native/device tests where their fidelity is material; recognizing `live_llm` and human/manual evidence boundaries; Feature-close validation selection.
- A full local `make check` passes end to end after every change in this Feature, with the same pass/fail/skip counts and zero new warnings relative to the pre-change baseline measured during the review.

### Validate (Feature-close)

Per `docs/technical/testing.md`'s own Tier 3 rule and the `testing-review` skill (invoked directly for this decision): this Feature modified `Makefile` itself, which is one of the three named triggers for running the full `make check` rather than a narrower per-subsystem subset — not a default reflex, the policy's own explicit exception. A full local `make check` was run once, clean, as the Feature's closing evidence: `check-python` 57 passed/16 deselected, `pyright` 0 errors, `ruff check`/`ruff format --check` clean (40 files); `check-frontend` 1/1 vitest passed, `oxlint` clean; `check-native` 6/6 ctest passed; `check-desktop` 7/7 `cargo test` passed, release build + DMG bundled cleanly; `check-transport` 14 passed/59 deselected. Every count matches the pre-Feature baseline exactly; the one CMake warning in the log (`protobuf-src/CMakeLists.txt`'s `CMP0141` policy notice) is the same pre-existing, already-catalogued vendored warning named in `.claude/memory/native-build-third-party-warnings.md`, confirmed unrelated by inspection, not newly introduced. Total wall time: 2m10s.

One detail deliberately not treated as requiring a fresh cross-platform CI run before Close, reasoned explicitly rather than assumed: the Makefile's new `SCCACHE_INSTALLED := $(shell command -v sccache 2>/dev/null)` / `ifneq`/`?=` logic is unconfirmed on real Windows CI. Unlike this project's own native/Rust-behavioral risk history (`RSK-002` through `RSK-018`, all real API/ABI/IPC surfaces), this is a Make-language-semantics question with a bounded failure mode: `.github/workflows/check.yml` was not touched, and CI already sets `CMAKE_CONFIGURE_FLAGS` (explicitly, even to `''` on Windows) and `RUSTC_WRAPPER: sccache` as real environment variables before `make check` runs — GNU Make's `?=` never overrides an already-set environment variable, so CI's own behavior is unchanged regardless of how `SCCACHE_INSTALLED` evaluates there. The next ordinary CI run (for whichever Feature follows) exercises this Makefile path naturally; no dedicated confirmation run was judged necessary to open for a locally-bounded, non-native default-variable computation.
