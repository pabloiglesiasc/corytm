# FT-030 — Wire Real-Time Playback into the Command Protocol and Desktop UI

Status: active
Epic: EP-014
Milestone: MS-003

## Objective

Complete EP-014's Outcome: extend `native_runtime`'s command/event protocol with Play/Stop/live-position commands built on FT-027's already-proven native playback mechanism, wire them through the Desktop channel and a persistent Rust connection, and give the real Desktop app a Play/Stop control with a live playhead — so a human can launch the real app, click Play, hear real-time audio-device output, watch the playhead move, and click Stop to halt it.

## Scope / Out of scope

In scope:

- `src/schemas/project.proto`: `PlayCommand` (carries a full `Project`, mirroring `MaterializeProjectCommand`'s shape, since playback needs its own dedicated `Edit::forEditing` build rather than reusing any `forRendering` one), `StopCommand`, `GetPlaybackPositionCommand`, and their `PlaybackStartedEvent`/`PlaybackStoppedEvent`/`PlaybackPositionEvent` counterparts, added to the existing `Command`/`Event` oneofs (fields 8-10).
- `src/backend/audio/wire_codec.{h,cpp}`: decode the three new commands into new `DecodedCommand` variant alternatives; encode the three new events.
- `src/backend/audio/native_runtime.cpp`: handle Play (build a `forEditing` Edit via `buildEdit`, open the real device via `openRealtimeOutputDevice`, start playback via `startPlayback`), Stop (`stopPlayback`, reporting final position), and GetPlaybackPosition (`isPlaying`/`getPlaybackPositionSeconds`) — all reusing FT-027's already-proven `materializer` functions unchanged. A new ctest proves position tracking and transport state remain correct under `native_runtime`'s actual threading model: blocked on a condition variable between commands, with zero JUCE message-loop pumping — genuinely different from `playback_proof`'s own test shape, which pumps the message loop while waiting.
- A new Python `PlaybackSession` (`corytm/runtime/session.py`) that spawns and holds one dedicated `native_runtime` process open across Play → (any number of position polls) → Stop — a materially different lifecycle than every existing Desktop-channel command, which spawns a fresh process per single command/response. The "spawn and authenticate" logic shared with the existing one-shot `_connected_native_runtime` is factored into a common helper rather than duplicated.
- `corytm/runtime/desktop.py`: `_run_session` holds an optional `PlaybackSession` across loop iterations, alongside `current_project`; `_dispatch_command` gains `play`/`stop`/`get_playback_position` branches, and kills any live playback session if the Desktop-channel connection itself closes while playback is active.
- `src/frontend/desktop/src-tauri/src/lib.rs`: `play`/`stop`/`get_playback_position` `#[tauri::command]`s on the existing held `DesktopConnection`, registered in `generate_handler!` and `capabilities/default.json`.
- `src/frontend/desktop/src/`: a Play/Stop control and a live playhead display, polling `get_playback_position` on a short interval while playing, reusing the existing card-layout/design-token scaffold FT-025 established.

Out of scope (unchanged from EP-014's own Out-of-scope list): seek/arbitrary positioning, loop-region playback, pause as distinct from stop, metronome/count-in, sample-rate/buffer/device configuration, hot-plug/recovery, master metering/clipping indication, multi-track materialization, and any workspace/information-architecture redesign.

## Acceptance criteria

- A new native ctest proves that, driven exactly as `native_runtime.cpp`'s own command loop drives it (no JUCE message-loop pumping between the start-playback and read-position calls), `isPlaying()`/`getPlaybackPositionSeconds()` still reflect genuine real-time progress, and stop still halts it correctly.
- An automated Python integration test drives the real Desktop channel end to end: `CreateProjectCommand` → `AddAudioTrackCommand` → `AddAudioClipCommand` → `PlayCommand` (`device_opened` observed) → `GetPlaybackPositionCommand` (position genuinely advances across two polls, when a real device is available; the test tolerates and explicitly reports the no-device case rather than failing on it, mirroring `playback_proof`'s own soft-skip precedent) → `StopCommand` (`isPlaying` false afterward).
- The new `play`/`stop`/`get_playback_position` Rust commands are reachable through the real IPC/ACL pipeline (mirroring `real_app_commands_are_permitted_and_readiness_is_observable`'s existing pattern), and a `cargo test` drives Play → GetPosition → Stop over one held connection.
- The Desktop UI's Play control is disabled until a project with at least one clip exists and enabled/disabled appropriately once playing; Stop is only enabled while playing; the playhead visibly advances while playing and halts on Stop.
- The `ui-ux-review` skill is applied to the new UI against `docs/product/design.md`, with findings addressed before Close.
- `make check` (all five targets, including `make check-desktop`'s release build) passes end to end with zero new warnings.
- A human confirms the real running UI (`npm run tauri dev`): create/open a project with a clip, click Play, hear real-time audio-device output, see the playhead move, click Stop to halt it — mirroring EP-014's own Acceptance criteria and FT-027's audible-confirmation precedent.
- A real, independently-verified passing Windows GitHub Actions run, once pushed — this project's established practice for any Feature touching Rust/native-adjacent code.
- Added after the first human-validation round found these unmet (TK-043/TK-044): a warm (device already open) Play completes in well under 500ms, ideally under 250ms at steady state; playback stops on its own once the project's effective content ends, with no explicit Stop and no frontend timer involved; Stop followed by Play again resumes from the stopped position rather than restarting at 0.

## Notes

Decomposed into four Tasks, mirroring EP-004's own precedent for a cross-boundary vertical slice (native → Python → Rust → UI), each a genuinely separable, independently-resumable subproblem: TK-039 (native protocol/mechanism, Sound Backend), TK-040 (Python session/Desktop-channel wiring, Backend), TK-041 (Rust Desktop-channel commands/ACL, Frontend), TK-042 (Desktop UI, Frontend). Executed in that order, each depending on the previous. Task records are created just-in-time, immediately before each begins, per `CLAUDE.md` §7.

This Feature's central new architectural fact, not present anywhere in the codebase before it: unlike every prior Desktop-channel command (each spawns a fresh `native_runtime` process for exactly one command/response), Play must keep one `native_runtime` process alive across multiple, separately-arriving Desktop-channel commands (Play, then any number of position polls, then Stop) — because the live `Edit` and the open audio device it drives must persist across the calls, not merely because bounded rework might otherwise follow later. This is deliberately still narrower than fixing `RSK-017`'s own separately-noted "one native process per command, even in a persistent session" performance observation for every other command — those are unrelated concerns.

### Review

Applied the `code-review` skill (medium effort) against the complete integrated diff (TK-039 through TK-042 together). It surfaced one real, confirmed defect (detailed in TK-040's Notes): `_dispatch_command`'s `play` branch treated any already-held `PlaybackSession` as still genuinely playing, so a session whose device failed to open on a previous Play — `is_playing` reading `False` forever — wedged Play permanently for the rest of the connection, with no recovery short of a full reconnect. Fixed via TDD (a new deterministic, hardware-independent regression test confirmed failing before the fix and passing after); see TK-040's Notes for the full mechanism. The reviewer's second proposed failure mode (Tracktion's transport auto-stopping once an Edit's content ends) was checked empirically and found not to hold — the transport keeps running past the end of content, producing silence, until an explicit Stop — so the fix targets the real, confirmed mechanism rather than the unconfirmed one; `docs/technical/architecture.md`'s Unresolved entry and a code comment that had assumed the unconfirmed behavior were both corrected in place.

A second, independent defect was found directly (not by the review agent) while implementing TK-039: `waitForNextCommand`'s poll-and-pump loop checked `isPlaying()` once at entry rather than on every iteration, which would have kept polling indefinitely against an Edit no longer playing rather than falling back to the plain long wait. Fixed by re-checking on every iteration (see TK-039's Notes).

No dead code, suppression directives, or weakened tests found. No scope creep: `RSK-017`'s separately-noted "one native process per command" performance observation was deliberately not addressed here — a different, unrelated concern this Feature's own Notes explicitly declines to fold in. `git diff --stat` confirms only this Feature's own declared files changed.

## Second human-validation round (2026-09-03) — three material transport defects found and fixed

Human validation of the initial implementation above confirmed the basic vertical path genuinely works (Play produces real audible output, the playhead advances coherently, Stop halts it, the full Desktop → Rust → Python → native → device path is real) but found FT-030 did not yet meet product acceptance: (1) click-to-audible/playhead latency of ~3-4s, far outside the required <500ms Alpha ceiling; (2) playback never stopped on its own at the end of a project's content; (3) Stop followed by Play again incorrectly restarted from position 0 instead of resuming from the stopped position. Per the user's explicit instruction, these were diagnosed empirically (not guessed) and fixed within this same Feature rather than deferred, decomposed into two further Tasks: **TK-043** (Play latency + stop/resume position — the same root cause, fixed together: see TK-043's own Notes for the full empirical diagnosis, tracing the latency to a real several-second macOS CoreMIDI cold-start cost paid on every Play because each one spawned a brand-new process, and the resume bug to a brand-new `Edit` starting at 0 by construction rather than any Tracktion-side position reset) and **TK-044** (automatic stop at effective playback end, with the authoritative-layer decision recorded explicitly in TK-044's own Notes: the Native Audio Runtime, reusing `renderEdit`'s own already-proven "where does the content end" computation, since this is a mechanical fact about the materialized Edit, not a musical/arrangement interpretation requiring Corytm Engine's own judgment).

An independent `code-review` pass against this second round's diff, plus this session's own full-suite validation, caught one further regression before it could reach Close: the first version of TK-043's eager-warm-up design blocked a closing connection on the full ~5s warm-up before it could clean up, breaking two existing tests with short timeouts — fixed by splitting the playback session's fast, always-awaited process spawn from its slow, independently-cancellable device-warm-up (see TK-043's own Notes).

`docs/technical/architecture.md`'s "Real-time audio-device playback" Unresolved entry and `RSK-019` were both updated to describe the pre-warmed/persistent-session/auto-stop mechanisms this round added (see Sync below); TK-039/TK-040's own Notes are left as the accurate historical record of the first round's implementation and validation, not rewritten.
