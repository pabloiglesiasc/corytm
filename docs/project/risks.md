# Risk Register

A risk is something uncertain that may happen. A blocker is something already preventing or affecting work right now — blockers live on the affected work item's own Status/Blocker field, never here.

## Format

`RSK-001` | Description | Likelihood (low/med/high) | Impact (low/med/high) | Status (open/monitoring/materialized/closed) | Mitigation | Related work

`RSK-002` | Adding a Rust/Tauri build toolchain (ADR-006) and Protobuf codegen integrated into both the CMake native build and the uv-managed Python project (ADR-007) — two new cross-platform build-toolchain surfaces at once — may expose macOS/Windows-specific integration issues similar in kind to RSK-001's, affecting EP-004 timing | med | med | materialized | Rust/Tauri half remains fully proven on both platforms (TK-008, confirmed by a real passing GitHub Actions run). The Protobuf half **materialized**: the real Windows `check` run on `bef35c2` (TK-009's commit) failed at link time — `error LNK2038: mismatch detected for 'RuntimeLibrary': value 'MT_StaticRelease' doesn't match value 'MD_DynamicRelease' in proof_schema.obj` (156 errors across 50 `libprotobuf.lib` objects) — and separately the job ran ~53 minutes (macOS: ~15 min, unaffected). Root cause of the link failure, confirmed by reading protobuf's own `CMakeLists.txt` at the vendored tag: with `protobuf_BUILD_SHARED_LIBS` off (our case), protobuf unconditionally sets the directory-scoped `CMAKE_MSVC_RUNTIME_LIBRARY` to static (`MultiThreaded...` without `DLL`) whenever `protobuf_MSVC_STATIC_RUNTIME` (a `cmake_dependent_option` defaulting **ON** for static libs) is on — forcing `/MT` on every protobuf/abseil target while our own targets, defined in a sibling directory scope that never sets this variable, keep CMake's own default `/MD`. Root cause of the duration regression, confirmed empirically: (a) protobuf's `FetchContent` did a full-history git clone (measured locally: 2m35s / 355MB) where a shallow clone at the pinned tag is 12.5s / 118MB; (b) `protobuf_BUILD_PROTOC_BINARIES` (default ON) unconditionally forces `protobuf_BUILD_LIBPROTOC` on, and upstream's `libprotoc` target bundles **every** language's codegen backend (java/kotlin/objectivec/php/python/ruby/rust/csharp/upb) as one inseparable target — confirmed by the compile log and by reading `protoc.cmake`/`libprotoc.cmake` — even though Corytm only ever needs `--cpp_out`; (c) without `EXCLUDE_FROM_ALL`, `cmake --build`'s default `ALL` target also builds abseil's full ~200-target tree (test/debug utilities we never link against), not just the ~70 targets `libprotobuf` actually uses. Fix applied and locally re-validated on macOS (TK-009 reopened, see its Notes for the full fix and verification): `protobuf_MSVC_STATIC_RUNTIME OFF` (fixes the CRT mismatch; a no-op on non-MSVC, confirmed by reading the same upstream logic — it is unconditional on platform, but `CMAKE_MSVC_RUNTIME_LIBRARY` itself is only consulted by MSVC); `protobuf_BUILD_PROTOC_BINARIES`/`protobuf_BUILD_LIBPROTOC`/`protobuf_BUILD_LIBUPB` all `OFF` (confirmed `libprotobuf.cmake` has zero dependency on libupb); `protoc` obtained instead via upstream's official prebuilt release binaries (`protoc-36.1-osx-aarch_64.zip` / `protoc-36.1-win64.zip`, SHA256-pinned) rather than built from source; `GIT_SHALLOW TRUE` and `EXCLUDE_FROM_ALL` (requires the `cmake_minimum_required` bump to 3.28, well within both the local 4.4.3 and CI's `lukka/get-cmake@v4.4.2` toolchains) added to protobuf's `FetchContent_Declare`. A genuinely clean local macOS rebuild (post-fix) confirmed: no `libprotoc`/`protoc`/`protoc-gen-upbdefs`/`protoc-gen-upb_minitable`/unused-absl targets are built at all (verified by diffing the actual target list); configure dropped from 347.7s to 204.1s; full clean configure+build+ctest completed in under 9 minutes with both proofs passing. **What remains unverified from this session** (`CLAUDE.md` §10 push restriction): an actual passing Windows CI run confirming the CRT fix resolves the real LNK2038 failure and that the Windows job's total duration drops to a reasonable range — the win64 protoc binary was downloaded and SHA256-verified from this session but never executed on Windows | EP-004, FT-007, FT-008, TK-008, TK-009, ADR-006, ADR-007
