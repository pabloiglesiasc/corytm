This session diagnosed both from real CI evidence (`gh run view`/`gh api`, not the user's report alone) and from reading protobuf's own upstream `CMakeLists.txt` at the vendored tag rather than guessing: `protobuf_MSVC_STATIC_RUNTIME` defaults ON for static libs and forces `/MT` via a directory-scoped `CMAKE_MSVC_RUNTIME_LIBRARY` override that never reaches our own targets; separately, wanting `protoc` at all unconditionally forces the full multi-language `libprotoc` (java/kotlin/objectivec/php/python/ruby/rust/csharp/upb, none of which Corytm uses), and `FetchContent` was doing a full-history clone of protobuf where a shallow one is ~12x faster (measured: 2m35s/355MB vs 12.5s/118MB). `TK-009` and `FT-008` were reopened (`done` → `active`) rather than left standing against this contrary evidence, per `CLAUDE.md` §4/§7 and the user's explicit instruction to do so honestly. The user pushed that fix as `567f353` and ran it: independently confirmed via `gh run view`/`gh api` (run `33483815957`) that the CRT fix genuinely worked (zero `LNK2038`) and duration improved (macOS 10m58s pass; Windows 31m19s, down from ~53 min) — but Windows still failed, further into the build, with a **new** error: `proof.pb.obj : error LNK2001: unresolved external symbol ... fixed_address_empty_string`, `proof_schema.exe : fatal error LNK1120: 1 unresolved externals`. Diagnosed from protobuf `v36.1`'s actual `src/google/protobuf/port.h`, not guessed: `fixed_address_empty_string`'s type is chosen per-translation-unit by an SFINAE probe of `std::string`'s constexpr-default-constructibility, whose result depends on the active C++ standard — confirmed with a standalone reproducer against this machine's own libc++ (`false` under C++17, `true` under C++20). `proof_schema` was set to `cxx_std_20` while `libprotobuf` is unconditionally forced to `cxx_std_17` by protobuf's own CMake (`protobuf_configure_target`); the two TUs disagreed on the symbol's real type — a genuine ODR violation. Checked (not assumed) why this never broke macOS despite the exact same standard split existing there the whole time: MSVC's decorated names encode a global variable's type and correctly refused the mismatched link; the Itanium C++ ABI (macOS/Linux) does not encode a plain variable's type in its mangled name, so the identical violation links silently there — macOS's passing build was never actually correct, just undetected. `protoc`-vs-source version compatibility, which the user specifically asked to rule out first, checked out clean: both are exactly `v36.1`, confirmed via `protoc --version` (`libprotoc 36.1`) and the generated file's own embedded runtime-version comment. Fix: `proof_schema`'s `target_compile_features` changed from `cxx_std_20` to `cxx_std_17`, matching `libprotobuf` exactly — no linker workaround of any kind. For duration, protobuf's `FetchContent` was switched from a git clone to the official source tarball (`URL`/`URL_HASH`, matching the already-established `protoc_binary` pattern); checked first that this doesn't just relocate the cost: file count is nearly identical either way (~3500 files), so this is applied as a legitimate simplification (fewer moving parts, an immutable hash-pinned artifact) rather than a proven speed win — local timing was inconclusive across repeated runs, and Windows CI itself showed no measurable configure-time gain from `GIT_SHALLOW` alone in the prior run either, pointing at per-file checkout overhead (not addressed by either shallow-clone or tarball, both of which fetch the same file count) as the likely real floor; a genuine sparse-checkout was considered and deliberately not attempted this session, as higher-risk/harder-to-validate than justified before correctness lands. Locally re-validated on macOS from a genuinely clean state (both changes together): clean build in 6m30s, `proof_schema`'s own compiler flags now show `-std=gnu++17` matching `libprotobuf`, both `ctest`s pass, full `make check` passes end to end. TK-009/FT-008 remain `active` — this session has now been surprised twice by evidence macOS cannot produce, so it is being explicit that only a real passing Windows Actions run will close this out.
