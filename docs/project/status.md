Diagnosed from protobuf `v36.1`'s actual `src/google/protobuf/port.h`, not guessed: `fixed_address_empty_string`'s type is chosen per-translation-unit by an SFINAE probe of `std::string`'s constexpr-default-constructibility, whose result depends on the active C++ standard — confirmed with a standalone reproducer against this machine's own libc++ (`false` under C++17, `true` under C++20). `proof_schema` was set to `cxx_std_20` while `libprotobuf` is unconditionally forced to `cxx_std_17` by protobuf's own CMake (`protobuf_configure_target`); the two TUs disagreed on the symbol's real type — a genuine ODR violation. Checked (not assumed) why this never broke macOS despite the exact same standard split existing there the whole time: MSVC's decorated names encode a global variable's type and correctly refused the mismatched link; the Itanium C++ ABI (macOS/Linux) does not encode a plain variable's type in its mangled name, so the identical violation links silently there — macOS's passing build was never actually correct, just undetected. `protoc`-vs-source version compatibility, which the user specifically asked to rule out first, checked out clean: both are exactly `v36.1`, confirmed via `protoc --version` (`libprotoc 36.1`) and the generated file's own embedded runtime-version comment. Fix: `proof_schema`'s `target_compile_features` changed from `cxx_std_20` to `cxx_std_17`, matching `libprotobuf` exactly — no linker workaround of any kind. For duration, protobuf's `FetchContent` was switched from a git clone to the official source tarball (`URL`/`URL_HASH`, matching the already-established `protoc_binary` pattern); checked first that this doesn't just relocate the cost: file count is nearly identical either way (~3500 files), so this is applied as a legitimate simplification (fewer moving parts, an immutable hash-pinned artifact) rather than a proven speed win — local timing was inconclusive across repeated runs, and Windows CI itself showed no measurable configure-time gain from `GIT_SHALLOW` alone in the prior run either, pointing at per-file checkout overhead (not addressed by either shallow-clone or tarball, both of which fetch the same file count) as the likely real floor; a genuine sparse-checkout was considered and deliberately not attempted this session, as higher-risk/harder-to-validate than justified before correctness lands.
