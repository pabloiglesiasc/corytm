# TK-001 — Establish Python Development Foundation

Status: done
Feature: FT-001

## Objective

Establish a uv-managed Python project at `src/backend/core/` with pytest, Pyright (strict), and Ruff (lint + format) configured and passing, proving the Python development toolchain before any product/domain code exists.

## Scope / Out of scope

In scope: a uv-managed project boundary at `src/backend/core/` (`pyproject.toml`, `uv.lock`, `.python-version`); pytest, Pyright (strict), and Ruff (lint + format) configured and passing; only the minimal non-domain artifact(s) genuinely required to prove the tooling works — no domain-named package (`engine`, `dorian`, `runtime`, or similar) is created, no source package is required merely for symmetry, and no installable/importable package structure is required unless the tooling genuinely needs one.

Out of scope: any Corytm Engine/Dorian/Runtime domain code or other product/domain functionality; Bandit/security scanning; the unified root quality interface (FT-004); frontend or native work; CI; freezing a specific Python version as a roadmap decision (the implementation PLAN step selects one).

## Acceptance criteria

A valid uv-managed Python project exists at `src/backend/core/`. `.python-version` records a specific, currently-supported Python version. `pytest` discovers and passes the minimal non-domain test used to prove the test foundation works. Pyright strict reports zero errors. Ruff lint passes. Ruff format validation passes. No Corytm product/domain functionality is introduced.

## Dependencies

None.

## References

FT-001 (parent Feature — full accepted scope and exclusions); `docs/technical/architecture.md` (System Shape / Source Tree Direction — establishes `src/backend/core/` as the Python application core's home).

## Notes

The exact Python version is chosen during implementation, not frozen here — an ordinary implementation choice, not a protected architectural decision. Completion is verified using each tool's own native invocation directly, not a root Make command, since FT-004 doesn't exist yet. A minimal non-domain pytest test may be created during execution because pytest needs executable test evidence to prove discovery/execution works — it is infrastructure evidence, not a TDD artifact; classic red-green TDD is not forced onto this tooling/configuration work.
