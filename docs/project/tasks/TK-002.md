# TK-002 — Establish Native Runtime Build Foundation

Status: done
Feature: FT-003

## Objective

Establish a CMake-based native build system at `src/backend/audio/` that vendors Tracktion Engine and JUCE, builds a minimal target linking against them, and runs at least one passing native test — proving the native toolchain works before any production audio behavior exists.

## Scope / Out of scope

In scope: a CMake project boundary at `src/backend/audio/`; vendoring Tracktion Engine and JUCE (git submodules or an equivalent CMake-native mechanism); a minimal build target that links against both; one minimal, explicitly non-domain native test that builds and runs, proving the toolchain works.

Out of scope: any production audio/DAW behavior (track creation, plugin hosting, playback, transport, rendering); the Python↔C++ protocol or any schema under `src/schemas/`; cross-platform CI validation (EP-002); the unified root quality interface (FT-004); Windows validation (macOS only for this proof — cross-platform validation belongs to EP-002 per RSK-001's mitigation).

## Acceptance criteria

A CMake build system exists at `src/backend/audio/` and configures and builds successfully on this machine. Tracktion Engine and JUCE are vendored and linked into the build. At least one native test builds and runs successfully. No production audio/DAW functionality exists anywhere in the project.

## Dependencies

None.

## References

FT-003 (parent Feature — full accepted scope and exclusions); `docs/technical/architecture.md` (Tracktion Engine + JUCE / Source Tree Direction — establishes `src/backend/audio/` as the Native Audio Runtime's home); ADR-003 (Tracktion Engine + JUCE as the Native Audio Foundation — the accepted technology choice this Task builds against).

## Notes

RSK-001 (Tracktion Engine + JUCE native build/integration across macOS and Windows) applies directly to this Task; its mitigation — keep the initial proof deliberately minimal (build + link + one test) — is exactly this Task's scope. Only macOS is validated here; Windows validation is EP-002's concern. Vendoring mechanism (e.g. git submodule vs. CMake `FetchContent`) and exact Tracktion Engine/JUCE versions are chosen during implementation as ordinary tooling decisions, not frozen here. Completion is verified using the native build's own commands directly, not a root Make command, since FT-004 doesn't exist yet.

## Knowledge impact

Several non-obvious Tracktion Engine/JUCE CMake integration gotchas (SSH-pinned submodule, version-specific root `CMakeLists.txt` differences, required `C` language, actual C++ namespace) were captured in `.claude/memory/tracktion-engine-cmake-integration.md` for future native work to reuse without rediscovery.
