# TK-004 — Establish Unified Quality Interface

Status: done
Feature: FT-004

## Objective

Establish a root `Makefile` that unifies the Python, frontend, and native quality checks into a canonical Task-level quality gate (`make check`) and a canonical full-repository quality gate (`make check-all`), without weakening any component's existing checks.

## Scope / Out of scope

In scope: a root `Makefile` with `check`, `check-all`, `check-python`, `check-frontend`, `check-native`, and `clean` targets; `check` invoking each component's already-established native validation commands (`uv run pytest`/`pyright`/`ruff` for Python; `npm run build`/`test`/`lint` for frontend; `cmake`/`ctest` for native); `check-all` running the same validation from a fully clean state (no cached `.venv`, `node_modules`, or native `build/`).

Out of scope: CI invocation of this interface (EP-002); a pre-commit hook (explicitly optional in FT-004's Objective, not pursued here); any change to the per-component tool configuration established by TK-001/TK-002/TK-003; any weakening of an existing check.

## Acceptance criteria

`make check` runs the Python, frontend, and native checks and passes. `make check-all` performs the same validation from a fully clean state and passes. No component's quality constraint is weakened by the unification. No product/domain functionality is introduced anywhere.

## Dependencies

TK-001, TK-002, TK-003.

## References

FT-004 (parent Feature — full accepted scope and exclusions).

## Notes

Target names (`check`, `check-all`) are decided here, in the Feature/Task that actually builds this interface — until now they were deliberately left as capability language elsewhere in PMO/knowledge artifacts, per `CLAUDE.md` §11. `check-all` reuses `check`'s own per-component targets after `clean`, rather than duplicating validation logic.
