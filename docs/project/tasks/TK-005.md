# TK-005 — Author CI Workflow

Status: done
Feature: FT-005

## Objective

Author a GitHub Actions workflow at `.github/workflows/` that runs `make check` on a `macos-latest` / `windows-latest` build matrix for every push and pull request, matching what a local session already runs.

## Scope / Out of scope

In scope: one workflow file triggered on `push` and `pull_request`; a matrix job over `macos-latest` and `windows-latest`; steps provisioning uv, Node, CMake/Ninja, and (Windows only) GNU Make via Chocolatey, then invoking `make check`.

Out of scope: actually observing a triggered run — this session cannot push commits (`CLAUDE.md`'s git-administration prohibition is absolute), so no GitHub Actions run can be triggered or watched from here; dependency/security scanning; deployment/release; CI invocation of `make check-all` (reserved for globally significant work, not every push).

## Acceptance criteria

A workflow file exists at `.github/workflows/` with valid YAML and a correct `macos-latest`/`windows-latest` matrix. Its steps use current, real action versions (verified against each action's actual latest release, not guessed). The macOS leg's command sequence is identical in substance to the `make check` sequence already validated locally on this machine (TK-004). The Windows leg's tool-provisioning steps are grounded in the actual GitHub-hosted Windows runner image's documented software list (verified, not assumed) — specifically, that GNU Make is absent by default (Chocolatey install needed) and that Git Bash is present (enabling a POSIX-style `make` invocation).

## Dependencies

None.

## References

FT-005 (parent Feature — full accepted scope); `docs/project/tasks/TK-004.md` (defines the exact `make check` sequence this workflow must reproduce).

## Notes

This Task's Acceptance criteria is deliberately scoped to what a session without Git push access can actually deliver and verify: a correctly authored, evidence-grounded workflow. Whether the workflow actually succeeds when GitHub Actions runs it — especially the Windows leg's native build, which RSK-001 already flags as the highest-risk, least-proven part of the toolchain — is not and cannot be verified here; it requires an actual push-triggered run, which only a human with Git privileges can perform and observe. This residual gap is why FT-005 completing does not itself satisfy EP-002's own Acceptance criteria ("CI runs on every relevant change") — EP-002 stays open until that real run is observed.

## Knowledge impact

The Windows-runner tooling gap (no GNU Make by default; Chocolatey and Git Bash are present) is captured in `.claude/memory/github-actions-windows-runner.md`. `RSK-001` updated to note a CI workflow now exists to validate Windows, pending an actual run.
