# TK-006 — Fix Windows Native Build Compiler Selection

Status: done
Feature: FT-005

## Objective

Fix the Windows CI failure in `check-native` (real evidence: `error: "MinGW is not supported. Please use an alternative compiler."` from JUCE, with CMake's Ninja generator having auto-detected `C:/mingw64/bin/cc.exe`/`c++.exe` instead of MSVC) while keeping the root `Makefile`'s `check-native` target identical across platforms.

## Scope / Out of scope

In scope: diagnosing why CMake selected a MinGW compiler on the Windows runner; a fix confined to the root `Makefile`'s `check-native` target (no OS-conditional branching, no separate Windows build path, no change to `CMakeLists.txt` or `.github/workflows/check.yml`); re-validating `make check-all` locally on macOS after the change.

Out of scope: actually observing the fix on a real Windows GitHub Actions run — this session cannot push, so the fix cannot be confirmed on the runner itself, only reasoned through from documented CMake/Windows generator behavior and validated locally on macOS.

## Acceptance criteria

The root cause is identified and stated precisely, grounded in the actual CI evidence (not assumed). The fix removes CMake's Windows dependency on PATH-based compiler auto-detection (the actual failure mechanism), without introducing per-OS branches into the Makefile or workflow. `make check-all` passes locally on macOS after the change, from a fully clean state. `RSK-001` and relevant knowledge artifacts are updated to reflect the real failure and the fix's reasoning.

None.

## Notes

**Root cause:** the Makefile's `check-native` target hardcoded `cmake ... -G Ninja`. CMake's Ninja generator locates a compiler by searching `PATH` (after checking `CC`/`CXX` env vars, neither of which the workflow set) — it has no awareness of Visual Studio. GitHub's `windows-latest` runner image ships an MSYS2/MinGW toolchain reachable on `PATH` by default, while `cl.exe` is *not* on `PATH` without first running Visual Studio's `vcvarsall.bat`-equivalent environment setup (which the workflow never did). So Ninja's auto-detection found MinGW's `gcc`/`g++` and used those — and JUCE explicitly refuses to compile under MinGW (`juce_TargetPlatform.h`), so the build fails immediately. Python and frontend were unaffected because neither uv nor npm does PATH-based *C/C++* compiler discovery.

**Why this fix over the alternative:** the standard workaround for "Ninja + MSVC on Windows CI" is the `ilammy/msvc-dev-cmd` action, which injects `cl.exe`'s directory (plus `INCLUDE`/`LIB`) onto `PATH`. It was deliberately not used: its own documented caveat is that GitHub Actions' `shell: bash` (required here, since the Makefile uses `&&`/`cd`/`rm -rf`) unconditionally re-prepends GNU paths at the start of every step, which is documented to shadow MSVC's `link.exe` with `/usr/bin/link` — trading one PATH-ordering failure mode for another, still-fragile one. Dropping `-G Ninja` instead (letting CMake use its own per-platform default generator — "Unix Makefiles" on macOS/Linux, the installed Visual Studio/MSBuild generator on Windows) sidesteps PATH-based compiler discovery on Windows entirely: the Visual Studio generator locates MSVC through Visual Studio's own installation metadata, independent of `PATH` or shell. `--config Release` / `-C Release` were added to `cmake --build`/`ctest` since the VS/MSBuild generator is multi-config (unlike Ninja); both flags are accepted as no-ops on the single-config generators macOS/Linux fall back to.

**Unverified:** whether the Windows leg's MSVC compile of Tracktion Engine + JUCE itself succeeds (a separate concern from compiler *selection*) is not provable without an actual GitHub Actions run.
