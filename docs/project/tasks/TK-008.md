# TK-008 — Bootstrap Tauri 2 Desktop Shell Wrapping Existing Frontend

Status: done
Feature: FT-007

## Objective

Scaffold a Tauri 2 project under `src/frontend/desktop/` that hosts the existing Vite/React frontend unchanged, get it building and launching locally on this macOS development machine, and wire it into the root Makefile's quality interface — the first direct proof of ADR-006 (Tauri 2 as the desktop shell).

## Scope / Out of scope

In scope: installing a local Rust toolchain; adding the Tauri 2 CLI and scaffolding a `src-tauri/` Rust crate inside `src/frontend/desktop/`, configured to load the existing Vite dev server in development and the existing production build in a release bundle; verifying `cargo tauri build` produces a working macOS application bundle and that it launches (a process starts and can be cleanly terminated) hosting the existing frontend's current placeholder content unchanged; a new `check-desktop` Makefile target invoked from `check`; updating `.github/workflows/check.yml` to install a Rust toolchain and attempt the same build on both the macOS and Windows runners.

Out of scope: confirming the Windows CI leg actually passes — this session cannot push (`CLAUDE.md` §10), so only local macOS validation and reasoned-through CI configuration are possible, mirroring TK-006's precedent; Tauri's sidecar mechanism and any Python/Native Audio Runtime process spawning (future EP-004 work, no Feature/Task created yet); any Protobuf schema or transport work (likewise, future EP-004 work only); any real product UI, design system, or screens; code signing/notarization or installer distribution concerns.

## Acceptance criteria

A Tauri 2 project exists under `src/frontend/desktop/src-tauri/`. `cargo tauri build` succeeds locally and produces a macOS `.app` bundle. The built app launches as a real process (started and cleanly terminated) hosting the existing frontend's current content, unchanged from its pre-Tauri form. `make check` includes a `check-desktop` target that builds the Tauri shell and passes locally. `.github/workflows/check.yml` is updated to install Rust and run the new target on both `macos-latest` and `windows-latest`, reasoned through against documented Tauri/Windows (WebView2) build requirements even though an actual passing Windows run cannot be confirmed from this session. RSK-002 is updated to reflect what was actually proven locally versus what remains unconfirmed pending a real CI run.

## Notes

Toolchain/config bootstrap: TDD is skipped per `CLAUDE.md` §7 — there is no behavior to write a failing test against, only a build/launch toolchain to prove, mirroring FT-001/FT-002/FT-003's precedent in EP-001.

A local Rust toolchain (`rustup`, stable, 1.98.0) was installed on this development machine as a prerequisite — anticipated by ADR-006's Consequences ("Rust is added as a build/toolchain language"). The Tauri CLI is consumed as the npm devDependency `@tauri-apps/cli` (invoked via `npm run tauri`), not a separately-installed `cargo tauri` subcommand, so `make check-desktop` has no hidden machine-level prerequisite beyond what `npm ci` already installs.

**Verified:** `cargo tauri init` scaffolded `src-tauri/` configured with `frontendDist: "../dist"`, `devUrl: http://localhost:5173`, and before-dev/before-build commands delegating to the existing `npm run dev`/`npm run build` — the existing frontend is unmodified. `npm run tauri build` succeeds locally from a clean state (confirmed via a full `make check` run) and produces `corytm.app` and `corytm_0.1.0_aarch64.dmg` under `src-tauri/target/release/bundle/`. The built `.app`'s binary was also launched directly as a process, observed running, and cleanly terminated with no error output.

`npm run tauri dev` was separately verified: it started the Vite dev server on `localhost:5173`, then compiled and ran the debug binary (`Finished 'dev' profile ... Running 'target/debug/app'`), which opened a real window. The user directly observed this window in this session's own GUI environment and confirmed it displayed the existing frontend's "Frontend toolchain proof" text — genuine human visual confirmation, not a process-level proxy, that the WebView correctly renders the existing frontend unchanged, satisfying FT-007's "launches ... hosting the existing frontend's current content" criterion for both `dev` and `build`. This session's own attempt to capture a screenshot (`screencapture`) failed ("could not create image from display"), so the earlier plan to rely on a process-level proxy for "launches" is now superseded by this direct observation.

**Unverified:** a real passing Windows CI run — this session cannot push (`CLAUDE.md` §10), so the CI workflow change is reasoned through against documented Tauri/Windows requirements (WebView2 is preinstalled on GitHub's `windows-latest` image; MSVC build tools are already required and present for `check-native`) but not observed running, mirroring TK-006's precedent exactly.

An unrelated local-only build failure was diagnosed and fixed during VALIDATE: `bundle_dmg.sh` failed once with an opaque error because a prior `tauri build` invocation had left a temporary DMG volume mounted under `/Volumes`; detaching it resolved the failure immediately with no code change needed. Captured in `.claude/memory/tauri-dmg-stale-mount.md` since it is local-machine-specific and cannot recur in CI's always-clean runners.
