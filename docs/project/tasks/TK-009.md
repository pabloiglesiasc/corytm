# TK-009 — Vendor Protobuf and Prove Cross-Language Codegen from a Minimal Schema

Status: done
Feature: FT-008

## Objective

Add one minimal, illustrative `.proto` message under `src/schemas/`, vendor Protobuf into the CMake native build (mirroring the existing JUCE/Tracktion Engine `FetchContent` pattern) to generate and compile C++ bindings, wire a uv-managed codegen step to generate the matching Python bindings, add `protobuf` as a Python runtime dependency, and prove both sides can construct, serialize, and deserialize the same message with a round-trip test — the first direct proof of ADR-007's schema/codegen half.

## Scope / Out of scope

In scope: `src/schemas/proof.proto` defining one message with an explicit schema-version field and one payload field; `src/backend/audio/CMakeLists.txt` changes to `FetchContent` Protobuf and generate/compile C++ bindings from that schema; a native round-trip proof (construct, serialize, deserialize, assert equality) run via `ctest`; a uv-managed Python codegen step (dev-only tool) generating Python bindings from the same `.proto`; `protobuf` added to `[project.dependencies]` in `src/backend/core/pyproject.toml`; a Python round-trip proof run via `pytest`; wiring both into `make check-native` / `make check-python` so `make check` exercises the whole thing from a clean state.

Out of scope: Tauri sidecar process spawning and any Python/Native Audio Runtime process lifecycle work; the loopback-socket transport, framing, or per-launch-secret authentication (ADR-007's transport half); any real product command/event content (Track, Clip, Note, or any other Corytm Engine concept); `.github/workflows/check.yml` changes (no new system-level prerequisite is introduced — Protobuf is vendored via `FetchContent` on the C++ side and via a uv dev-dependency on the Python side, matching TK-008's "no hidden machine prerequisite" precedent, so the existing workflow should already exercise this unchanged); confirming a real GitHub Actions run (mirrors TK-006/TK-008 precedent — this session can validate locally only, per `CLAUDE.md` §10).

## Acceptance criteria

`src/schemas/proof.proto` exists, defining a minimal message with a schema-version field. Its naming alone — file `proof.proto`, package `corytm.schemas.proof`, message `ProofMessage` — signals it is an illustrative toolchain proof rather than real product content, per `CLAUDE.md` §8's zero-comments rule (mirrors `toolchain_proof.cpp`'s existing naming precedent); no comment is added to the schema file itself. `make check-native` vendors Protobuf via CMake `FetchContent`, generates C++ bindings from `proof.proto`, builds a proof that round-trips the message (construct → serialize → deserialize → assert equality, including the version field), and this proof passes via `ctest`. `make check-python` generates Python bindings from the same `proof.proto` via a uv-managed dev tool, and a `pytest` test round-trips the same message and passes. `protobuf` is a `[project.dependencies]` entry in `src/backend/core/pyproject.toml`. `make check` passes locally from a clean state (`make check-all`). RSK-002 and `docs/project/status.md` are updated to reflect that both toolchain halves are now proven.

## Notes

Toolchain proof, not product behavior: mirrors FT-001/FT-002/FT-003/TK-008's precedent — the "failing test first" TDD default is expressed here as writing the round-trip proof against the not-yet-generated bindings (so it fails to even compile/import first), then making it pass by wiring the codegen, rather than testing pre-existing behavior.

**Verified:** `src/schemas/proof.proto` defines `corytm.schemas.proof.ProofMessage` (a `schema_version` uint32 and a `payload` string). Python side: `protobuf>=7.36.1` added to `[project.dependencies]`; `grpcio-tools>=1.83.1` added as a dev-only codegen tool (used only for its bundled `protoc` via `python -m grpc_tools.protoc`, not for gRPC itself); `pythonpath = ["generated"]` (pytest) and `extraPaths = ["generated"]` (pyright) added so `tests/test_proof_schema.py` resolves the generated `proof_pb2`/`proof_pb2.pyi` without including generated code in Pyright's own strict `include`; `generated/` excluded from ruff and gitignored (build output, never hand-edited, per `CLAUDE.md` §8). The round-trip test failed with `ModuleNotFoundError: No module named 'proof_pb2'` before this wiring, confirmed passing after. `make check-python` regenerates the bindings before running `pytest`/`pyright`/`ruff`; all pass from a clean `generated/` state. C++ side: `src/backend/audio/CMakeLists.txt` vendors Protobuf via `FetchContent` (`v36.1`, matching the Python runtime's `7.36.1` line), mirroring the existing JUCE/Tracktion Engine pattern; `protobuf_INSTALL` forced `OFF` since nothing is installed. Protobuf's own CMake only exposes its `protobuf_generate()` helper function through the post-install `find_package(protobuf CONFIG)` path (confirmed by reading `cmake/protobuf-config.cmake.in` upstream at the vendored tag), not when consumed via `FetchContent`/`add_subdirectory` directly — so C++ codegen instead uses an explicit `add_custom_command` invoking the `protobuf::protoc` ALIAS executable target directly against `proof.proto`, generating into `${CMAKE_CURRENT_BINARY_DIR}/generated`, consumed as a source of the new `proof_schema` executable (linked against `protobuf::libprotobuf`) and run via `ctest`. Abseil-cpp is pulled in transitively and automatically by protobuf's own `cmake/abseil-cpp.cmake` (`FetchContent` fallback when `find_package(absl CONFIG)` doesn't find a local install) — no action needed on this Task's part. `make check-native` (`cmake -S ... -B ...` reusing the existing JUCE/Tracktion cache, then a from-scratch protobuf+abseil fetch/build, then `ctest`) passes locally on macOS: both `toolchain_proof` and the new `proof_schema` test pass. A `[[nodiscard]]` compiler warning on `SerializeToString`/`ParseFromString`'s ignored return values was fixed by checking both booleans in the round-trip assertion, per `CLAUDE.md` §8 ("warnings are failures to understand, not noise to suppress") — not suppressed. Full `make check` was also run locally end to end (Python, native, and — after separately confirming this session's own Bash-tool shell simply doesn't have `~/.cargo/bin` on `PATH`, an environment quirk unrelated to this Task, see `.claude/memory/cargo-path-missing-in-tool-shell.md` — frontend/desktop) and passes.

**Unverified:** a real passing Windows CI run for the new protobuf/abseil `FetchContent` additions — this session cannot push (`CLAUDE.md` §10), mirroring TK-006/TK-008's precedent exactly. `.github/workflows/check.yml` needed no changes: Protobuf is vendored via CMake `FetchContent` (no new system package) and Python codegen runs via a `uv`-managed dev dependency (`grpcio-tools`), matching TK-008's "no hidden machine prerequisite" precedent, so the existing `make check` invocation on both runners should already exercise it — reasoned through, not observed running.
