# TK-009 — Vendor Protobuf and Prove Cross-Language Codegen from a Minimal Schema

Status: done
Feature: FT-008

## Objective

Add one minimal, illustrative `.proto` message under `src/schemas/`, vendor Protobuf into the CMake native build (mirroring the existing JUCE/Tracktion Engine `FetchContent` pattern) to generate and compile C++ bindings, wire a uv-managed codegen step to generate the matching Python bindings, add `protobuf` as a Python runtime dependency, and prove both sides can construct, serialize, and deserialize the same message with a round-trip test — the first direct proof of ADR-007's schema/codegen half.

## Scope / Out of scope

In scope: `src/schemas/proof.proto` defining one message with an explicit schema-version field and one payload field; `src/backend/audio/CMakeLists.txt` changes to `FetchContent` Protobuf and generate/compile C++ bindings from that schema; a native round-trip proof (construct, serialize, deserialize, assert equality) run via `ctest`; a uv-managed Python codegen step (dev-only tool) generating Python bindings from the same `.proto`; `protobuf` added to `[project.dependencies]` in `src/backend/core/pyproject.toml`; a Python round-trip proof run via `pytest`; wiring both into `make check-native` / `make check-python` so `make check` exercises the whole thing from a clean state.

Out of scope: Tauri sidecar process spawning and any Python/Native Audio Runtime process lifecycle work; the loopback-socket transport, framing, or per-launch-secret authentication (ADR-007's transport half); any real product command/event content (Track, Clip, Note, or any other Corytm Engine concept); `.github/workflows/check.yml` changes (no new system-level prerequisite is introduced — Protobuf is vendored via `FetchContent` on the C++ side and via a uv dev-dependency on the Python side, matching TK-008's "no hidden machine prerequisite" precedent, so the existing workflow should already exercise this unchanged); confirming a real GitHub Actions run (mirrors TK-006/TK-008 precedent — this session can validate locally only, per `CLAUDE.md` §10).

## Acceptance criteria

`src/schemas/proof.proto` exists, defining a minimal message with a schema-version field. Its naming alone — file `proof.proto`, package `corytm.schemas.proof`, message `ProofMessage` — signals it is an illustrative toolchain proof rather than real product content, per `CLAUDE.md` §8's zero-comments rule (mirrors `toolchain_proof.cpp`'s existing naming precedent); no comment is added to the schema file itself. `make check-native` vendors Protobuf via CMake `FetchContent`, generates C++ bindings from `proof.proto`, builds a proof that round-trips the message (construct → serialize → deserialize → assert equality, including the version field), and this proof passes via `ctest`. `make check-python` generates Python bindings from the same `proof.proto` via a uv-managed dev tool, and a `pytest` test round-trips the same message and passes. `protobuf` is a `[project.dependencies]` entry in `src/backend/core/pyproject.toml`. `make check` passes locally from a clean state (`make check-all`). RSK-002 and `docs/project/status.md` are updated to reflect that both toolchain halves are now proven.

## Reopened — real Windows CI failure (2026-09-01)

This Task was closed `done` above on local macOS evidence alone, with a real Windows CI run explicitly flagged as the one unverified item. That run (`bef35c2`, this Task's own commit) genuinely failed, and the failure is now the authoritative evidence per `CLAUDE.md` §4 (current code and CI behavior over a prior session's optimistic summary). Reopened per the user's explicit instruction to do so honestly rather than leave the "fully proven" claim standing. Full diagnosis, fix, and re-validation below; the **Verified**/**Unverified**/Knowledge impact sections above are left untouched as the historical record of what was actually checked at the time (`CLAUDE.md` §5's "accepted decisions... must not be rewritten to hide history" applied here by analogy).

**Real evidence gathered** (`gh run view`/`gh api` against run `33473723986`, independently pulled, not taken on the user's word): the Windows job took 52m53s and failed; macOS took 15m9s and passed, so the regression and the failure are both Windows-specific. Step timing: all setup steps (checkout/uv/node/cmake/rust/choco) together took under a minute; the entire cost is inside `Run make check`. Within that: Tauri's `beforeBuildCommand`/bundling ran from job start to 05:40:21 (~11 min, matching the user's "~10 min" figure, and unrelated to this Task); `cmake -S` (native configure) ran 05:40:21→05:46:09, "Configuring done (347.7s)" (~5m48s, matching the user's "~6 min"); `cmake --build` started 05:46:11 and the first of 156 `LNK2038` errors (across 50 distinct `libprotobuf.lib` objects) appeared at 06:09:04 — `libprotobuf.lib(arenastring.obj) : error LNK2038: mismatch detected for 'RuntimeLibrary': value 'MT_StaticRelease' doesn't match value 'MD_DynamicRelease' in proof_schema.obj`; MSBuild then kept building the *other*, independent `toolchain_proof` target (JUCE/Tracktion, unaffected by protobuf) for another ~12 minutes before the job reported failure at 06:21:05 (`make: *** [Makefile:26: check-native] Error 1`) — real wasted CI time from having two independent executables in one default-`ALL` build where one's failure doesn't stop the other.

**Root cause, CRT mismatch** — confirmed by reading protobuf's own `CMakeLists.txt` at the vendored tag (`v36.1`), not guessed: `cmake_dependent_option(protobuf_MSVC_STATIC_RUNTIME "Link static runtime libraries" ON "NOT protobuf_BUILD_SHARED_LIBS" OFF)` defaults **ON** for static libs (our case — we never build protobuf as a DLL), and further down: `if (protobuf_MSVC_STATIC_RUNTIME) set(CMAKE_MSVC_RUNTIME_LIBRARY MultiThreaded$<$<CONFIG:Debug>:Debug>) else() set(CMAKE_MSVC_RUNTIME_LIBRARY MultiThreaded$<$<CONFIG:Debug>:Debug>DLL) endif()`. This directory-scoped `set()` runs inside protobuf's own `FetchContent`-populated subdirectory and does not propagate up to our own top-level `CMakeLists.txt`, so `proof_schema`/`toolchain_proof` (defined there) silently kept CMake's own default (`.../DLL`, i.e. `/MD`) while every protobuf/abseil object was forced to `/MT` — precisely the reported `MT_StaticRelease` vs `MD_DynamicRelease` mismatch. `protobuf_MSVC_STATIC_RUNTIME`'s effect is unconditional in that file (not gated by `if(WIN32)`), but `CMAKE_MSVC_RUNTIME_LIBRARY` itself is a no-op on non-MSVC toolchains, which is exactly why this never surfaced on macOS.

**Root cause, build-surface/duration** — also confirmed from upstream source, not assumed: (1) `if (protobuf_BUILD_PROTOC_BINARIES OR protobuf_BUILD_TESTS) set(protobuf_BUILD_LIBPROTOC ON) endif()` — since `protobuf_BUILD_PROTOC_BINARIES` defaults ON, building `protoc` at all unconditionally forces the full `libprotoc` target, which (`libprotoc.cmake`) bundles **every** language backend (java/kotlin/objectivec/php/python/ruby/rust/csharp/upb) as one inseparable CMake target — confirmed directly in both the original local build log and this Windows log (`compiler/java/*`, `compiler/kotlin/*`, `compiler/objectivec/*`, `compiler/php/*`, `compiler/rust/accessors/*`, `protoc-gen-upbdefs`, `protoc-gen-upb_minitable`, none of which Corytm's `--cpp_out`-only usage needs). (2) Without `EXCLUDE_FROM_ALL` on the `FetchContent_Declare`, `cmake --build`'s default `ALL` target also builds abseil's entire ~200-target tree — confirmed by comparing the pre-fix build log's target list (`absl_scoped_set_env`, `absl_cordz_sample_token`, `absl_random_internal_distribution_test_util`, `absl_flags_parse`, `absl_flags_usage`, `absl_failure_signal_handler`, `absl_log_flags`, `absl_periodic_sampler`, etc.) against `libprotobuf.cmake`'s actual `target_link_libraries` (only `${protobuf_ABSL_USED_TARGETS}`, `utf8_validity`, threads, zlib — none of the above). (3) `cmake -S`'s own ~6-minute configure cost is dominated by `FetchContent`'s full-history git clone of protobuf — measured directly on this machine: a full `git clone` of `protocolbuffers/protobuf` took 2m35s (355MB) versus a shallow `git clone --depth 1 --branch v36.1` at 12.5s (118MB), a ~12x difference; abseil's own clone was checked too (28s full / 9.6s shallow) but the gain there is comparatively small.

**Fix applied to `src/backend/audio/CMakeLists.txt`** (smallest change preserving ADR-007 — the schema and the C++/Python codegen pipelines stay parallel and independent exactly as ADR-007 describes; nothing about the transport, the schema, or the shipped runtime dependency changes): `protobuf_MSVC_STATIC_RUNTIME OFF` (fixes the CRT mismatch directly); `protobuf_BUILD_PROTOC_BINARIES OFF`, `protobuf_BUILD_LIBPROTOC OFF`, `protobuf_BUILD_LIBUPB OFF` (stop building `protoc`/`libprotoc`/every language backend from source — `libprotobuf`, the only thing ADR-007 actually requires vendored/built for linking, is unaffected and stays `ON`); `protoc` for C++ codegen is now obtained from protobuf's own official prebuilt release binaries (`protoc-36.1-osx-aarch_64.zip`, `protoc-36.1-win64.zip`), fetched via a `FetchContent_Declare(protoc_binary URL ... URL_HASH SHA256=...)` with hashes computed from a direct download of each asset from `github.com/protocolbuffers/protobuf`'s real release page this session (upstream's own `tool_integrity.bzl` for this release was checked first but its hash table was empty, so this is a self-computed pin, the same practice Homebrew/vcpkg/Bazel `http_archive` use for exactly this kind of asset); `GIT_SHALLOW TRUE` and `EXCLUDE_FROM_ALL` added to the `protobuf` `FetchContent_Declare` (the latter requires bumping `cmake_minimum_required` from 3.22 to 3.28 — well within both the local CMake 4.4.3 and CI's `lukka/get-cmake@v4.4.2`). The `add_custom_command` that generates `proof.pb.cc`/`proof.pb.h` now invokes the downloaded `protoc` executable path directly instead of the (no-longer-built) `protobuf::protoc` target. Only macOS/Windows branches are handled (`if (APPLE) ... elseif (WIN32) ... else() message(FATAL_ERROR ...)`), matching the actual `check.yml` matrix — no Linux support was added since none exists in CI or was ever claimed.

**Locally re-validated on macOS from a genuinely clean state** (`rm -rf src/backend/audio/build` first): `cmake -S`/`-B` configure dropped from 347.7s to 204.1s; verified the protobuf `_deps` git checkout is now truly shallow (`git rev-parse --is-shallow-repository` → true, 1 commit) and that the downloaded `protoc` binary is a real, executable (permission bits preserved through CMake's own zip extraction — confirmed, this was a real risk worth checking, not assumed) arm64 Mach-O; a clean `cmake --build` completed in 5m37s and produced **no** `libprotoc`/`protoc`/`protoc-gen-upbdefs`/`protoc-gen-upb_minitable` targets and none of the previously-observed unused `absl_*` test/debug targets — confirmed by diffing the actual built-target list, not assumed; `ctest` passed both `toolchain_proof` and `proof_schema`; `make check-native` (the literal CI-invoked target) and a full `make check` (Python/native/frontend/desktop) were run afterward and passed. Total clean `check-native` pipeline (configure + build + test) is now under 9 minutes locally, versus the prior run's ~35 minutes to a still-failing result.

## Reopened again — real Windows CI LNK2001 (2026-09-01, later same day)

The user pushed the CRT/build-surface fix as `567f353` and ran it on real CI. Confirmed independently via `gh run view`/`gh api` (run `33483815957`), not taken on faith: the CRT fix genuinely worked — zero `LNK2038` anywhere in the log — and duration improved materially (macOS 10m58s pass; Windows 31m19s, down from ~53 min, still a failure). A **new**, later link failure surfaced: `proof.pb.obj : error LNK2001: unresolved external symbol "class google::protobuf::internal::GlobalEmptyStringConstexpr const google::protobuf::internal::fixed_address_empty_string"` then `proof_schema.exe : fatal error LNK1120: 1 unresolved externals`, with `libprotobuf.vcxproj` itself building successfully first and `proof.pb.cc`/`proof.pb.h` generated successfully — the final `make: *** [Makefile:26: check-native] Error 1` is only the propagated wrapper failure, per the user's framing. Kept Status `active` (was never re-closed after the first reopening) rather than pretending this second failure doesn't also need honest tracking.

**Diagnosis, grounded in protobuf's actual source, not guessed:** fetched `src/google/protobuf/port.h` at the exact vendored tag (`v36.1`). `fixed_address_empty_string`'s type is `using GlobalEmptyString = std::conditional_t<GlobalEmptyStringConstexpr::HasConstexprDefaultConstructor(0), const GlobalEmptyStringConstexpr, GlobalEmptyStringDynamicInit>;` — an SFINAE probe of whether `std::basic_string` with a deliberately non-constexpr-friendly custom allocator can be default-constructed and measured (`.size()`) during constant evaluation. This is a property of the **standard library implementation under the active language standard**, not a protobuf feature flag. Verified with a standalone reproducer compiled against this machine's own libc++ (the exact probe code copied from `port.h`): `false` under `-std=c++17`, `true` under `-std=c++20`, both confirmed by direct execution, not assumed. `proof_schema` (in `src/backend/audio/CMakeLists.txt`) was set to `target_compile_features(proof_schema PRIVATE cxx_std_20)`, while `libprotobuf` is unconditionally forced to `cxx_std_17` by protobuf's own `cmake/protobuf-configure-target.cmake` (`target_compile_features("${target}" PUBLIC cxx_std_17)`, applied to every protobuf target with no override option) — confirmed directly via each target's generated `flags.make` locally (`-std=gnu++20` for `proof_schema` vs `-std=gnu++17` for `libprotobuf`, pre-fix). The two TUs therefore disagreed on `fixed_address_empty_string`'s actual type — a genuine ODR violation, not a version-numbering mismatch between the prebuilt `protoc` and the vendored source (both are the exact `v36.1` tag/release; `protoc --version` reported `libprotoc 36.1`, and the generated `.pb.h`'s own "Protobuf C++ Version: 7.36.1" comment matches the vendored `protobuf` source's own runtime version line — no version skew was found there, which is exactly what the user asked to rule out first, and it checked out clean).

**Why this only broke on Windows** — checked rather than hand-waved, since the exact same `cxx_std_20`/`cxx_std_17` split already existed on macOS every time this session built it, yet macOS never failed: MSVC's decorated name for the unresolved symbol embeds the variable's *type* (`?fixed_address_empty_string@internal@protobuf@google@@3VGlobalEmptyStringConstexpr@123@B` — the `VGlobalEmptyStringConstexpr` portion is the type), so its linker correctly refuses to resolve a reference typed `GlobalEmptyStringConstexpr` against a definition typed `GlobalEmptyStringDynamicInit`. The Itanium C++ ABI (Clang/GCC, i.e. macOS/Linux) does not encode a plain namespace-scope variable's type in its mangled name at all — only function parameter types are mangled — so the identical ODR violation links "successfully" and silently on macOS. **macOS's passing build was never actually correct here; it was an undetected violation, not an absence of one.** This is now captured generally in `.claude/memory/protobuf-generated-code-cxx-standard-abi.md` since it applies to any vendored C++ library with its own forced language standard, not just this one symbol.

**Fix:** `target_compile_features(proof_schema PRIVATE cxx_std_20)` → `cxx_std_17` in `src/backend/audio/CMakeLists.txt` — the one target that both compiles protobuf-generated code and links `protobuf::libprotobuf` now matches the standard protobuf itself is built with, exactly. `toolchain_proof` (JUCE/Tracktion only, no protobuf dependency) is untouched — no reason to touch it, and doing so would be unrelated scope. No `/FORCE`, no manual symbol definitions, no `NODEFAULTLIB`, no warning suppression, no platform-specific branch — the upstream contract (build everything touching protobuf ABI at the same standard protobuf itself uses) was the thing actually violated, so removing that violation is the fix, exactly as instructed.

**Duration, continued:** protobuf's `FetchContent` was switched from `GIT_REPOSITORY`/`GIT_TAG`/`GIT_SHALLOW` to the official source tarball (`URL https://.../protobuf-36.1.tar.gz`, `URL_HASH SHA256=...`, self-computed the same way the `protoc_binary` hashes were), matching the pattern already established for `protoc_binary`. Checked before applying, not assumed: the tarball extracts to 3514 files / 54MB versus the shallow git clone's 3573 files / 118MB — file *count* is essentially identical (the git clone's extra ~60 files are `.git`-related, not source), so this does not address the dominant Windows configure-time cost, which is most likely per-file checkout/write overhead rather than network transfer or history depth. It's applied anyway as a legitimate, low-risk simplification (fewer moving parts than git — no tag/ref resolution, an immutable hash-pinned release artifact, one less subsystem in the fetch path) but is **not** claimed as a proven speed fix: local timing was inconclusive across repeated runs (204.1s → 431.9s), most plausibly network variance given the near-identical file counts, and the prior `GIT_SHALLOW`-only change showed no measurable improvement on the actual Windows runner either (347.7s → 355.3s in the previous run). A real fix for the Windows configure-time floor would need a genuine sparse-checkout (fetching only `src/google/protobuf/**` + `cmake/**`, skipping the java/python/csharp/php/ruby/objectivec/rust/kotlin/benchmarks/conformance/docs/examples subtrees protobuf's repo also carries) — not attempted this session: it requires abandoning the plain `FetchContent_Declare` pattern used everywhere else in this file for something more manual and fragile, its actual Windows-checkout-speed benefit can't be measured without CI access, and correctness had to come first per the user's explicit instruction. Left as a documented, evidence-backed candidate for a future session, not implemented speculatively.

**Locally re-validated on macOS from a genuinely clean state** (`rm -rf build` first, for both the tarball switch and the C++17 fix together): configure succeeded (431.9s — see duration note above); clean build completed in 6m30s with **no** `libprotoc`/`protoc`/`protoc-gen-*`/unused-`absl` targets (re-confirmed, same check as the first reopening); `proof_schema`'s own `flags.make` now shows `-std=gnu++17`, matching `libprotobuf`'s; `ctest` passed both `toolchain_proof` and `proof_schema`; a full `make check` (Python/native/frontend/desktop) passed end to end afterward.

**Still unverified from this session** (`CLAUDE.md` §10 — cannot push): whether `LNK2001`/`LNK1120` are actually gone on real Windows/MSVC (this bug was never observable on macOS in the first place, per the ABI analysis above, so a clean local build here is necessary but not remotely sufficient evidence); the real Windows job duration after this second fix.
