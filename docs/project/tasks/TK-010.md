# TK-010 — Implement and Prove the ADR-007 Loopback Transport Round Trip

Status: done
Feature: FT-009

## Objective

Add a new native executable that connects to a Python-owned loopback socket using JUCE's `InterprocessConnection` framing, authenticates with a per-launch secret, and round-trips one `ProofMessage` command/event pair; add a Python-side `asyncio` server implementing the same wire framing manually; wire both into `make check` as a real, automated, cross-language integration test.

## Scope / Out of scope

In scope: `src/backend/audio/transport_proof.cpp` (a `juce::InterprocessConnection` client: connects to `127.0.0.1:<port>`, sends the secret, receives and decodes a `ProofMessage` command, sends back a `ProofMessage` event, exits); a small shared `proof_proto` CMake library so the already-generated `proof.pb.cc`/`.h` (from FT-008) is compiled once and linked by both `proof_schema` and `transport_proof`, with `cxx_std_17` set as a `PUBLIC` requirement on that library so any future target linking it automatically matches `libprotobuf`'s own build standard (per `.claude/memory/protobuf-generated-code-cxx-standard-abi.md` — prevents TK-009's exact bug from recurring by construction rather than by convention); `src/backend/core/tests/test_transport_proof.py` (an `asyncio` TCP server: generates the secret, listens on an OS-assigned port, spawns the built `transport_proof` executable, validates the secret, sends the command, receives and asserts the event); a new `check-transport` Makefile target run after `check-native` (so the native executable is guaranteed built first) via a dedicated pytest marker, since this test cannot run as part of `check-python` (which runs before native is built).

Out of scope: Tauri sidecar process spawning (a separate, later EP-004 Feature — this proof spawns the native executable directly from Python, matching ADR-002's "Python core... owns the Native Audio Runtime process's lifecycle," independent of whatever spawns Python itself); the explicit shutdown protocol ADR-006's Consequences calls for (Tauri-specific, unrelated to this Python↔native proof); any real product command/event content or persistent/reconnecting transport behavior; changes to `src/schemas/proof.proto` (reused exactly as FT-008 left it).

## Acceptance criteria

`transport_proof` builds via `check-native` and, given a port and secret as `argv[1]`/`argv[2]`, connects to that port, sends the secret as its first message, decodes the next message it receives as a `ProofMessage`, and sends back a `ProofMessage` event before exiting 0. `test_transport_proof.py` drives a full round trip against the real built executable (not a mock) and passes. `make check-transport` (Python spawning the real native binary) passes locally, sequenced after `check-native` in `make check`. `proof_schema` continues to pass unchanged. RSK-002 does not need reopening — this is new work, not a fix to it — but any real cross-platform issue discovered is tracked the same way TK-009's were: honestly, with a real reopening if closed prematurely.

## Notes

TDD: the Python test is written against the not-yet-built `transport_proof` executable and the not-yet-implemented server logic, so it fails first (executable not found / connection refused), then is made to pass by implementing both sides — mirrors TK-009's own precedent for a cross-language proof where "test-first" means proving the absence of the capability before building it, not testing pre-existing behavior.

**Verified:** the exact wire format was read directly from JUCE's own `juce_InterprocessConnection.cpp` (`InterprocessConnection::sendMessage`/`readNextMessage`) rather than assumed: an 8-byte header — a `uint32` magic number then a `uint32` payload length, both passed through `ByteOrder::swapIfBigEndian` (a no-op on the little-endian platforms `check.yml` actually runs, i.e. plain little-endian on the wire) — followed by that many payload bytes; `test_transport_proof.py` replicates this exactly with `struct.pack("<II", ...)`. Both sides use a project-specific magic number (`0x636f7274`) rather than JUCE's own default, matching the API's own guidance that sender/receiver must agree on one. `proof_proto` (a new small static library compiling the already-generated `proof.pb.cc` once) sets `cxx_std_17` as a `PUBLIC` requirement, so `transport_proof` inherits it automatically — chosen deliberately over repeating an explicit `cxx_std_17` on each target, so a future target linking `proof_proto` cannot reintroduce TK-009's exact ABI bug by simply forgetting to set it. `transport_proof.cpp` uses `callbacksOnMessageThread=false` (no JUCE `MessageManager` pump is running, matching `toolchain_proof.cpp`'s existing headless-safe precedent) and a `std::condition_variable` to hand the round-trip result from the IPC background thread back to `main()`, with a 5-second timeout so a real bug can't hang the test suite forever. Built cleanly on the first attempt with zero warnings on `transport_proof.cpp` itself (confirmed by grepping the build log for the file specifically). A genuinely clean local build (`rm -rf build`, `rm -rf generated`) ran the real round trip successfully: Python spawns the actual built `transport_proof` binary (not a mock), the secret is sent and validated, a real `ProofMessage` command crosses the socket, `messageReceived` decodes it and sends back a real `ProofMessage` event, Python decodes and asserts it. `make check-transport` passes on its own; a full clean `make check` (Python, frontend, desktop, native, transport) passes end to end, confirming `check-python`'s new `-m "not transport"` filter correctly excludes this test from the too-early run (native isn't built yet at that point) while `check-transport` (sequenced after `check-native`) picks it up.

**Unverified from this session** (`CLAUDE.md` §10 — cannot push): real Windows CI. Python's `asyncio.create_subprocess_exec` needs the Proactor event loop for subprocess support on Windows — this has been the default since Python 3.8, well below this project's `>=3.14.2` floor, so no extra configuration should be needed, but this is reasoned from Python's own documented default, not observed running on Windows from this machine. JUCE's `InterprocessConnection`/`Thread` machinery is already proven cross-platform by `toolchain_proof` (unrelated to this Task, but the same underlying `juce_events`/`juce_core` code paths), which raises confidence but is not the same as observing this exact new executable run. RSK-003 tracks this explicitly rather than assuming it's fine given the CRT/ABI precedent set by TK-009.
