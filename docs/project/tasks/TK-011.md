# TK-011 — Spawn, Communicate With, and Cleanly Shut Down a Sidecar Process from Tauri

Status: active
Feature: FT-010

## Objective

Add `tauri-plugin-shell` to the Tauri shell, spawn a minimal Python script as a managed child process from Rust, and prove — via an automated `cargo test`, not manual observation — that an explicit stdin-based shutdown message cleanly terminates it.

## Scope / Out of scope

In scope: `tauri-plugin-shell` added to `src/frontend/desktop/src-tauri/Cargo.toml` and registered via `.plugin(tauri_plugin_shell::init())` in `lib.rs`; `src/backend/core/sidecar_proof.py` (prints `READY` on startup, then blocks reading stdin lines until it sees `SHUTDOWN`, then exits 0); a `#[test]` in `lib.rs` that spawns it via `Shell::command()` (invoking `uv run --directory <path-to-core> python sidecar_proof.py`, keeping the sidecar's own dependency environment managed by `uv` exactly as the rest of the Python core is), reads the `CommandEvent` stream for the `READY` stdout line, writes `SHUTDOWN\n` to the child's stdin, and asserts a `CommandEvent::Terminated` event arrives with exit code 0; `check-desktop`'s Makefile recipe updated to run `cargo test` (in `src-tauri/`) alongside the existing `npm run tauri build`.

Out of scope (see FT-010's Notes for why): `Shell::sidecar()`/`externalBin` bundling and any frozen-executable packaging (PyInstaller/Nuitka or similar) — deferred to Beta per `docs/project/plan.md`; spawning the actual Native Audio Runtime (no real runtime executable exists yet, only toolchain proofs); any frontend/JS-side shell plugin usage, IPC command invocation, or `capabilities/*.json` changes (unnecessary — confirmed by reading `tauri-plugin-shell`'s source that its ACL scope checks apply only to the JS-invoked command handlers, not the Rust `Shell` API this Task calls directly); any real product process-lifecycle policy (restart-on-crash, health checks, multiple sidecars) — this proves one spawn/communicate/shutdown cycle only.

## Acceptance criteria

`cargo test` (run from `src/frontend/desktop/src-tauri/`) passes a test that spawns the real `sidecar_proof.py` process (not a mock), observes its `READY` signal, sends `SHUTDOWN`, and confirms clean exit (code 0) via a real `CommandEvent::Terminated` event — the whole round trip genuinely exercised, not reasoned through. `make check-desktop` runs this test as part of its normal recipe. No capability/permission JSON files are touched. `sidecar_proof.py` passes `ruff check`/`ruff format --check` (already covered by `check-python`'s whole-directory invocation, even though it isn't under `tests/` and so isn't in Pyright's current `include`).

## Reopened by real Windows CI evidence — STATUS_ENTRYPOINT_NOT_FOUND (2026-09-01, later same day)

The user pushed `5acff08` and ran it on real CI. Confirmed independently via `gh run view`/`gh api` (run `33501836929`): macOS passed; Windows failed, but **not inside the test** — `npm run tauri build` (including the MSI/NSIS bundles) completed successfully immediately beforehand, then `cargo test` finished compiling ("`Finished 'test' profile ... in 5m 03s`") and the produced harness executable failed to even start, 0.06s later: `process didn't exit successfully: ...app_lib-8536336b3aa50ae0.exe (exit code: 0xc0000139, STATUS_ENTRYPOINT_NOT_FOUND)`. `STATUS_ENTRYPOINT_NOT_FOUND` means the OS loader found every required DLL but a specific *exported function* one of them was expected to provide doesn't exist in the version actually present — a fundamentally different failure class from a missing-DLL or missing-`PATH`-entry error, and not something inside `sidecar_shuts_down_via_explicit_protocol` itself, since the harness never got that far.

**Diagnosis, grounded in real upstream evidence, not guessed:** `cargo tree --target x86_64-pc-windows-msvc` (comparing the plain dependency graph against one including `[dev-dependencies]`) showed almost no delta — one proc-macro crate (`tokio-macros`, compile-time only, no runtime DLL implications) — ruling out "a new test-only dependency pulls in an incompatible Windows API" as the mechanism; the crate graph reaching the linker is essentially identical between the release binary and the test harness. `WebSearch`/`WebFetch` against `tauri-apps/tauri`'s own issue tracker found this exact symptom is a known, reproducible upstream Tauri limitation (issues #11028, #13419, #13948, #13954), not something specific to this project's code. A Tauri co-maintainer's (amrbashir) own explanation, and — more authoritatively — Tauri's own real, currently-shipping `examples/api/src-tauri/build.rs` (fetched directly via `gh api` from `tauri-apps/tauri`, not paraphrased) confirmed the actual mechanism: `tauri-build`'s automatic Windows application-manifest embedding (which declares a dependency on `Microsoft.Windows.Common-Controls` 6.0.0.0 — confirmed by fetching the real, shipped `crates/tauri-build/src/windows-app-manifest.xml`) is applied per-`[[bin]]`-target only. Cargo's auto-generated unit-test harness for a `[lib]` target (`app_lib-<hash>.exe`) is not a declared `[[bin]]`, so it never receives that manifest. Without it, Windows' SxS activation context loads the legacy COMCTL32 v5 instead of v6; some Tauri-internal Windows UI code path that `tauri::test::mock_builder()` still links in (even though no window is ever created) references a v6-only export, and the loader rejects the whole executable before any code — including test code — runs. This exactly explains every piece of the evidence: the release binary is fine (its `[[bin]]` gets the manifest normally), the failure is specific to the debug test executable (the only artifact that's a library-crate test harness rather than a declared bin), and the test harness never starts (a loader-time failure, before `main` or any test function runs).

**Fix, matching Tauri's own proven pattern exactly rather than inventing a new one:** `build.rs` now calls `tauri_build::try_build(Attributes::new().windows_attributes(WindowsAttributes::new_without_app_manifest()))` (opting out of `tauri-build`'s own bin-scoped default manifest entirely, verified via `docs.rs` to be the exact, real API surface of the pinned `tauri-build 2.6.3`) and, only on `#[cfg(windows)]` with `CARGO_CFG_TARGET_ENV == "msvc"`, embeds the same manifest content via `cargo:rustc-link-arg=/MANIFEST:EMBED` + `/MANIFESTINPUT:windows-app-manifest.xml` (a *bare*, unscoped linker argument, applied uniformly to every linked artifact from this crate — release binary and test harness alike — deliberately avoiding the "one bin-scoped embed plus one bare embed" combination that a separate real Tauri issue (#10154) reports as a genuine "duplicate resource" linker failure). `windows-app-manifest.xml` is copied verbatim from Tauri's own shipped file (a standard, publicly documented Windows manifest snippet, not project-specific content). This reduces test-only *behavioral* surface rather than adding a workaround bolted onto existing behavior: the release binary and the test harness now go through the exact same, single, uniformly-applied manifest-embedding path instead of two different implicit ones — the "unnecessary test-only runtime surface" the user asked to look for turned out to be a *missing* uniform surface, not an excess one.

**Locally verified as far as this machine allows:** `cargo check --target x86_64-pc-windows-msvc` (cross-target, no linking) succeeds cleanly with the new `build.rs` — this required installing `llvm-rc` (`brew install llvm`) since `tauri-build`'s own icon-resource compilation already needed a Windows resource compiler even before this change, confirming that requirement is pre-existing and unrelated to this fix. Caught and corrected a real blind spot during verification: `#[cfg(windows)]` inside `build.rs` reflects the *host* running the build script, not the `--target` being cross-checked for, so the actual new function was silently compiled out of that first cross-check; re-verified its syntax/type-correctness directly by temporarily lifting the `#[cfg(windows)]` gate and running a native `cargo check` (confirmed clean), then restored the gate. `make check-desktop` and a full clean `make check` (all six targets) still pass on macOS with `new_without_app_manifest()` in place, confirming no regression there — expected, since manifest embedding is meaningless off Windows. What remains genuinely unverifiable without a Windows machine: whether `/MANIFEST:EMBED` actually resolves the `STATUS_ENTRYPOINT_NOT_FOUND` for real, whether `/WX` (linker-warnings-as-errors, kept because it's part of Tauri's own proven pattern, presumably to surface exactly this kind of conflict loudly rather than silently) introduces any unrelated warning-turned-error on the real Windows/MSVC toolchain, and whether the bare (non-bin-scoped) `rustc-link-arg` genuinely reaches the `app_lib` test-harness link step the way Cargo's documentation describes.

FT-010/TK-011 stay `active`; `RSK-004` stays `monitoring`, updated with this specific finding rather than closed on local reasoning alone.
