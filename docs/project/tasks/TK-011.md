# TK-011 — Spawn, Communicate With, and Cleanly Shut Down a Sidecar Process from Tauri

Status: active
Feature: FT-010

## Objective

Add `tauri-plugin-shell` to the Tauri shell, spawn a minimal Python script as a managed child process from Rust, and prove — via an automated `cargo test`, not manual observation — that an explicit stdin-based shutdown message cleanly terminates it.

## Scope / Out of scope

In scope: `tauri-plugin-shell` added to `src/frontend/desktop/src-tauri/Cargo.toml` and registered via `.plugin(tauri_plugin_shell::init())` in `lib.rs`; `src/backend/core/sidecar_proof.py` (prints `READY` on startup, then blocks reading stdin lines until it sees `SHUTDOWN`, then exits 0); a `#[test]` in `lib.rs` that spawns it via `Shell::command()` (invoking `uv run --directory <path-to-core> python sidecar_proof.py`, keeping the sidecar's own dependency environment managed by `uv` exactly as the rest of the Python core is), reads the `CommandEvent` stream for the `READY` stdout line, writes `SHUTDOWN\n` to the child's stdin, and asserts a `CommandEvent::Terminated` event arrives with exit code 0; `check-desktop`'s Makefile recipe updated to run `cargo test` (in `src-tauri/`) alongside the existing `npm run tauri build`.

Out of scope (see FT-010's Notes for why): `Shell::sidecar()`/`externalBin` bundling and any frozen-executable packaging (PyInstaller/Nuitka or similar) — deferred to Beta per `docs/project/plan.md`; spawning the actual Native Audio Runtime (no real runtime executable exists yet, only toolchain proofs); any frontend/JS-side shell plugin usage, IPC command invocation, or `capabilities/*.json` changes (unnecessary — confirmed by reading `tauri-plugin-shell`'s source that its ACL scope checks apply only to the JS-invoked command handlers, not the Rust `Shell` API this Task calls directly); any real product process-lifecycle policy (restart-on-crash, health checks, multiple sidecars) — this proves one spawn/communicate/shutdown cycle only.

## Acceptance criteria

`cargo test` (run from `src/frontend/desktop/src-tauri/`) passes a test that spawns the real `sidecar_proof.py` process (not a mock), observes its `READY` signal, sends `SHUTDOWN`, and confirms clean exit (code 0) via a real `CommandEvent::Terminated` event — the whole round trip genuinely exercised, not reasoned through. `make check-desktop` runs this test as part of its normal recipe. No capability/permission JSON files are touched. `sidecar_proof.py` passes `ruff check`/`ruff format --check` (already covered by `check-python`'s whole-directory invocation, even though it isn't under `tests/` and so isn't in Pyright's current `include`).

## Notes

TDD: the test is written against the not-yet-added plugin/not-yet-written script, so it fails to compile/run first (missing crate, missing file), then made to pass — mirrors FT-008/FT-009's precedent for toolchain-proof Tasks.

**Verified:** `tauri-plugin-shell` and `tauri`'s own real source were read directly (via a throwaway scratch `cargo` project fetching the exact pinned versions, not guessed or taken from documentation) before writing any code — confirmed `Shell::command()`/`CommandChild::write()`/`kill()`, that `tauri::test::mock_builder()` genuinely spawns real child processes (the shell plugin's process handling is runtime-agnostic, wrapping plain `std::process::Command`; only the windowing/webview layer is mocked), and confirmed by reading the ACL/scope-checking code in `commands.rs` that direct Rust calls to `Shell::command()` bypass the JS-invoke capability system entirely — no `capabilities/*.json` change was needed, and none was made. First real run hit a genuine, informative compile error (`tauri::test` requires the crate's own `test` feature — not implied by the crate being a test target of the CONSUMING crate); fixed by adding `tauri = { version = "2.11.3", features = ["test"] }` under `[dev-dependencies]` so production builds are unaffected. Second real run then hit a genuine logic bug caught by the test itself doing exactly its job: comparing `CommandEvent::Stdout(line)` against `b"READY"` failed silently and hung until timeout, because `tauri-utils`' own `read_line` (read directly, not assumed) includes the delimiter byte in the returned buffer — fixed by trimming (`String::from_utf8_lossy(&line).trim() == "READY"`), which also makes the comparison robust to Windows CRLF translation on `print()`'s output, not just macOS's bare `\n`. `cargo test` passed reliably across three consecutive runs with zero warnings on the new code (`cargo build --tests` warning-scan came back empty). `make check-desktop` (the real release build plus this test) and a full clean `make check` (all six targets, `rm -rf` on both native build and Python `generated/` first) passed end to end.

**Unverified from this session** (`CLAUDE.md` §10 — cannot push): real Windows CI. The specific risk worth naming: Windows' text-mode stdout CRLF translation is exactly why the `.trim()` fix (not a bare `\n` strip) was chosen, but that reasoning is unconfirmed by an actual Windows run; `Command::new("uv")` resolving via inherited `PATH` should work identically to how `check.yml`'s own Windows job already relies on `uv`/`cargo` being on `PATH` for every other step, but this is this session's first time spawning a process *from within a Rust test* rather than from the shell directly.
