# TK-013 — Implement Tracktion Edit Materialization and Offline Render

Status: done
Feature: FT-012
Milestone: MS-002

## Objective

Implement `src/backend/audio/materializer.h`/`.cpp` (a plain `ProjectSpec` → real Tracktion `Edit` → offline render pipeline, no protobuf involved) and `src/backend/audio/materializer_proof.cpp` (a ctest exercising it against a real headless `Engine`).

## Scope / Out of scope

In scope: `materializer.h` declaring `ClipSpec`/`TrackSpec`/`ProjectSpec`/`RenderResult` (plain structs: strings, doubles, `uint64_t` — no protobuf, no JUCE/Tracktion types in the public data shapes beyond what `materialize()`'s own signature needs) and `RenderResult materialize (tracktion::Engine&, const ProjectSpec&, const juce::File& outputDirectory)`; `materializer.cpp` implementing it: `Edit::createSingleTrackEdit(engine, Edit::EditRole::forRendering)`, a deterministic sine-wave fixture generator (`juce::WavAudioFormat`/`AudioFormatWriter`, pure math, no RNG, frequency/sample-rate as fixed internal constants — not exposed on `ClipSpec`), `insertWaveClip` onto the Edit's one `AudioTrack`, `Renderer::Parameters` (`destFile`, `time`, `audioFormat = engine.getAudioFileFormatManager().getWavFormat()`) plus `EditRenderer::render` waited on via a `std::condition_variable` (no message-loop pumping needed — confirmed by reading `tracktion_Renderer.cpp` directly: the render-graph-building `callBlocking` call happens synchronously on the calling thread before the background render thread is even spawned, and the completion callback fires directly from that background thread, not via the message loop), then reading the rendered file back (`AudioFormatReader::readMaxLevels`) for sample count and peak amplitude; `materializer_proof.cpp` (its own local `Engine`/`UIBehaviour`/`PropertyStorage`/`EngineBehaviour` stub set, mirroring `toolchain_proof.cpp`'s existing pattern exactly rather than extracting a shared helper for a second call site — see Notes) constructing a headless `Engine` with `EngineBehaviour::getNumberOfCPUsToUseForAudio()` overridden to return `1` (forcing single-threaded, deterministic graph execution — a real, source-confirmed non-determinism risk otherwise, not a hypothetical one), calling `materialize()` twice with identical input, and asserting both succeed with matching sample count/peak amplitude and the expected duration; `src/backend/audio/CMakeLists.txt` updated with a `materializer` library (linking Tracktion/JUCE targets, `cxx_std_20` — matching `toolchain_proof`'s established requirement) and `materializer_proof` executable/ctest.

Out of scope: anything protobuf-related (`project.proto`, `MaterializeProjectCommand`/`ProjectRenderedEvent`) — deliberately not linked or included here at all; any socket/process/transport code; the real Python entry point; more than one track or clip; real user-imported audio (the fixture is synthetic, generated internally by `materialize()`).

## Acceptance criteria

`materializer_proof` builds and passes as a ctest: two independent calls to `materialize()` with an identical one-track/one-clip `ProjectSpec` each succeed, each produces a WAV file with sample count within rounding of `duration_seconds * 44100`, each has a peak amplitude consistent with genuine sine content (not near-zero, not clipped/invalid), and the two calls' sample counts and peak amplitudes match each other exactly. No message-loop pumping is required anywhere in the implementation (confirmed against real Tracktion Engine source, not assumed). `make check-native` passes locally end to end alongside the existing `toolchain_proof`/`proof_schema`/`project_schema` targets, with zero new warnings on `materializer.cpp`/`materializer_proof.cpp` themselves.

None.

## Notes

TDD, adapted for native code with no existing unit-test framework here: `materializer_proof.cpp` is written against the not-yet-implemented `materialize()`, confirmed failing to compile (a real, informative error — `getNumberOfCPUsToUseForAudio` overriding a non-`const` virtual with a `const` signature, `tracktion_EngineBehaviour.h:128` is not `const`), then made to pass by fixing the signature and implementing `materializer.cpp` — mirrors `transport_proof`/`sidecar_proof`'s own precedent for proof-style Tasks in this native tree.

`materializer_proof.cpp`'s headless `Engine`/`UIBehaviour`/`PropertyStorage`/`EngineBehaviour` stubs duplicate `toolchain_proof.cpp`'s existing ones almost verbatim. Deliberately not extracted into a shared header this Task: `CLAUDE.md` §8 prefers temporary local duplication over a premature shared abstraction, and this is only the second call site — `toolchain_proof.cpp` is an already-closed, unrelated Task's file, and touching it here would be scope creep for a cosmetic dedup it doesn't need. If FT-013's `native_runtime.cpp` needs a third, genuinely identical copy, that is the point real reuse is demonstrated and extraction becomes justified — flagged here so it isn't silently inconsistent.

**A real, informative surprise, caught by running against reality rather than trusting analysis:** the References section's claim that no message-loop pumping is needed (reasoned from `EditRenderer::render`'s `.cpp`, where `callBlocking`'s graph-construction call happens synchronously before the background render thread is spawned) was directly tested and found wrong — the first real run hung indefinitely with the render callback never firing. Diagnosed by instrumenting `materialize()` with temporary `std::cerr` checkpoints (removed once fixed) rather than guessing further: the render task's background thread genuinely blocks on something needing the message thread to be actively pumping (observed directly: a lazy MIDI-input-device scan — unrelated to `autoInitialiseDeviceManager()`, which only gates the *audio* device manager — ran to completion only once dispatch-loop pumping started). Fixed by replicating `Renderer.test.cpp`'s own real pattern exactly (`test_utilities::runDispatchLoopUntilTrue`, reimplemented locally rather than depending on that test-only header): a polling loop calling `juce::MessageManager::getInstance()->runDispatchLoopUntil (10)` until an `std::atomic<bool>` completion flag is set or a 10-second deadline passes, replacing the originally-planned plain `condition_variable` wait. This is the concrete lesson: the vendored test's own use of dispatch-loop pumping was real, load-bearing behavior to copy exactly, not an artifact of that test's own setup to reason past.

Also fixed during implementation, before any real bug surfaced from it: fixture files were originally written via `juce::File::createTempFile` (the raw OS temp directory, outside Tracktion's own temp-file lifecycle) — changed to `engine.getTemporaryFileManager().getTempFile (juce::Uuid().toString() + ".wav")` so generated fixtures live in and are cleaned up by the same temp-file management Tracktion Engine already owns and was observed logging cleanup for (`"Cleaning up temp files.."` at shutdown), rather than leaking into the system temp directory across runs.

**Verified locally:** `materializer_proof` (ctest) calls `materialize()` twice with an identical one-track/one-clip `ProjectSpec` (2.0s duration); both succeed, each render's sample count is within rounding of `2.0 * 44100`, each peak amplitude exceeds `0.5` (consistent with genuine full-scale sine content, not silence or noise), and the two calls' sample counts and peak amplitudes match each other exactly — with single-threaded rendering forced via `EngineBehaviour::getNumberOfCPUsToUseForAudio() = 1`. A full clean `make check-native` (all five native targets: `toolchain_proof`, `proof_schema`, `project_schema`, `materializer_proof`, plus the pre-existing `transport_proof`) passes end to end with zero new warnings on `materializer.cpp`/`materializer_proof.cpp` themselves — the one warning present (`Ditherer.h`'s `RAND_MAX` implicit conversion) is pre-existing vendored third-party noise already in `.claude/memory/native-build-third-party-warnings.md`.
