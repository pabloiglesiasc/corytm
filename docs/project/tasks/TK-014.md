# TK-014 — Implement the Real Entry Point, Native Wire Adapter, and End-to-End Round Trip

Status: active
Feature: FT-013
Milestone: MS-002

## Objective

Implement `src/backend/audio/wire_codec.h`/`.cpp`, `src/backend/audio/native_runtime.cpp`, `src/backend/core/modules/runtime/session.py`, and `src/backend/core/main.py`; prove the whole round trip with a new automated cross-language test.

## Scope / Out of scope

In scope: `src/backend/audio/wire_codec.h` declaring `decodeMaterializeCommand(const std::vector<std::byte>&) -> ProjectSpec` and `encodeRenderedEvent(const std::string& projectId, const RenderResult&) -> std::vector<std::byte>` using only `project_spec.h`'s plain types (no protobuf, no Tracktion/JUCE in this header); `wire_codec.cpp` implementing both using `project.pb.h` (TK-012), compiled `PRIVATE cxx_std_17` (matching `project_proto` — this is the translation-unit boundary that keeps protobuf-touching code and Tracktion-touching code from ever coexisting in one TU, preventing TK-009's ABI bug by construction); `src/backend/audio/native_runtime.cpp` (`main(argc, argv)`: `<port> <secret> <output_directory>` — a headless `Engine` mirroring `materializer_proof.cpp`'s stub set, a `juce::InterprocessConnection` mirroring `transport_proof.cpp`'s `callbacksOnMessageThread=false`/secret-on-connect/mutex+condvar pattern exactly for receiving raw command bytes, then — back on `main()`'s own thread, which is the real JUCE message thread, not the connection's reader thread, because `materialize()` needs message-loop pumping (TK-013's finding) — decodes the command via `wire_codec`, calls `materialize()`, encodes the event via `wire_codec`, and sends it back); `src/backend/audio/CMakeLists.txt` updated with a `wire_codec` library and `native_runtime` executable; `src/backend/core/modules/runtime/session.py` (`materialize_project(project, output_directory) -> ProjectRenderedEvent`, an `asyncio` function spawning `native_runtime`, doing the secret handshake via `runtime.transport`, sending `runtime.projection.to_materialize_command(project)`, and returning the decoded event — real production code, not test-only); `src/backend/core/main.py` (constructs the one-track/one-clip `Project`, calls `session.materialize_project`, prints the result); a new `tests/test_first_sound.py` cross-language test (marked `transport`, run via `check-transport`) that calls `session.materialize_project` against the real built `native_runtime` binary and asserts on the returned event.

Out of scope: any change to `materializer.h`/`.cpp` (FT-012, reused unchanged) or `project.proto`/`projection.py`/`transport.py` (FT-011, reused unchanged); a live-audio-device playback code path (see FT-013's Notes — the rendered WAV file is sufficient for the human audible check); any Tauri/sidecar-shutdown-protocol involvement (that is TK-011/FT-010's already-proven, unrelated concern — this Task's native process is spawned directly by Python per ADR-002, exactly as FT-009/TK-010 already established, and exits on its own after one round trip rather than needing an explicit shutdown message).

## Acceptance criteria

`wire_codec`'s round trip (`ProjectSpec` → command bytes → back, and `RenderResult` → event bytes → decoded `ProjectRenderedEvent`) is correct. `native_runtime` connects, authenticates with the secret, receives a real `MaterializeProjectCommand`, materializes and renders it via the unchanged `materialize()`, and sends back a real `ProjectRenderedEvent` with a genuine, playable output file. `session.materialize_project` and `main.py` both work against the real built `native_runtime` binary — `test_first_sound.py` proves this automatically and passes locally (`make check-transport`), and `main.py` run directly by a human produces a real WAV file reported by path. `make check` passes locally end to end (all targets, including the new native ones). No warnings on any new file.

## Notes

TDD: each piece was proven failing before it existed — `wire_codec`/`native_runtime` failed to build without their implementations (a real, informative compile error: `const juce::File outputDirectory (juce::String (argv[3]));` was parsed by the compiler as a function declaration, not a variable — C++'s "most vexing parse" — fixed with brace-initialization), and `test_first_sound.py` was written against the not-yet-existing `session.materialize_project`/`native_runtime` binary. The end-to-end integration test itself passed on its first real run once both sides existed — expected, since every piece it exercises (schema/projection, transport framing, `materialize()`) was already independently proven in TK-012/TK-013; integration failures at this layer would only be expected from a wiring mistake in this Task's own new glue code, which the individual build/compile errors already caught.

A second real, non-obvious issue caught by a `[[nodiscard]]` warning, not by reasoning ahead of time: `MaterializeProjectCommand::ParseFromArray`'s return value was originally ignored; fixed by checking it and returning a default-constructed (empty) `ProjectSpec` on parse failure, which `materialize()` already handles correctly (empty tracks → early `{false, ...}` return) — a real error path, not just a silenced warning.

`native_runtime.cpp`'s connection design deliberately does *not* run `materialize()` from `messageReceived()`: `messageReceived` fires on the `InterprocessConnection`'s own reader thread (`callbacksOnMessageThread=false`, mirroring `transport_proof.cpp`), but TK-013 established that `materialize()` needs the real JUCE message thread to be actively pumping. `messageReceived` therefore only captures the raw command bytes and signals `main()` (via the same mutex/condvar pattern `transport_proof.cpp` already uses) — `main()` itself, which genuinely is the message thread, then calls `materialize()` directly. Sending the response back via `connection.sendEvent()` from `main()` afterward mirrors `transport_proof.cpp`'s precedent of calling `sendMessage` off the object's own dedicated callback context.

**Verified locally:** `test_first_sound.py` (via `make check-transport`) passes: the real `native_runtime` binary is spawned, authenticates, receives a real `MaterializeProjectCommand` for a 2-second one-clip project, materializes and renders it, and returns a `ProjectRenderedEvent` with `rendered_sample_count == 88200` (exactly `2.0 × 44100`) and `peak_amplitude` consistent with genuine sine content. `main.py`, run directly (`PYTHONPATH=modules:generated uv run python main.py` from `src/backend/core/`, needed because a plain script invocation has no other way to reach the `modules/` package layout pytest's own `pythonpath` setting handles for tests — documented here as the exact human-facing invocation), produced a real, valid RIFF/WAVE file (confirmed via the `file` command) reporting `Rendered 88200 samples ... Peak amplitude: 1.0000`; the file was deleted afterward as a throwaway local artifact, not a repo deliverable, since it is trivially reproducible by that one command. All 16 Python tests pass (`pytest`, both marker groups); `pyright` (strict, including `main.py` now added to `include`) and `ruff check`/`ruff format --check` all pass clean on the whole directory. `wire_codec.cpp` and `native_runtime.cpp` both build with zero warnings of their own (confirmed by a forced clean rebuild of just those two targets and grepping the log for their filenames specifically) — the only warnings anywhere in a full `make check-native` are the pre-existing vendored ones already catalogued in `.claude/memory/native-build-third-party-warnings.md`.

**Human acceptance step — confirmed (2026-09-01):** the user ran `PYTHONPATH=modules:generated uv run python main.py` from `src/backend/core/` on macOS, generated `first-sound.wav`, played it, and audibly confirmed the rendered tone — reported as "unpleasant but clearly audible and stable." This satisfies EP-005/FT-013's distinct human-only audible-evidence acceptance boundary (an automated test can assert sample count/peak amplitude but cannot itself confirm audibility); the tone's unpleasantness is expected and not a defect — `materialize()`'s fixture is a plain 440Hz full-scale (peak-amplitude-1.0) sine tone, an internal proof-of-pipeline detail, not a musical or product concern this slice makes any claim about. This is human acceptance evidence only: it does not by itself move TK-014/FT-013/EP-005 to `done` — real Windows CI confirmation (see the Unverified note below and `RSK-005`/`RSK-006`/`RSK-007`) is still required first, per `CLAUDE.md`'s established practice for this Task family.
