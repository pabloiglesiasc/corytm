# TK-015 — Add `with_clip_moved` and the `MoveClipCommand`/`ClipMovedEvent` Schema

Status: done
Feature: FT-014
Milestone: MS-002

## Objective

Give Corytm Engine its first real edit operation — moving a clip's start position — and the independent wire command/event pair describing that same intention, both proven in isolation from the Native Audio Runtime.

## Scope / Out of scope

In scope: `AudioTrack.with_clip_moved(*, clip_id, new_start_seconds)` and `Project.with_clip_moved(*, track_id, clip_id, new_start_seconds)` on the existing Pydantic domain models (`src/backend/core/src/corytm/engine/{track,project}.py`); `MoveClipCommand`/`ClipMovedEvent` added to `src/schemas/project.proto`; a pure `to_move_clip_command` function in `src/backend/core/src/corytm/runtime/projection.py`; the new messages' round trip proven in `src/backend/audio/tests/project_schema.cpp`; unit tests for all of the above.

Out of scope: wiring this command/event to `native_runtime.cpp`/`materializer`, any change to the native process's single-command-then-exit lifecycle, a Python-side decode helper for `ClipMovedEvent` (nothing consumes it yet), and everything EP-006's own Out of scope already excludes.

## Acceptance criteria

- `AudioTrack.with_clip_moved` returns a new `AudioTrack` with the targeted clip's `start_seconds` updated; the original `AudioTrack` and its other clips are unchanged; an unknown `clip_id` raises `ValueError` naming "clip"; an invalid `new_start_seconds` raises `pydantic.ValidationError` via `AudioClip`'s existing `Field(ge=0)` constraint (not a duplicated check).
- `Project.with_clip_moved` delegates to the targeted `AudioTrack` and returns a new `Project` with only that track changed; an unknown `track_id` raises `ValueError` naming "track"; the same clip-level validation propagates unchanged.
- `project.proto` gains `MoveClipCommand` (`schema_version`, `project_id`, `track_id`, `clip_id`, `new_start_seconds`) and `ClipMovedEvent` (`schema_version`, `project_id`, `track_id`, `clip_id`, `start_seconds`).
- `to_move_clip_command` constructs a `MoveClipCommand` from plain arguments with no I/O and no dependency on a `Project` instance.
- `project_schema` (C++) round-trips both new messages, mirroring the existing `MaterializeProjectCommand`/`ProjectRenderedEvent` assertions in the same file.
- `uv run pytest -m "not transport"`, `pyright`, `ruff check`, `ruff format --check`, the full native ctest suite, and `uv run pytest -m transport` all pass with zero new warnings.

## Notes

Implemented via TDD: failing tests written first for `with_clip_moved` (both levels) and `to_move_clip_command` (confirmed failing via a missing-import collection error), then implemented minimally. `AudioTrack.with_clip_moved` rebuilds the targeted clip through full `AudioClip(...)` construction rather than a raw `model_copy(update=...)` field patch — pydantic v2's `model_copy` does not re-run validation, so a raw patch would have silently admitted a negative start time; full construction was chosen specifically so the existing `Field(ge=0)` constraint keeps applying to edits exactly as it does to construction, with no new invariant duplicated.

Validated beyond this Task's own isolated scope, per `CLAUDE.md` §7's cross-boundary bar (Python domain model + shared Protobuf schema also consumed by the native side): `uv run pytest -m "not transport"` (26 passed), `pyright` (0 errors), `ruff check`/`ruff format --check` (clean, after `ruff check --fix`/`ruff format` resolved one import-ordering and one line-length issue the initial edit introduced), a full native rebuild of all five targets (zero new warnings — confirmed by reading the build log, not assumed) and the full `ctest` suite (4/4 passed, including the extended `project_schema`), and `uv run pytest -m transport` (3 passed — `test_transport_proof`, `test_first_sound`, `test_entrypoint`, none of which this Task's own scope touches, re-run specifically to confirm the shared schema/generated-bindings change didn't regress EP-005's already-closed round trip). Not yet independently confirmed on real Windows CI — this session cannot push (`CLAUDE.md` §10); the new C++ messages reuse `project_proto`'s exact existing CMake shape (same custom-command/`PUBLIC cxx_std_17` pattern RSK-005 already closed for this shape of nested/nested-adjacent generated code), so no new build-toolchain risk is expected, but per this project's own established practice (RSK-005/006/007), that expectation is not treated as proof without a real passing Windows Actions run.

No new ADR: this is routine implementation inside ADR-001/ADR-007/ADR-008's already-accepted shapes, not a new architecturally-significant or hard-to-reverse choice.
