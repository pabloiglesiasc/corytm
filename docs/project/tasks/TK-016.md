# TK-016 — Diagnose Windows Sccache Routing and Native Target-Graph Duplication

Status: done
Feature: FT-015

## Objective

Using real GitHub Actions evidence (not the reported summary alone), diagnose why the Windows `check` job shows zero sccache compiler-cache activity for both native MSVC C/C++ and Cargo/Rust despite the prior optimization's configuration, and why the same Tracktion/JUCE translation units are compiled once per native target instead of once total — then apply whatever fix is genuinely safe and evidence-justified for each, in that order (Windows sccache first, then the native target graph).

## Scope / Out of scope

In scope:
- Independently pulling and reading the actual downloaded logs of the latest real `check` run (both `check (macos-latest)` and `check (windows-latest)` jobs) via `gh run view`/`gh api`, to confirm or correct every reported observation before designing a fix.

- `src/backend/audio/CMakeLists.txt`: consolidating genuinely identical Tracktion/JUCE compilation requirements shared by `toolchain_proof`, `materializer`, `materializer_proof`, and `native_runtime` into one shared library those four targets link, if and only if their actual compile definitions/C++ standard/linkage requirements are confirmed identical — leaving `transport_proof`/`proof_schema`/`project_schema` untouched.

### Investigation 1 — Windows sccache

**MSVC C/C++ (conclusively diagnosed, structural, not expected to recur):** CMake's Visual Studio (MSBuild) generator has never wired `CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER` into the generated `.vcxproj` files — only the Makefile and Ninja generators do (tracked upstream at CMake's own `gitlab.kitware.com/cmake/cmake` issue #19326). This is reproduced identically, symptom-for-symptom (all-zero `sccache --show-stats` after a successful MSVC build via the VS generator with the exact same `-DCMAKE_C_COMPILER_LAUNCHER=sccache` flags), in two independent `mozilla/sccache` bug reports (issues #957 "How does this work with CMake & MSVC, without Ninja?" and #1097 "no compiles were run via sccache in windows using cmake" — both still open). The idiomatic MSBuild-generator workaround the wider ccache/clcache community uses (`CMAKE_VS_GLOBALS` with `CLToolExe`/`CLToolPath` pointing at a copy of the cache tool renamed to `cl.exe`, requiring CMP0141=NEW and `UseMultiToolTask=true`) does **not** transfer to sccache: `mozilla/sccache` issue #1063 (still open) shows sccache explicitly erroring `cannot find binary path` when invoked this way, because — unlike ccache/clcache — sccache has no mode to auto-detect the real compiler when invoked without one as an explicit argument. Conclusion: there is currently no configuration that routes MSVC C/C++ compilation through sccache while keeping the Visual Studio generator (which is preserved per `.claude/memory/cmake-windows-generator.md`'s established precedent). Independently, the workflow's `-DCMAKE_POLICY_CMP0141=NEW` was already a no-op for an unrelated reason — the CI log itself shows `CMake Warning (unused-cli): ... CMAKE_POLICY_CMP0141` — because CMake's real variable is `CMAKE_POLICY_DEFAULT_CMP0141` (confirmed against CMake's own CMP0141 policy docs); this typo was copied verbatim from `mozilla/sccache`'s own README, which carries the identical mistake. Fix applied: the dead `-DCMAKE_C_COMPILER_LAUNCHER`/`-DCMAKE_CXX_COMPILER_LAUNCHER`/`-DCMAKE_MSVC_DEBUG_INFORMATION_FORMAT`/`-DCMAKE_POLICY_CMP0141` flags were removed from Windows's `CMAKE_CONFIGURE_FLAGS` in `check.yml` (macOS's flags, which the Makefile generator genuinely honors, are unchanged) rather than left silently ineffective.

**Cargo/Rust (genuinely unresolved from static evidence):** `RUSTC_WRAPPER=sccache` is confirmed present in the `Run make check` step's own environment (directly visible in the log's per-step env dump); `mozilla-actions/sccache-action`'s `core.addPath()` call (read directly from its `src/setup.ts` at the pinned `v0.0.11` tag) is cross-platform-identical, so PATH exposure is not an evident asymmetry between platforms; hundreds of real `rustc` invocations occurred via two independently-verified call paths — `npm run tauri build`'s internal cargo invocation (starting 22:09:44) and a separate, direct `cd src-tauri && cargo test` invocation with no tooling in between (starting 22:12:50, itself recompiling the identical dependency crates the release build had just compiled, since the two use different Cargo profiles/`target/` subdirectories) — and both ended in the same all-zero final stats. This rules out a tauri-cli-specific environment-sanitizing explanation, but no conclusive root cause could be established from log text alone; sccache's own architecture (`docs/Architecture.md`) shows the CLI process talking to a long-lived daemon over local IPC (confirmed locally: sccache 0.17.0 listens on a loopback TCP address, not a Windows-specific named pipe, which argues somewhat against an OS-specific IPC mechanism being the cause), and a coherent, evidence-consistent (though unconfirmed) hypothesis is a race between many near-simultaneous first-use client processes (Cargo's own build parallelism) all trying to start that daemon, with only Windows silently losing that race for every subsequent client rather than reconnecting. Applied: an explicit `sccache --start-server` step right after `mozilla-actions/sccache-action` (serializing daemon startup before any parallel compile wave begins — verified locally, `sccache --start-server` exits 0 and the server reports itself listening) and `SCCACHE_LOG=sccache=debug` / `SCCACHE_ERROR_LOG` (both confirmed as the exact, current sccache `Configuration.md` variable names) so the next real Windows run's own log settles this conclusively instead of leaving it speculative. This remains open — see `RSK-008`.

### Investigation 2 — native CMake target-graph audit

Empirically confirmed (not assumed) via both platforms' actual build logs: `toolchain_proof`, `materializer`, `materializer_proof`, and `native_runtime` each get their own independently-compiled copy of the same Tracktion/JUCE translation units. The Windows MSBuild log shows `tracktion_core.cpp`/`tracktion_graph.cpp`/every `tracktion_engine_*.cpp`/every linked JUCE module `.cpp`/`.mm` compiled 8–9 times each; the macOS Makefile-generator log shows the mechanism directly via each object's own path — e.g. `CMakeFiles/toolchain_proof.dir/_deps/.../tracktion_core.cpp.o`, `CMakeFiles/materializer.dir/_deps/.../tracktion_core.cpp.o`, `CMakeFiles/materializer_proof.dir/...`, `CMakeFiles/native_runtime.dir/...` — one real, separate compile per target, not a shared/reused static library. All four targets that touch Tracktion/JUCE declare the identical three compile-definitions (`JUCE_USE_CURL=0`, `JUCE_WEB_BROWSER=0`, `JUCE_MODAL_LOOPS_PERMITTED=1`), so the precondition that would make consolidation unsafe (divergent per-target JUCE configuration) does not hold in this repository.

A consolidation was genuinely attempted and locally validated, not just reasoned about: a new `tracktion_runtime` static library was introduced, bundling `tracktion::tracktion_core`/`tracktion_engine`/`tracktion_graph`/`juce::juce_audio_devices`/`juce::juce_audio_utils` `PUBLIC`, with `toolchain_proof`/`materializer` linking it instead of the raw JUCE/Tracktion targets. A full local clean rebuild (reusing the already-fetched `_deps` tree, `cmake --build ... -- -j 4`, exit 0) showed this made the duplication **worse, not better**: `tracktion_runtime` itself compiled a genuinely-shared copy, but `toolchain_proof`, `materializer`, `materializer_proof`, and `native_runtime` each *still* independently compiled their own copies on top of it — a fifth, wasted compile added to the original four. Root cause, confirmed by CMake's own transitive-usage-requirement propagation model: JUCE's module targets set their own `INTERFACE_SOURCES`, which CMake forwards to *every* real (non-`INTERFACE`) target anywhere in a `PUBLIC`-linked dependency chain that gets built — not just the first library that links them — so wrapping them in another real static library does not stop the propagation. The only way to stop it (linking the JUCE/Tracktion targets `PRIVATE` inside the wrapper) would also silently stop forwarding the include directories, compile definitions, and OS-framework link requirements (e.g. CoreAudio/CoreMIDI on macOS, WinMM/DirectSound on Windows) that each consumer's own translation units still need — manually re-exporting everything except `INTERFACE_SOURCES` via `$<TARGET_PROPERTY:...>` generator expressions is the only theoretical workaround, and is exactly the kind of fragile, easy-to-silently-break-on-one-platform complexity `CLAUDE.md` §8 and this Task's own acceptance criteria warn against for a build-time optimization whose benefit is largely already absorbed by a working sccache (as macOS's 94% C/C++ hit rate shows). **Rejected**, and reverted to the original `CMakeLists.txt` (confirmed via `git diff` — zero net change); the reverted structure was rebuilt clean and re-validated (`ctest`: 4/4 passed, `toolchain_proof` 2.01s, `proof_schema` 0.59s, `project_schema` 0.61s, `materializer_proof` 3.26s).

This duplication is real, uncached wall-clock cost on Windows specifically (no working C/C++ cache there, per Investigation 1) but mostly free on macOS (cache hits, per the 94% C/C++ hit rate above) — meaning fixing Investigation 1's Windows sccache question, if it succeeds, would absorb most of this cost the same way macOS already does, without any target-graph change. The duplicated Tauri release-build + `cargo test` Rust recompilation (confirmed above) was left unchanged for the analogous reason: its real fix is the same open Rust/sccache question, not a separate Cargo-profile-unification change that would risk silently changing test semantics (`debug_assertions`/overflow-checks differ between the release and test/dev profiles).

### The user pushed the fix as `64f6264`; real run confirmed and resolved the Cargo/Rust question definitively

Independently pulled and read (`gh run view`/`gh api`, run `33594758288`, commit `64f6264`, not the user's summary alone) — `check` passed on both platforms; macOS improved further (4m38s wall, 99.17% overall / 96.30% C/C++ / 99.83% Rust hit rate on a now-doubly-warm cache) confirming no regression. Windows's plain `sccache --show-stats` again reported all-zero — but this time the `SCCACHE_LOG=sccache=debug`/`SCCACHE_ERROR_LOG` instrumentation added specifically for this purpose caught the real mechanism directly, not by further inference:

The debug log shows the server started once (`start_server: 127.0.0.1:4226` at 05:28:20) and genuinely served the entire Cargo/Rust build with real cache hits — e.g. `[unicode_ident]: compile result: cache hit` at 05:29:32, and a `stats after compile result: ServerStats { compile_requests: 756, ..., requests_executed: 615, cache_hits: PerLanguageCount { counts: {"Rust": 522} }, cache_misses: PerLanguageCount { counts: {"Rust": 82} }, ... }` snapshot at 05:33:27 — a genuine ~86% Rust hit rate. **Windows Cargo/Rust sccache routing was never actually broken.** The last real compile activity is at 05:33:38 (the `cargo test` phase's own final crates); nothing touches the server again until `2026-09-02T05:43:43Z INFO sccache::server] shutting down due to being idle or request` — exactly 10 minutes 5 seconds of inactivity later, sccache's own documented default `SCCACHE_IDLE_TIMEOUT` (600s). That gap exists specifically *because* Investigation 1's fix (removing the confirmed-dead Windows C/C++ launcher flags) means the ~17-minute native `cmake --build` phase that follows generates zero sccache traffic by design — nothing else refreshes the daemon's activity clock before the job ends. When `mozilla-actions/sccache-action`'s own post-step finally calls `sccache --show-stats` near job end, it finds no server running, silently auto-spawns a brand-new, empty one just to answer the query, and that fresh server — not the one that did 615 real compiles — is what reports all-zero. This fully explains every prior observation across both runs (`33564596456` and `33594758288`): the "zero requests" symptom was a **stats-reporting artifact of the idle timeout racing the final query**, not a caching failure, on every occasion it was observed.

Fix applied: `SCCACHE_IDLE_TIMEOUT: "0"` added to the job-level `env:` (sccache's own documented value to disable the timeout and "run sccache permanently" — confirmed against `Configuration.md`), so the same server survives from the first Cargo compile through to the final stats query regardless of how long the native build phase leaves it idle. The now-served-their-purpose diagnostic scaffolding (`SCCACHE_LOG`/`SCCACHE_ERROR_LOG` env vars, the "Start sccache server" step, the "Show sccache diagnostic log" step) was removed — the mechanism is understood and the fix is a plain, small, permanent config change; leaving debug-level logging enabled indefinitely would only bloat every future run's log for no ongoing diagnostic value. `actionlint .github/workflows/check.yml` re-run clean after this edit.
