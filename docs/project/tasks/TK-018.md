# TK-018 — Long-Lived `native_runtime` Session: Materialize Then Move Over the Real Transport

Status: done
Feature: FT-017
Milestone: MS-002

## Objective

Replace `native_runtime`'s single-command-then-exit lifecycle with a loop that keeps its materialized `tracktion::Edit` alive across multiple commands, add the minimal wire envelope needed to distinguish `MaterializeProjectCommand` from `MoveClipCommand` on the same connection, drive a real materialize-then-move sequence from Python over one connection, and prove the move's effect with an automated cross-language test.

## Scope / Out of scope

In scope:

- `src/schemas/project.proto` gains two envelope messages sized to exactly the two command/event pairs that exist today: `Command { oneof command { MaterializeProjectCommand materialize = 1; MoveClipCommand move_clip = 2; } }` and `Event { oneof event { ProjectRenderedEvent project_rendered = 1; ClipMovedEvent clip_moved = 2; } }`. `ClipMovedEvent` gains `bool moved = 6`, `string rendered_file_path = 7`, `uint64 rendered_sample_count = 8`, `double peak_amplitude = 9` — additive fields only, so it stays the single response to a `MoveClipCommand` (mirroring `materialize()`'s own established build+render bundling, applied here to move+render) rather than requiring a second wire round trip per move.
- `src/backend/audio/wire_codec.h`/`.cpp`: replace `decodeMaterializeCommand`/`encodeRenderedEvent` with `decodeCommand` (parses a `Command` envelope into `std::optional<std::variant<ProjectSpec, MoveClipSpec>>`, a new small `MoveClipSpec` struct in `wire_codec.h`), `encodeProjectRenderedEvent`, and `encodeClipMovedEvent` (each wraps its message in an `Event` envelope before serializing). No change to `project_spec.h`'s existing `ProjectSpec`/`TrackSpec`/`ClipSpec`/`RenderResult`.
- `src/backend/audio/native_runtime.cpp`: replace the current connect → wait-for-exactly-one-command → decode-as-materialize → `materialize()` → send → exit shape with: connect, then loop on `waitForCommand`, decoding each arrival via `decodeCommand` and dispatching — a `ProjectSpec` calls `buildEdit` (keeping the returned `Edit` alive across loop iterations, replacing the `materialize()` convenience call since `buildEdit` + `renderEdit` composed together already reproduce its exact external behavior, per TK-017's own regression proof) then `renderEdit`, sending `encodeProjectRenderedEvent`; a `MoveClipSpec` calls `moveClip` against the still-live `Edit` (a null/not-yet-built `Edit` is treated as a failed move, not a crash) and, only on success, `renderEdit` again, sending `encodeClipMovedEvent` either way. The loop exits when the connection is lost (added `NativeRuntimeConnection::wasConnectionLost()` accessor) or a command fails to arrive/decode, and `main()`'s exit code reflects whether every command in the session succeeded.
- `src/backend/audio/tests/project_schema.cpp`: extend with round-trip assertions for the new `Command`/`Event` envelope messages and `ClipMovedEvent`'s four new fields, mirroring its existing per-message assertion style.
- `src/backend/core/src/corytm/runtime/session.py`: factor the existing spawn/connect/authenticate/teardown block out of `materialize_project` into a private `_connected_native_runtime` async context manager (no behavior change); keep `materialize_project`'s signature and externally observed behavior unchanged (now wraps/unwraps through the `Command`/`Event` envelope internally); add `ClipMove` (a `NamedTuple` of `track_id`/`clip_id`/`new_start_seconds`) and `materialize_then_move_clips(project, moves: Sequence[ClipMove], output_directory) -> tuple[ProjectRenderedEvent, list[ClipMovedEvent]]`, which sends one materialize command followed by one `MoveClipCommand` per entry in `moves` (in order) over the same connection and returns every response event — `moves` accepting a sequence, not exactly one, is what lets the new cross-language test also prove an unknown-id failure doesn't corrupt the still-live session, without inventing any dispatch beyond the two command types already in scope.
- `src/backend/core/tests/test_incremental_edit.py` (new, `@pytest.mark.transport`): the cross-language proof — materialize a one-track/one-clip project, move that clip forward, and assert the second render's sample count/peak amplitude reflect the longer, shifted output the move implies; a second case sends an unknown-id move followed by a valid move in the same session and asserts the first response's `moved` is `False` (zeroed render fields) while the second still succeeds correctly.
- `docs/technical/architecture.md`'s "Python↔C++ Boundary" section gains one sentence noting the second command/event pair now flows over one long-lived session via the `Command`/`Event` envelope, once this Task's implementation confirms the shape (see Knowledge impact).

Out of scope: any edit operation other than clip move; a generalized command-dispatch/oneof envelope beyond the two concrete types above (per EP-006's own Scope); persistence across process restarts; concurrent/multi-client sessions; command ordering validation beyond "a move before any materialize fails gracefully" (no queueing, no reordering); real-time/live playback; Dorian and any UI work (EP-006's own Out of scope).

## Acceptance criteria

- `native_runtime` processes a materialize command followed by a move command over one connection without exiting between them, and the move is applied to the same live `Edit` the materialize command built (not a fresh rebuild) — proven by the second render's measurable output genuinely differing from the baseline in the way the move implies (longer/shifted duration, real signal after the new start).
- An unknown track/clip id in a `MoveClipCommand` returns a `ClipMovedEvent` with `moved = false` and zeroed render fields, without crashing the process or corrupting the live `Edit`; a subsequent valid move in the same session still succeeds correctly.
- `test_incremental_edit.py` (`pytest -m transport`) passes, proving both of the above from the real Python entry point over the real transport.
- `test_first_sound.py` and `test_entrypoint.py` (`pytest -m transport`) continue to pass unchanged, proving the new envelope preserves the existing single-command materialize path's external behavior exactly.
- `project_schema` (ctest) continues to pass, now also covering the `Command`/`Event` envelope and `ClipMovedEvent`'s new fields.
- `make check-python`, `make check-native`, and `make check-transport` all pass locally end to end with zero new warnings on touched/added files.
- Confirmed by real, independently-verified cross-platform CI evidence (macOS and Windows), per this project's established practice for a genuinely new native-behavioral/transport surface (RSK-005 through RSK-008) — this Task/Feature/Epic stay `active`, not `done`, until that evidence exists; this session cannot push (`CLAUDE.md` §10).

**Locally verified (2026-09-02):** TDD followed as planned. A real bug was found and fixed during implementation, not merely assumed away: `NativeRuntimeConnection::waitForCommand`'s `commandReceived` flag was never reset after being consumed, so a second call in the same session returned immediately with the already-moved-from (empty) `receivedCommandBytes` instead of actually waiting for the next message — surfacing as `decodeCommand` returning `nullopt` and the process exiting with "received an unrecognised command" on the *second* command of every session. Found by manually driving the built `native_runtime` binary over a raw socket outside of pytest (isolating the C++ loop from the Python/asyncio harness) after the full `pytest -m transport` run hung; fixed by resetting `commandReceived = false` once its bytes are consumed. A second, independently-considered design point: an unknown-id `MoveClipCommand` was deliberately kept from affecting the process's overall exit code (only a materialize failure or a failed re-render after a *successful* move does) — otherwise a legitimate later move succeeding in the same session would still make the whole process exit non-zero, contradicting this Task's own "a subsequent valid move in the same session still succeeds" acceptance criterion.

After the fix: a full clean reconfigure + rebuild of all seven native targets produced no new warning categories — the only warnings present are the pre-existing, already-catalogued vendored ones (`.claude/memory/native-build-third-party-warnings.md`: JUCE/HarfBuzz `-Wnontrivial-memcall`, Tracktion Engine `-Wimplicit-const-int-float-conversion`), reproduced in higher counts than that note's own snapshot only because a full clean rebuild recompiles vendored translation units an incremental build wouldn't touch — no new category, and nothing in a Corytm-owned file. `ctest` reports `100% tests passed out of 5` (`toolchain_proof`, `proof_schema`, `project_schema`, `materializer_proof`, `live_session_proof`), `project_schema` now also covering the `Command`/`Event` envelope and `ClipMovedEvent`'s four new fields. `uv run pytest -m transport` (5 passed: `test_first_sound`, `test_entrypoint`, both new `test_incremental_edit.py` cases, `test_transport_proof`) confirms the envelope preserves the existing single-command path's external behavior exactly and proves both this Task's own new scenarios — a move's effect reflected in a same-session re-render, and an unknown-id move failing without ending the session. `uv run pytest -m "not transport"` (23 passed), `pyright` (0 errors, after switching `_connected_native_runtime`'s `@asynccontextmanager` return annotation from the now-deprecated `AsyncIterator[...]` form to `AsyncGenerator[...]`), and `ruff check`/`ruff format --check` (clean, after `ruff check --fix`/`ruff format` resolved one import-ordering and two line-length issues) all pass.
