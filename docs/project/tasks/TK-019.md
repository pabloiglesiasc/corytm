# TK-019 — Prove Dorian's Move-Clip Tool Boundary End to End

Status: done
Feature: FT-018
Milestone: MS-002

## Objective

Implement `corytm.dorian`'s first semantic tool: a validated `MoveClipProposal` input shape and a `move_clip` function that is the only path through which a proposed clip move is authorized and executed — via Corytm Engine's `with_clip_moved` (producing the new canonical `Project`) and EP-006's `materialize_then_move_clips` (applying the same move to a live native session and re-rendering). Prove, with automated tests, that invalid tool-call-shaped input is rejected before reaching either, and that valid input produces both a correctly-updated canonical `Project` and a `ClipMovedEvent` reflecting the move in the re-rendered sound.

## Scope / Out of scope

In scope:

- `src/backend/core/src/corytm/dorian/__init__.py`, `dorian/tools.py`: a frozen, `extra="forbid"` Pydantic `MoveClipProposal` (`track_id: str`, `clip_id: str`, `new_start_seconds: float = Field(ge=0)`) and an async `move_clip(project, proposal, output_directory) -> tuple[Project, ClipMovedEvent]` that calls `project.with_clip_moved(...)` then `materialize_then_move_clips(project, [ClipMove(...)], output_directory)` with the same track/clip/new-start values, returning the new canonical `Project` alongside the native `ClipMovedEvent`.
- `src/backend/core/src/corytm/dorian/test_tools.py` (colocated unit test, no native process): construct `MoveClipProposal.model_validate(...)` from untrusted-input-shaped mappings and assert rejection (`pydantic.ValidationError`) for a missing field, an out-of-range `new_start_seconds`, and an unexpected extra field; assert a valid mapping constructs successfully.
- `src/backend/core/tests/test_dorian_move_clip.py` (new, `@pytest.mark.transport`, cross-component per this repo's own convention for tests spanning Engine+Runtime+native process): builds a one-track/one-clip `Project`, calls `move_clip` with a valid proposal, and asserts the returned `Project` has the clip's new start position while the original `Project` passed in is unchanged, and the returned `ClipMovedEvent` has `moved is True` with sample count/peak amplitude reflecting the move (mirroring `test_incremental_edit.py`'s existing assertion shape); a second case passes a proposal naming an unknown clip id and asserts `project.with_clip_moved` raises `ValueError` without any native process ever being spawned.
- `docs/technical/architecture.md`'s "Human/Dorian Shared Application Path" section: confirm or extend, once implementation settles the exact shape (see Knowledge impact), that it names this first concrete tool rather than only the illustrative example.

Out of scope: any other Dorian tool; any LLM/provider call or tool-call-format parsing beyond the `MoveClipProposal` shape itself; model routing/tiers; any Desktop or conversational UI; any change to `project.proto`, `wire_codec`, `native_runtime.cpp`, or any other native/schema code — this Task is pure Python glue over already-proven mechanisms.

## Acceptance criteria

- Constructing `MoveClipProposal` from a mapping missing a required field, one with an out-of-range `new_start_seconds`, or one with an unexpected extra field raises `pydantic.ValidationError`, proving invalid tool-call-shaped input never reaches Engine or native code.
- Calling `move_clip` with a valid `MoveClipProposal` against a project whose named track/clip exist returns a new `Project` with the clip moved (the original `Project` argument unchanged, per its own frozen semantics) and a `ClipMovedEvent` with `moved is True` and render fields (`rendered_sample_count`, `peak_amplitude`) reflecting the move, via the real native runtime.
- Calling `project.with_clip_moved` with an unknown track or clip id raises `ValueError` before any native process is spawned (asserted directly, since `move_clip` calls it first).
- `uv run pytest -m "not transport"` and `uv run pytest -m transport` both pass, including the new tests; `pyright` (strict) and `ruff check`/`ruff format --check` are clean on all new/changed files.
- No native or schema file is touched; `ctest`'s existing 5/5 pass rate is unaffected (not re-run as part of this Task's own gate, since nothing native changed).
