# TK-022 — Wire Real Sidecar Spawn/Shutdown Into Production `run()`

Status: active
Feature: FT-021
Milestone: MS-002

## Objective

Give `src-tauri/src/lib.rs`'s real `run()` — not a test — a working spawn of the Python core sidecar and completion of EP-009's handshake, plus a shutdown hook on app exit, by extracting the spawn/handshake logic FT-020/TK-021's test already proved into a shared, non-test function both `run()` and the test call.

## Scope / Out of scope

In scope:

- `src-tauri/src/lib.rs`: a new `spawn_desktop_sidecar<R: tauri::Runtime>(app: &tauri::AppHandle<R>) -> Result<(u16, String), String>` production function — generic over `Runtime` so it works against both the real `Wry` runtime and `tauri::test::MockRuntime` — factored out of `desktop_channel_tests`'s existing inline spawn+handshake-parsing logic (moved, not duplicated). It spawns `corytm serve` via `app.shell()`, parses the `READY`/`DESKTOP <port> <secret>` handshake, and returns the port/secret while keeping the spawned `CommandChild` reachable for shutdown.
- `run()`'s `Builder`: registers `tauri_plugin_shell::init()`; `.setup()` calls `tauri::async_runtime::spawn` to run `spawn_desktop_sidecar` in the background (logging success/failure via the existing `tauri-plugin-log` plugin, not blocking startup on it), storing the resulting `CommandChild` in `app.manage(Mutex<Option<CommandChild>>)` for the shutdown hook to reach.
- `run()` switches from `.run(context)` to `.build(context)?.run(move |app_handle, event| ...)`, matching on `RunEvent::ExitRequested`/`RunEvent::Exit` to take the managed `CommandChild` (if present) and write `SHUTDOWN\n` to it, best-effort (log, don't panic, on failure).
- `desktop_channel_tests::desktop_channel_round_trips_over_the_second_transport`: updated to call `spawn_desktop_sidecar` instead of its own inline spawn/parse logic, keeping its own connect/authenticate/round-trip/explicit-`SHUTDOWN` assertions unchanged.

Out of scope: any real domain command over the channel beyond the existing `DesktopProofMessage` proof (EP-010's second Feature); restart-on-crash or reconnection logic; any Desktop UI/state-management/rendering change; any change to `desktop.proto`, `project.proto`, `proof.proto`, or any file under `src/backend/audio/` or `src/backend/core`.

## Acceptance criteria

- `cargo test` continues to pass (`desktop_channel_round_trips_over_the_second_transport` now driven through the shared production function, not its own copy of the spawn/parse logic), plus the two pre-existing tests unaffected.
- `run()` genuinely calls the same `spawn_desktop_sidecar` function the test calls — verified by reading the code, not merely by the test passing (a shared-function claim a test alone cannot fully prove).
- `make check-desktop` passes locally with zero new compiler warnings.
- Human-verified, as a distinct non-automatable acceptance boundary: running `npm run tauri dev`, observing (via a log line or `ps`) that a real `corytm serve` process is spawned, quitting the app window, and confirming via `ps`/Activity Monitor that the process is no longer running afterward.
- Not closed `done` on local verification alone: per this project's established practice (RSK-002 through RSK-011), a real, independently-verified passing Windows GitHub Actions run is required first — production startup/shutdown wiring through Tauri's real event-loop callback is untested on Windows from this session.

## Notes

TDD is not the primary discipline for this Task's `run()`/shutdown-hook half, since Tauri's real event loop and OS process lifecycle cannot be exercised by `cargo test`'s mock app — that half is proven by the human confirmation step named above instead, mirroring EP-005's own audible-smoke-test precedent for exactly this kind of automation gap. The spawn/handshake half stays test-driven: the existing passing test is refactored to call the new shared function, and must still pass unchanged in behavior after the refactor.

**Implemented and validated locally (2026-09-02):** `spawn_desktop_sidecar<R: tauri::Runtime>` was factored out of `desktop_channel_tests`'s own inline logic into real production code in `lib.rs`, generic over `Runtime` so both the real app and `tauri::test::MockRuntime` can call it — confirmed by reading `tauri_plugin_shell::ShellExt`'s own trait bound (`ShellExt<R: Runtime>`), not assumed. Returns `(Receiver<CommandEvent>, CommandChild, u16, String)`: the receiver and child stay reachable so callers (the test, for its own post-`SHUTDOWN` termination check; `run()`, for its shutdown hook) aren't left holding an orphaned handle. Used `tauri::async_runtime::Receiver` rather than adding `tokio` as a direct production dependency, after confirming (by reading `tauri-plugin-shell`'s own source) that `Command::spawn()` already returns `tauri::async_runtime::Receiver<CommandEvent>`, itself already re-exported by `tauri`'s own async-runtime integration — avoiding an unnecessary new `Cargo.toml` production dependency entirely (`Cargo.lock`/`Cargo.toml` end up untouched by this Task, confirmed via `git status`).

`run()` now: registers `tauri_plugin_shell::init()`; `.setup()` calls `app.manage(Mutex::new(None::<CommandChild>))` then fires `tauri::async_runtime::spawn` (a background task, not blocking startup) to call `spawn_desktop_sidecar`, logging success/failure via the existing `tauri-plugin-log` plugin and storing the resulting `CommandChild` into the managed `Mutex` on success; switched from `.run(context)` to `.build(context)?.run(|app_handle, event| ...)` so a closure can observe `RunEvent::ExitRequested`/`RunEvent::Exit`, `.take()` the managed child (idempotent — a later event finds `None` and does nothing), and write `SHUTDOWN\n` to it, logging (not panicking) on failure — confirmed this `Builder::build`/`App::run(callback)` pattern and `Manager::manage`/`Manager::state` against the actual vendored `tauri` crate source (`app.rs`, `lib.rs`), not guessed from memory. `desktop_channel_tests::desktop_channel_round_trips_over_the_second_transport` was updated to call `spawn_desktop_sidecar(app.handle())` under a `tokio::time::timeout` instead of its own inline copy of the spawn/parse loop, with its connect/authenticate/round-trip/explicit-`SHUTDOWN`/termination-check logic otherwise unchanged.

Validated: `cargo build --lib` and `cargo build --release --bin app` both clean with zero warnings (the release binary is what `main.rs` actually ships, confirming the new `run()` code path — not just the test path — compiles warning-free); `cargo test` (all 3 tests, including the refactored one) passes; `make check-desktop` (release build, `.app`/`.dmg` bundling, `cargo test`) and a full clean `make check` (all five targets) both passed end to end. `git status` confirmed only `src/frontend/desktop/src-tauri/src/lib.rs` changed under `src/` — no `Cargo.toml`/`Cargo.lock` change, and nothing under `src/backend/audio/`, `src/backend/core/`, or any schema file was touched.

**Left `active`, not closed `done`:** two things remain unconfirmed. First, per this project's established practice (RSK-002 through RSK-011), a real, independently-verified passing Windows GitHub Actions run — `RSK-012` opened for the new combination (`async_runtime::spawn` from `.setup()`, `Manager`-based shared state, and `Builder::build().run(callback)` observing `RunEvent` instead of the simpler `.run(context)` every prior Task used). Second, the human confirmation step this Task's acceptance criteria itself calls for (launch `npm run tauri dev`, quit the app, confirm via `ps` that the spawned `corytm serve` process is gone) has not yet been performed — deliberately left to the user rather than attempted by this session, since it requires actually opening a real GUI window on the user's own desktop, which this session judged should not be done without the user's awareness (unlike EP-005's audible check, a surprise window is a more intrusive way to self-verify than asking).

**Human confirmation satisfied (2026-09-02):** the user ran `npm run tauri dev` on macOS and independently confirmed both halves of this acceptance criterion with real `ps` output, not just a visual impression: while the app was open, `ps aux | grep -i "corytm serve"` showed both the `uv run --project ../../../backend/core corytm serve` launcher and the spawned `.../corytm serve` Python process genuinely running; after closing the Corytm window (the real window-close path, which is what fires `RunEvent::ExitRequested`/`Exit` — not `Ctrl+C`, which would have bypassed the shutdown hook entirely), the same `ps` check returned zero matches. This confirms `spawn_desktop_sidecar` genuinely spawns the real sidecar from production `run()` code (not only from `cargo test`'s mock app) and that the `RunEvent` handler's `SHUTDOWN` write reaches the child in time to let it exit cleanly before the check ran. Only the real Windows GitHub Actions run (`RSK-012`) remains before this Task, FT-021, or EP-010 can close.
