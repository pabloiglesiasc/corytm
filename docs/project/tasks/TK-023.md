# TK-023 — Real Move-Clip Command/Event Over the Desktop Channel

Status: done
Feature: FT-022
Milestone: MS-002

## Objective

Make the Desktop channel (ADR-010) carry a real `MoveClipCommand`/`ClipMovedEvent` pair against an in-memory fixture project, reusing Corytm Engine's `with_clip_moved` and EP-006/EP-008's live-session native mechanism — replacing `DesktopProofMessage` as what the channel's round trip actually proves — with no frontend/UI change.

## Scope / Out of scope

In scope:

- `src/backend/core/src/corytm/runtime/session.py`: a new `move_clip_in_session()` function combining `Project.with_clip_moved` (canonical-state update, tried first so an unknown track/clip id fails before any native process spawns) with `materialize_then_move_clips` (live-session re-render), extracted so it has exactly one implementation shared by both call sites below.
- `src/backend/core/src/corytm/dorian/tools.py`: `move_clip` refactored to delegate execution to `move_clip_in_session` instead of duplicating its body — `MoveClipProposal`'s own validation-boundary role (ADR-004) is unchanged.
- `src/backend/core/src/corytm/runtime/desktop.py`: `serve_desktop_channel()` reads a real `project.proto` `MoveClipCommand` frame (not `DesktopProofMessage`) against a new hardcoded one-track/one-clip fixture project built locally in this module (mirroring the existing precedent of a small, independently-duplicated fixture builder per call site — `main.py`, `test_first_sound.py`, `test_incremental_edit.py`, `test_dorian_move_clip.py` each already have their own), applies the move via `move_clip_in_session` against a fresh temporary output directory, and writes back the real `ClipMovedEvent`.
- `src/frontend/desktop/src-tauri/build.rs`: also compile `project.proto` for Rust (`prost-build`), alongside the existing `desktop.proto` compilation — reusing the already-fetched/verified `protoc` binary.
- `src/frontend/desktop/src-tauri/src/lib.rs`: a `project_proto` module (mirroring the existing `desktop_proto` one); `write_frame`/`read_frame` promoted from `desktop_channel_tests`'s own test-local helpers into real production functions (needed by TK-024's production command, planned next) — this Task promotes them and updates the existing test to call the shared versions, without yet adding the production caller (TK-024's own scope); `desktop_channel_tests::desktop_channel_round_trips_over_the_second_transport` updated to send a real `MoveClipCommand` and assert the returned `ClipMovedEvent` reflects a genuine move (`moved = true`, the expected new start time, real render-evidence fields non-empty/non-zero).

Out of scope: the production `#[tauri::command]`, Tauri command-permission/capability wiring, and any frontend/UI change (TK-024); any change to `native_runtime.cpp`, `wire_codec`, or any file under `src/backend/audio/`; real project persistence; repeated/multi-command support on the same Desktop channel connection (the server still serves exactly one client for exactly one command, unchanged in shape).

## Acceptance criteria

- `desktop_proof_message_round_trips` (the pre-existing local `DesktopProofMessage` encode/decode unit test, unrelated to the live channel) continues to pass unchanged — kept deliberately as a permanent Rust-codegen toolchain proof, mirroring `proof.proto`/`project_schema`'s own precedent of coexisting with real product schemas.
- `desktop_channel_round_trips_over_the_second_transport` (updated) passes, proving end to end: the real spawned `corytm serve` process accepts a real `MoveClipCommand`, applies it to its own in-memory fixture project through `move_clip_in_session`, and returns a `ClipMovedEvent` whose fields prove the clip genuinely moved and was genuinely re-rendered.
- A new Python test proves `move_clip_in_session` directly (not only through Dorian's or Desktop's own callers), confirming it is genuinely one shared implementation.
- `test_dorian_move_clip.py` continues to pass unchanged in behavior after the `dorian.tools.move_clip` refactor (same inputs, same outputs, same raised exceptions).
- `make check-python` and `make check-transport` pass; `cargo build`/`cargo test` under `src/frontend/desktop/src-tauri` pass with zero new warnings; a full local `make check` passes end to end.

Under the current Feature-level delivery model (`CLAUDE.md` §6/§7), this Task's own Done is local validation only — it closes on the criteria above without waiting on its own Windows CI run. `RSK-013` (Rust `prost` compiling `project.proto`'s nested/repeated messages for the first time) is a real, still-open risk, but the required Windows GitHub Actions confirmation is tracked once, at FT-022's own `validating` stage, across this Task and TK-024 together — not re-gated per Task.

## Notes

TDD is the primary discipline throughout: the updated Rust test and the new Python test are both written and confirmed failing (wrong message type / `ModuleNotFoundError` or `AttributeError` for the not-yet-existing shared function) before the corresponding implementation lands.

**Implemented and validated locally (2026-09-02):** `move_clip_in_session` added to `runtime/session.py`, composing `Project.with_clip_moved` (tried first, so an unknown track/clip id raises before any native process spawns) and `materialize_then_move_clips`, confirmed via a new failing-then-passing `tests/test_move_clip_in_session.py` (transport-marked). `dorian/tools.py::move_clip` refactored to delegate to it; `test_dorian_move_clip.py` re-run unchanged and still passes, confirming behavior-preserving. `runtime/desktop.py::serve_desktop_channel()` now builds a hardcoded one-track/one-clip fixture project (`_build_desktop_fixture_project`), reads a real `MoveClipCommand` frame, applies it via `move_clip_in_session` against a fresh `tempfile.TemporaryDirectory()`, and returns the real `ClipMovedEvent`.

On the Rust side, `build.rs`'s `compile_desktop_proto` was renamed `compile_protos` and extended to also compile `project.proto`; `lib.rs` gained a `project_proto` module. `desktop_channel_tests::desktop_channel_round_trips_over_the_second_transport` now sends a real `MoveClipCommand` (matching `desktop.py`'s fixture ids, `new_start_seconds = 1.0`) and asserts the returned `ClipMovedEvent` reflects a genuine move (`moved = true`, correct track/clip id and start time, non-zero render evidence) — its own local `write_frame`/`read_frame` helpers were kept test-local (not yet promoted to production), since no production caller needs them until TK-024 adds the real `#[tauri::command]`; promoting them now would have left genuinely dead code in `cargo build --lib`/`--bin app` (confirmed by trying it first and seeing the real `dead_code` warnings), so the promotion is deliberately deferred to TK-024, mirroring TK-022's own precedent of promoting test-proven logic to production exactly when a production caller needs it, not before.

Validated beyond this Task's own minimum: full clean `make check` (all five targets) passed end to end, including a from-scratch native rebuild (`ctest` 5/5) and `make check-desktop` (release build, `.app`/`.dmg` bundling, `cargo test` — all 3 Rust tests passing with zero new warnings on both `cargo build --lib` and `cargo build --release --bin app`). `git status` confirmed only this Task's own named files changed — no `Cargo.toml`/`Cargo.lock`/`desktop.proto`/`native_runtime.cpp`/`wire_codec` touched.

`DesktopProofMessage` is deliberately not deleted from `desktop.proto` or `lib.rs` — see FT-022's own reasoning: it keeps proving the Rust `prost`/`protoc` toolchain in isolation, exactly the role `proof.proto`'s `ProofMessage` still plays for C++ alongside `project.proto`'s real messages. Reusing `project.proto`'s `MoveClipCommand`/`ClipMovedEvent` directly on the Desktop channel (rather than wrapping them in a new Desktop-owned envelope message) was judged the correct reading of ADR-010 point 1 for a channel that, today, carries exactly one command type: ADR-010's "own envelope and versioning" concern is about not being forced to share `project.proto`'s `Command`/`Event` oneof (which bundles unrelated native-facing command types), not about requiring a synthetic single-field wrapper message with no present purpose — introducing one now, before a second Desktop command type exists, would be exactly the premature abstraction `CLAUDE.md` §8 warns against, and diverges from this project's own precedent of adding an enveloping oneof only once ≥2 real command types exist (`project.proto` itself only gained its `Command`/`Event` oneof at FT-017, when `MoveClipCommand` joined the pre-existing `MaterializeProjectCommand`).
