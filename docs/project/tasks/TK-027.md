# TK-027 — Persistent Desktop Channel Connection and Create/Save/Open Commands

Status: done
Feature: FT-024
Milestone: MS-002

## Objective

Give the Desktop channel a genuinely persistent, reusable connection (replacing `move_clip`'s one-shot-per-call pattern, which only ever worked because it was the sole command invoked), and add `create_project`/`save_project`/`open_project` Tauri commands over it, backed by `tauri-plugin-dialog` for path resolution on the frontend side. No UI in this Task.

## Scope / Out of scope

In scope:

- `Cargo.toml`: `tauri-plugin-dialog = "2"` (matching `tauri-plugin-shell`/`tauri-plugin-log`'s existing version pin); `package.json`: `"@tauri-apps/plugin-dialog": "^2"` (matching `@tauri-apps/api`'s existing pin style).
- `lib.rs`: `run()` registers `tauri_plugin_dialog::init()`. A new managed state slot (`tokio::sync::Mutex<Option<(OwnedReadHalf, OwnedWriteHalf)>>` or equivalent) holds the Desktop channel's single authenticated connection, opened once right after `spawn_desktop_sidecar`'s handshake succeeds (same place `DesktopChannel{port, secret}` is currently stored) rather than reopened per command. A shared `async fn send_command(state, command: project_proto::Command) -> Result<project_proto::Event, String>` encodes, writes, reads, and decodes one round trip against that held connection. `move_clip` is refactored to build its `Command` and call `send_command`, with its external JSON shape and behavior unchanged. `create_project() -> Result<ProjectCreatedResult, String>`, `save_project(file_path: String) -> Result<ProjectSavedResult, String>`, `open_project(file_path: String) -> Result<ProjectOpenedResult, String>` are added, each building its `Command` variant and calling `send_command`, matching against the corresponding `Event` variant (returning an error string for any other variant, mirroring `move_clip`'s existing pattern). All four commands registered in `invoke_handler`.
- `capabilities/default.json`: `"dialog:default"` added alongside the existing `"allow-move-clip"`; `build.rs`'s command-manifest list extended for the three new commands (mirroring TK-024's existing `allow-move-clip` wiring), producing new `permissions/autogenerated/*.toml` entries (already `.gitignore`d per the existing `/permissions/autogenerated/` precedent).

Out of scope: any actual dialog-triggering code in Rust (the frontend calls `@tauri-apps/plugin-dialog`'s `save()`/`open()` directly per FT-024's own scope — this Task's commands only take an already-resolved path); any UI (TK-028); any change to `project.proto`, `desktop.py`, or `native_runtime.cpp`.

## Acceptance criteria

- A new `cargo test` (in `desktop_channel_tests`, reusing `SidecarGuard`) spawns the real sidecar once and, over the resulting single held connection, drives `create_project` → `save_project` (a real temp path) → `open_project` (a distinct, separately-prepared fixture file) → `move_clip`, in that sequence, all four succeeding against the same connection — proving the persistent-connection refactor genuinely supports a multi-command sequence, which a reopened-per-call design would fail on the second command.
- `save_project`'s written file independently round-trips via a direct Python `persistence.load_project` check (mirroring TK-026's own Python-side test pattern, invoked from the Rust test via a small helper script or by reusing an existing fixture path convention — decided during implementation).
- `open_project` against the fixture file returns the correct `track_count` and non-zero `rendered_sample_count`/`peak_amplitude`.
- `move_clip`'s existing test assertions (moved, start_seconds, sample count, peak amplitude) pass unchanged.
- `cargo build --lib`, `cargo build --release --bin app`, and `cargo test` are clean with zero new warnings; `make check-desktop` passes.
