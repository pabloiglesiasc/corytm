# TK-030 — Desktop Add-Track/Add-Clip Commands, UI, and First Design-System Materialization

Status: done
Feature: FT-025
Milestone: MS-002

## Objective

Add the Rust `add_track`/`add_clip` commands on the Desktop channel's existing held connection, and build the minimal UI that lets a human actually author a track/clip and see it render — the first real materialization of `docs/product/design.md`'s design-system direction against real UI work, reviewed via the `ui-ux-review` skill.

## Scope / Out of scope

In scope:

- `src/frontend/desktop/src-tauri/src/lib.rs`: `add_track(state) -> AudioTrackAddedResult { track_id, track_count }` and `add_clip(state, track_id, duration_seconds) -> AudioClipAddedResult { clip_id, start_seconds, duration_seconds, rendered_file_path, rendered_sample_count, peak_amplitude }`, following `create_project`/`save_project`'s existing parameterized-command shape exactly; both registered in `generate_handler!`.
- A `cargo test` extending the existing `create_save_open_move_all_succeed_over_one_held_connection` shape (or a sibling test) to also drive `add_track` → `add_clip` over the same held connection.
- `src/frontend/desktop/src/tokens.css` (or equivalent): semantic CSS custom properties — background/surface/text/border/accent colors, spacing scale, radius, font stack — light values on `:root`, dark values under `@media (prefers-color-scheme: dark)`, per `docs/product/design.md` §3/§5 (neutral chrome, low-to-medium-radius geometry, both themes from the start).
- `src/frontend/desktop/src/components/Button.tsx` and a labeled number-input component: the first small Corytm Desktop component catalog, justified by immediate repeated use (six buttons; one numeric input) per `docs/product/design.md` §4/§5's promotion criterion.
- `App.tsx`: "Add Track" and "Add Clip" controls (the latter taking a duration via the new number-input component, defaulting to 2 seconds), restyled alongside the existing New/Save/Open/Move-Clip controls using the new tokens/components. "Add Track" is disabled once the current project already has a track (`docs/technical/architecture.md`'s single-track materialization limit); "Add Clip" is disabled until a track exists.
- Applying the `ui-ux-review` skill against this UI change, addressing findings before Close.
- Human confirmation of the real running app (`npm run tauri dev`): New Project → Add Track → Add Clip (more than once) → genuine render evidence, in both light and dark OS theme settings.

Out of scope: any Engine/protobuf/Python change (TK-029, already done); any icon library, third-party component library, or component-catalog tooling (none is needed at this scale — plain semantic HTML/CSS is a legitimate first catalog per `docs/product/design.md` §6); multi-track UI; clip deletion/renaming/drag-to-place.

**Human validation attempted, failed with two real functional bugs and real design gaps (2026-09-02):**

1. **`add_track not allowed. Command not found`.** Root-caused, not assumed: `build.rs` passes a *hardcoded* command list to `tauri_build::AppManifest::new().commands(&[...])`, which is what actually generates `permissions/autogenerated/<command>.toml` — the only place a `capabilities/default.json` grant (`allow-<command>`) can come from. `add_track`/`add_clip` were registered in `generate_handler!` but never added to that list, so no permission ever existed to grant. This was invisible to every existing `cargo test` because they call the Rust functions directly (`add_track(app.state())`), bypassing Tauri's IPC/ACL pipeline entirely — the first time this project has tested a command through real ACL resolution. Fixed via TDD: a new test, `real_app_commands_are_permitted_and_readiness_is_observable`, builds the app against its own real, compiled-in `tauri.conf.json`/`capabilities/` (`tauri::generate_context!()`, not `mock_context`'s empty ACL) and drives commands through `tauri::test::get_ipc_response` — the genuine IPC invoke path. Confirmed failing first with the exact real error (`"desktop_channel_ready not allowed. Permissions associated with this command: allow-desktop-channel-ready"`); fixed by adding `add_track`/`add_clip`/`desktop_channel_ready` to `build.rs`'s command list and their `allow-*` grants to `capabilities/default.json`. A real Tauri constraint surfaced along the way: `generate_context!()` embeds a process-wide `_EMBED_INFO_PLIST` symbol that can only be defined once per compiled binary, colliding with `run()`'s own existing call — fixed by gating `run()`'s real body behind `#[cfg(not(test))]` (with a `#[cfg(test)] fn run() { unreachable!() }` stub, since `run()` is never called from a test), leaving the test's expansion as the sole one in that binary. A second, unrelated issue surfaced once the test compiled: `tauri::test::get_ipc_response` blocks its calling thread on a synchronous channel receive while the invoked async command runs, which deadlocks on a single-threaded runtime — fixed by `#[tokio::test(flavor = "multi_thread", worker_threads = 2)]`.

2. **The startup race** (New Project clicked before the sidecar/channel is genuinely ready → an early failure). Confirmed by design inspection, not by literally reproducing the exact wall-clock race: `run()`'s `.setup()` fires the sidecar-spawn-and-connect sequence via `tauri::async_runtime::spawn` and returns immediately — the window becomes interactive long before that async work (or even its intermediate "sidecar ready on port" log line) has any bearing on whether the Desktop-channel connection itself is stored yet, and nothing in the app ever told the frontend when it actually was. (A specific alternate hypothesis — that dropping `spawn_desktop_sidecar`'s returned `Receiver<CommandEvent>` in production, unlike the tests which retain it, corrupts the child's stdout pipe — was checked directly against `tauri_plugin_shell`'s own source and ruled out: a dropped receiver leaves its pipe-reading thread reading harmlessly into a void, per `read_line`'s own `let _ = ...` error handling.) Fixed structurally, per the instruction that a user must never need to infer readiness: a new `desktop_channel_ready` command reports whether the Desktop channel's `Option<TcpStream>` is genuinely `Some` yet; `App.tsx` polls it every 200ms from mount, disables every Desktop-channel-dependent control until it reports `true`, and shows a "Connecting to backend…" status line — closing the race by construction rather than by narrowing a timing window. Automated coverage added where practical (a wall-clock GUI race itself isn't reproducible headlessly): the same real-IPC test proves `desktop_channel_ready` reports `false` before the sidecar is even spawned and `true` once connected, and proves a Desktop-channel command invoked in that premature window fails with a clear, specific error (`"desktop channel is not connected yet"`) rather than hanging or producing a confusing failure.

3. **Design findings** — re-reviewed via `ui-ux-review` against the concrete reported gaps: `--radius-sm`/`--radius-md` (4px/8px) read as dated/toolkit-like rather than "contemporary low-to-medium-radius" (`docs/product/design.md` §3); the primary button's hover (`filter: brightness(1.1)` on an already-light accent) moved *toward* the background in light mode, collapsing contrast exactly when hover should increase it; the flat row of same-weight controls plus a raw JSON dump read as a debug harness, with no header/identity, no grouping, and no distinction between primary actions and secondary output.

Before iterating further by hand, a tooling evaluation was run (explicitly requested) against Corytm's token ownership, dark/light theming, accessibility, consistency-at-scale, third-party-identity avoidance, AI-assisted maintainability, integration cost, Web-portability, migration cost, and fit for a dense professional UI — comparing native CSS/CSS Modules, Tailwind, Panda CSS, and runtime CSS-in-JS, with headless-primitive libraries and component-catalog tooling considered separately. **ADR-012** records the outcome, approved by the user: Tailwind CSS 4 as the utility-*authoring* layer, with its default theme fully replaced (`--color-*: initial; --radius-*: initial;` in Tailwind's `@theme` block, not extended) by Corytm's own existing `tokens.css` custom properties, so Corytm's tokens remain the sole source of value and of light/dark behavior; `@ladle/react` adopted as the component-catalog tool, scoped to exactly `Button`/`NumberField`; headless/adaptable accessible-primitive libraries (Radix UI, Base UI) explicitly deferred until a real interactive widget needs one.

Applied: `--radius-sm`/`--radius-md` → `8px`/`14px`; a dedicated `--color-accent-hover` per theme, chosen for the *correct* contrast direction each way (darker in light mode, lighter in dark mode — the exact reason a single `brightness()` filter was wrong); `components.css`'s hand-written classes retired in favor of Tailwind utility classes bound to the token names (`bg-accent`, `border-border`, `rounded-sm`, etc. — confirmed by inspecting the compiled CSS that these resolve to `var(--color-*)`/`var(--radius-*)`, never a Tailwind default); `App.tsx` restructured into a real page shell — a header carrying product identity, "Project" and "Track & Clip" as labeled, bordered sections, and the JSON/error output demoted to a clearly secondary "Output" section — rather than one flat control row. `Button.stories.tsx`/`NumberField.stories.tsx` added for Ladle (`npm run catalog`); confirmed the compiled catalog build genuinely includes Corytm's own utilities (an explicit `@source './';` in `main.css` was needed — Tailwind's own root-relative auto-detection heuristic did not reliably see this directory when bundled by Ladle's own nested Vite instance).

**Reopened `done → active` (2026-09-02): a third real product-path bug found on continued human validation.** After leaving the real app open for a while, every backend-dependent control except Open/Save began failing with `failed to send command: Broken pipe (os error 32)`. Root-caused, not assumed: `_run_session`'s command-read (`corytm.runtime.desktop`, shared session-loop code TK-026/FT-023 originally introduced, outside this Task's own declared Rust/frontend scope — fixed directly here as the smallest necessary change, mirroring FT-024's own `session.py` precedent for a genuine FT-025 acceptance blocker) wrapped `read_frame` in `asyncio.wait_for(..., timeout=_COMMAND_TIMEOUT_SECONDS)` (30s) whose `TimeoutError` was never caught — only `IncompleteReadError` was. After 30 real seconds of inactivity this propagated uncaught through `serve_desktop_channel()` and `main()` (no `try`/`except` anywhere above it), silently killing the entire `corytm serve` process while Rust's `DesktopConnection` kept believing its `TcpStream` was still live; the next command's `write_frame` then failed with a genuine OS-level broken pipe. This directly contradicted `docs/technical/architecture.md`'s own already-stated intent ("`serve_desktop_channel()` accepts exactly one client connection per app session") — a real, arbitrarily-long idle gap between human clicks is normal for a desktop app, not something the protocol should ever time out on. (Why Open/Save appeared unaffected could not be pinned to any structural code difference — all six commands share the identical connection and helper — so it is most plausibly a test-sequencing artifact, not a distinct code path; noted rather than left unstated.)

Decided and documented the intended connection contract, per instruction, rather than silently picking one: the Desktop channel is genuinely persistent for the app's whole session; reconnection is explicitly **not** a supported behavior (`docs/technical/architecture.md`'s Desktop↔Python Boundary section updated accordingly) — a dead connection stays dead until the app relaunches.

Fixed via TDD: a new test (`test_session_survives_a_long_idle_gap_between_commands`) monkeypatches `_COMMAND_TIMEOUT_SECONDS` down to `0.2s` (`raising=False`, so the same line stays valid once the constant is removed) and confirms failing first with the exact real bug — `serve_desktop_channel()`'s task finishing with an uncaught `TimeoutError` after a `0.5s` idle gap. Fixed by removing the timeout wrapper entirely (`await read_frame(reader)`, no `wait_for`) and deleting the now-unused constant — the existing `except asyncio.IncompleteReadError: return` already correctly handles the one case that should end a session (the client actually disconnecting). A focused stress/repetition test was added per instruction (`test_repeated_commands_with_idle_gaps_stay_reliable_over_one_connection`): 10 real `move_clip` round trips over one held connection, each preceded by a short idle gap, catching any other lifecycle race a single-command test couldn't.

Rust-side defense in depth, per the explicit "a stale connection must never leave controls enabled while commands are guaranteed to fail" requirement: `send_command` now clears the stored `DesktopConnection` to `None` on any write/read I/O failure (not on a decode failure, which doesn't indicate a dead connection), so `desktop_channel_ready` immediately reflects reality — this is not reconnect logic, only honest state; nothing ever re-establishes the connection. Proven via a new test (`a_dead_connection_is_cleared_so_readiness_reflects_it`) using a throwaway TCP listener as the peer (deliberately not a real killed `corytm serve` process — `CommandChild::kill()` was confirmed, directly, to terminate only the `uv` process it spawns, not `corytm serve` running as `uv`'s own child, which a real-process version of this test would have silently left alive and connected). Confirmed failing first against the pre-fix `send_command`. The frontend's readiness poll (previously stopping once `channelReady` became `true`) now continues indefinitely at a slower steady interval once ready, so a later connection loss is detected and every control is disabled again — never by attempting to reconnect, only by observing the backend's own honest state — with the status banner distinguishing "Connecting to backend…" (never yet ready) from "Backend connection lost — restart Corytm to continue." (was ready, now isn't).
