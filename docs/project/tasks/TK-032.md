# TK-032 — Orchestrate move_clip's Tool Call and Prove It Live

Status: done
Feature: FT-026

## Objective

Wire `corytm.dorian.tools.MoveClipProposal` to TK-031's provider boundary via `corytm.dorian.agent.propose_move_clip`, and prove GPT-OSS 20B reliably drives it through a human-run live evaluation.

## Scope / Out of scope

In scope: `agent.py`'s `MOVE_CLIP_TOOL_SPEC` and `propose_move_clip`; unit tests against a fake `ModelProvider` (no network) covering a valid call, no call, a mismatched tool name, and invalid arguments; a `live_llm`-marked evaluation module (skipped automatically without a real `GROQ_API_KEY`) driving `propose_move_clip` with a real `GroqProvider` against representative simple move-clip instructions; `docs/technical/architecture.md` sync.

Out of scope: any change to `corytm.dorian.tools.move_clip` itself (the trusted execute path, unchanged); any Desktop UI.

## Acceptance criteria

- `propose_move_clip` returns a validated `MoveClipProposal` when a fake `ModelProvider` returns a valid `move_clip` `ToolCall`.
- `propose_move_clip` returns `None` when the fake provider returns no `ToolCall`, or one naming a different tool.
- `propose_move_clip` propagates `pydantic.ValidationError` when the fake provider's arguments fail `MoveClipProposal`'s own validation (missing field, negative `new_start_seconds`, unexpected extra field) — the same rejections `test_tools.py` already proves for a hand-constructed proposal, now proven through the model-facing path too.
- The live evaluation module is collected but skipped by default (no `GROQ_API_KEY`), and documented as this Feature's human acceptance step.
- `make check-python` passes end to end with zero new warnings.
