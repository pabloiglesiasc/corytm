# TK-034 — Local Validation Tooling: sccache Reuse, Lockfile-Gated Frontend Install, live_llm Exclusion

Status: done
Feature: FT-028

## Objective

Apply three small, independently low-risk local-tooling changes decided in the approved review: wire local `sccache`/CMake compiler-launcher reuse into `check-native`/`check-desktop` using the exact mechanism CI already proves works; replace `check-frontend`'s unconditional `npm ci` with a lockfile-stamp-gated mechanism (no install when the installed state is already known to correspond to `package-lock.json`; `npm ci` when the lockfile changed, the install is absent, or validity can't be established); exclude `live_llm` from `check-python`'s default pytest invocation.

## Scope / Out of scope

In scope: `Makefile` (`check-native`, `check-desktop`, `check-frontend`, `clean` targets); `pyproject.toml`'s `[tool.pytest.ini_options]`.

Out of scope: `.github/workflows/check.yml` (CI keeps unconditional `npm ci`, and CI already sets its own sccache env vars independently of this Task); the Python test layout migration (TK-035); anything about `npm install` as a fallback — the lockfile-stamp mechanism must fall back to `npm ci`, never `npm install`, per the user's explicit override of the original review recommendation.

## Acceptance criteria

- `make check-native` and `make check-desktop`, run locally after a change that requires real compilation, show non-zero `sccache --show-stats` activity, using `RUSTC_WRAPPER=sccache` and CMake's `CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER=sccache` — the same flags `.github/workflows/check.yml` already sets, not a new mechanism.
- `make check-frontend`'s install step: computes whether `node_modules`' installed state already corresponds to the current `package-lock.json` (a stamp file recording the lockfile's own hash, updated only on a successful install); performs no install when it matches; runs `npm ci` (never `npm install`) when the stamp is missing, stale, or `node_modules` itself is absent. Implemented as a Make file-dependency rule (a stamp-file target `node_modules`/`.npm-ci-stamp` depending on `package-lock.json`), not a bespoke script.
- The Makefile's `check-python` recipe excludes `live_llm` in addition to `transport` from its pytest `-m` filter (the marker itself is already declared in `pyproject.toml` and needs no change there); `test_agent_live_eval.py`'s two tests are no longer collected/run by `make check-python`, but remain runnable via an explicit `uv run pytest -m live_llm ...` invocation; the existing `skipif(GROQ_API_KEY)` guard is untouched.
- A full local `make check` passes end to end after these changes, with the same pass/fail/skip counts as the pre-change baseline (57 passed / 2 skipped / 14 deselected → 57 passed / 14 deselected once `live_llm`'s 2 tests are excluded by marker instead of skipped, confirmed exactly, not assumed).

## Notes

All three changes applied entirely within `Makefile` — the `live_llm` exclusion is a one-word addition to `check-python`'s existing `-m "not transport"` expression (`pyproject.toml`'s `markers` list already declares `live_llm` and needed no change). `SCCACHE_INSTALLED := $(shell command -v sccache 2>/dev/null)` gates all sccache wiring on the tool actually being present — a machine without it gets exactly today's unchanged behavior, not a broken build. Verified with real evidence, not by inspection alone: touching `native_runtime.cpp` and rebuilding twice produced a genuine miss-then-hit pair (`sccache --show-stats`: 1 hit / 1 miss, 50% C/C++ hit rate) — the exact same `CMAKE_C_COMPILER_LAUNCHER`/`CMAKE_CXX_COMPILER_LAUNCHER=sccache` mechanism CI already proves works, now active locally too. Touching `src-tauri/src/lib.rs` and running `RUSTC_WRAPPER=sccache cargo test` showed 6 real compile requests routed through sccache (non-cacheable under cargo's default dev/test-profile incremental compilation — expected and consistent with this repository's own prior finding, `.claude/memory/sccache-idle-timeout-final-stats.md`, that release-profile builds are where Rust's real cache hits show, since `cargo test`'s dev profile has `incremental = true` by default); the wiring itself, not the profile-specific hit rate, is this Task's own acceptance bar and is confirmed. `make check-frontend` run twice back to back: first run took 11.3s (ran a real `npm ci`); second, immediately after with nothing changed, took 3.4s with zero `npm ci` invocation — confirmed by its absence from the recipe's own output, not inferred from timing alone. `pytest -m "not transport and not live_llm"`: `57 passed, 16 deselected` (were `57 passed, 2 skipped, 14 deselected`) — the two `live_llm` tests are now excluded by marker rather than collected-then-skipped, with `skipif(GROQ_API_KEY)` itself untouched and still reachable via `uv run pytest -m live_llm`. `git diff --stat` on every touched file confirmed each verification step's `touch` produced zero content change, only the intended `Makefile`/`pyproject.toml` edits are real diffs. No warning newly introduced by this Task (the native rebuild's one pre-existing compiler warning is unrelated — surfaced by any full recompile of that file, not by this Task's changes, confirmed by the file having zero content diff).
