# TK-039 — Native Playback Command Protocol

Status: done
Feature: FT-030

## Objective

Extend `project.proto`'s `Command`/`Event` oneofs and `native_runtime.cpp`'s session loop with Play/Stop/GetPlaybackPosition, reusing FT-027's already-proven `materializer` playback functions unchanged. Prove, via a new ctest, that transport position tracking remains correct under `native_runtime`'s actual threading model — blocked on a condition variable between commands, with zero JUCE message-loop pumping — since `playback_proof`'s own test pumps the message loop while waiting and has therefore never actually exercised this.

## Scope / Out of scope

Mirrors FT-030's own scope, restricted to `src/schemas/project.proto`, `src/backend/audio/wire_codec.{h,cpp}`, `src/backend/audio/native_runtime.cpp`, and the new native ctest. No Python, Rust, or frontend change.

## Acceptance criteria

- `project.proto` gains `PlayCommand`/`PlaybackStartedEvent`, `StopCommand`/`PlaybackStoppedEvent`, `GetPlaybackPositionCommand`/`PlaybackPositionEvent`, added to the existing oneofs (fields 8-10).
- `wire_codec` decodes all three new commands and encodes all three new events.
- `native_runtime.cpp`'s session loop handles Play (builds a dedicated `Edit::forEditing` Edit via `buildEdit`, opens the real device, starts playback), Stop (stops playback, reports final position), and GetPlaybackPosition (reports `isPlaying`/position) — none of it touching the existing `liveEdit`/`liveProjectId` render path's own behavior.
- A new ctest starts real-time playback, then waits using only `std::this_thread::sleep_for` (never `runDispatchLoopUntil`) before reading position — proving position genuinely advances, and stop genuinely halts it, with zero message-loop pumping; soft-skips (does not fail) when no real audio device is available, mirroring `playback_proof`'s own precedent.
- `make check-native` passes with zero new warnings.

## Notes

A real, non-obvious finding changed this Task's own design mid-implementation, caught by a throwaway diagnostic executable (not shipped) before wiring anything into `native_runtime.cpp`: with zero JUCE message-loop pumping between starting playback and reading position — exactly how `native_runtime.cpp`'s existing `NativeRuntimeConnection::waitForCommand` blocks (a plain `std::condition_variable::wait_for`) — `isPlaying()` correctly reports `true` but `getPlaybackPositionSeconds()` stays frozen at its starting value indefinitely, even after a full second of real elapsed time; a single brief pump taken right before reading position does not fix it either. Real-time device audio itself keeps playing regardless (it runs on its own audio-callback thread), but `TransportControl`'s queryable position is only kept current by periodic message-thread service. Confirmed the fix empirically before shipping it: continuous small-slice pumping (10ms) throughout the wait, matching `playback_proof.cpp`'s own already-proven pumping cadence, does keep position accurate.

Fixed by replacing the single long blocking wait with `waitForNextCommand` (`native_runtime.cpp`): while a live `Edit` is playing, it polls `waitForCommand` in 10ms slices, pumping the message loop between each one, until a command arrives or the connection is lost; it falls back to the original single long blocking wait whenever nothing is playing, so every existing command path (materialize, move_clip) is behaviorally unchanged. No dedicated native ctest was added for this: an isolated ctest mirroring `playback_proof.cpp`'s own pumping cadence would only re-confirm an already-proven fact (FT-027) without exercising the actual command-loop/connection code this Task changes. Real confidence instead comes from a manual end-to-end smoke test driving the actual built `native_runtime` binary over its real wire protocol (Play → four `GetPlaybackPositionCommand` polls at 300ms intervals → Stop): `device_opened: true`, position genuinely advancing in real time across all four polls (0.27s → 0.58s → 0.88s → 1.18s, tracking the real ~300ms poll spacing), `is_playing` staying `true` throughout, and a clean Stop with a consistent final position — and by the permanent, higher-fidelity Python integration test TK-040 adds against this same real binary and command loop.

`project.proto`'s new messages/oneof fields, `wire_codec.{h,cpp}`'s new `DecodedCommand` variants and encoders, and `native_runtime.cpp`'s new command branches touch nothing in the existing render/move-clip paths — confirmed by `make check-native` (via direct `ctest`) passing all 6 existing ctests unchanged after the change, zero new warnings beyond the already-catalogued vendored set (`.claude/memory/native-build-third-party-warnings.md`).

**Correction found during FT-030's Feature-level Review (`code-review` skill):** `waitForNextCommand` checked `isPlaying(*liveEdit)` once at entry to decide whether to enter the poll-and-pump loop, but never re-checked it inside that loop — if playback ended while waiting for the next command (a real possibility this Task's own follow-on investigation found: Tracktion's transport does **not** stop itself once an Edit's content ends, it keeps running past the end producing silence until an explicit Stop, so this specific scenario doesn't actually arise from content simply ending — but a stale, no-longer-playing `liveEdit` could still be reached this way in principle), the loop would keep polling/pumping indefinitely rather than falling back to the plain long wait once playback genuinely stops. Fixed by changing the entry check to a `while` condition re-evaluated every iteration. Re-verified: all 6 native ctests still pass with zero new warnings.
