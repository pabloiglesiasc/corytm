# TK-040 — Python Playback Session and Desktop-Channel Wiring

Status: done
Feature: FT-030

## Objective

Give `corytm.runtime` a `PlaybackSession` that spawns and holds one dedicated `native_runtime` process open across Play → (any number of position polls) → Stop, and wire `play`/`stop`/`get_playback_position` into the Desktop channel's `_dispatch_command`/`_run_session`, holding that session across loop iterations alongside `current_project`.

## Scope / Out of scope

`src/backend/core/src/corytm/runtime/{session,projection,desktop}.py` and their tests only. No Rust or frontend change (TK-041/TK-042).

## Acceptance criteria

- `projection.to_play_command(project)` projects a canonical `Project` into a `PlayCommand`, reusing the same nested Project→message conversion `to_materialize_command` already uses (factored out, not duplicated).
- `session.PlaybackSession` spawns `native_runtime`, sends `PlayCommand`, and exposes `get_position()`/`stop()` against the same held connection, plus a `kill()` for abnormal/early teardown; the "spawn native_runtime and authenticate" logic shared with the existing one-shot `_connected_native_runtime` is factored into a common helper.
- `desktop.py`'s `_run_session` holds an `Optional[PlaybackSession]` across loop iterations; `_dispatch_command` gains `play`/`stop`/`get_playback_position` branches; the connection's own disconnect path kills any live playback session rather than leaking the child process.
- A new automated integration test drives the real Desktop channel end to end (spawning the real `corytm serve` sidecar): `CreateProjectCommand` → `AddAudioTrackCommand` → `AddAudioClipCommand` → `PlayCommand` → two `GetPlaybackPositionCommand`s with a real sleep between them (asserting position advances when a device is available, and explicitly reporting rather than failing when none is) → `StopCommand`.
- `pytest -m "not transport and not live_llm"`, `pytest -m transport`, `pyright`, `ruff check`, `ruff format --check` all pass.

## Notes

`_connected_native_runtime`'s "spawn, listen, accept, authenticate" logic was factored into a new `_spawn_and_authenticate` helper (returning a `_NativeRuntimeProcess` NamedTuple) rather than duplicated — `PlaybackSession.start` is a genuine second real caller needing the identical sequence, only differing in teardown timing (one-shot close-immediately vs. held-open-until-Stop). `PlaybackSession` exposes `start`/`get_position`/`stop`/`kill`, the last used only when the owning Desktop-channel connection itself disconnects while playback is still active, so the child `native_runtime` process is never leaked.

`_dispatch_command`'s signature grew a `playback_session: PlaybackSession | None` parameter, threaded through and returned alongside `current_project` exactly the same way, and `_run_session` now holds it across loop iterations. A defensive double-Play guard queries the already-live session's real position rather than fabricating a response; Stop/GetPlaybackPosition with no live session return an honest "not playing" event rather than raising, since a UI-driven race (Stop arriving just as a stray poll was in flight) is not a real precondition violation worth crashing the session over.

### Validate

`pytest -m "not transport and not live_llm"` (58 passed, 17 deselected — one more of each than before this Task, from the new `to_play_command` and Play/Stop integration tests), `pytest -m transport` (15 passed, 60 deselected — one more than before, the new end-to-end play/position/stop test), `pyright` (0 errors), `ruff check`/`ruff format --check` (clean) all pass. The new integration test (`test_play_reports_advancing_position_and_stop_halts_it`) passed against a real local audio device: position genuinely advanced across two polls 0.3s apart, and `is_playing` correctly read `false` immediately after Stop.

**Real bug found and fixed during FT-030's Feature-level Review (`code-review` skill), before Close:** `_dispatch_command`'s `play` branch treated any already-held `playback_session` as still genuinely playing, only ever querying its position — but a session whose device failed to open never starts playing at all, so `is_playing` reads `False` forever, and every subsequent Play call reused that same stale session and returned `device_opened=False` for the rest of the connection, with no way to recover short of a full reconnect. Fixed: when the held session reports `is_playing=False`, it is killed and a fresh one started instead of reused. Reproduced deterministically first (TDD, not assumed): `test_play_recovers_from_a_session_that_never_started` (new, `tests/integration/test_desktop_channel_session.py`) monkeypatches `PlaybackSession.start` with a fake that never actually plays, confirmed to fail against the pre-fix branch (`start_call_count` stayed `1` after two Play commands) and pass against the fix (`start_call_count` becomes `2`) — deterministic and hardware-independent, since forcing a real no-device condition isn't reliably reproducible on a dev machine with a real audio device. A different failure mode the review agent also proposed — Tracktion's transport auto-stopping once an Edit's content ends — was checked empirically and found **not** to hold (confirmed via a real Play → wait 1s past a 0.4s clip → GetPlaybackPosition: `is_playing` stayed `true`, position kept climbing past the clip's own duration): the transport keeps running past the end of content, producing silence, until an explicit Stop. The fix and its regression test target the real, confirmed failure mode (a session that never started) rather than the unconfirmed one. Full `pytest -m "not transport and not live_llm"` (58 passed), `pytest -m transport` (16 passed — one more than the pre-fix count above), `pyright`, `ruff check`/`ruff format --check` all re-pass after the fix.
