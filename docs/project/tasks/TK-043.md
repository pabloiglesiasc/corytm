# TK-043 — Pre-Warmed, Connection-Persistent Playback Session

Status: done
Feature: FT-030

## Objective

Fix two real defects human validation of FT-030 found: Play startup latency of ~3-5s (target: <250ms warm/steady-state, <500ms Alpha ceiling), and Stop followed by Play again incorrectly restarting from position 0 instead of resuming. Both traced to the same root architectural cause and fixed together.

## Scope / Out of scope

`src/backend/audio/{materializer,native_runtime,wire_codec}.{h,cpp}`, `src/schemas/project.proto` (new `PrepareDeviceCommand`/`DevicePreparedEvent`), `src/backend/core/src/corytm/runtime/{session,desktop}.py`. No auto-stop-at-content-end (TK-044). No Rust/frontend change — the Desktop-channel wire commands (`Play`/`Stop`/`GetPlaybackPosition`) are unchanged in shape; `PrepareDeviceCommand` is purely an internal Python↔native concern, never sent by Rust.

## Diagnosis (empirical, not guessed)

Instrumented `native_runtime.cpp`/`materializer.cpp` with temporary stage-by-stage timing (removed once understood, per this project's own established practice). Measured via a real end-to-end smoke script driving the actual built `native_runtime` binary:

- `main()` entry to connecting the Python loopback socket: ~50ms.
- `buildEdit`/`startPlayback` themselves: ~15-30ms combined.
- `openRealtimeOutputDevice`'s device-settle wait: **~4.6-5.5 real seconds**, on every single Play — the dominant cost by nearly two orders of magnitude.

Drilled further with per-iteration logging inside the settle-wait loop: `waveOut` device count was already `1` within ~200ms, but `midiIn` stayed `0` for **~3.6-4.4 seconds** before the MIDI scan even began (the scan itself, once started, completed in ~600ms — matching `RSK-018`'s own prior estimate, which had only ever measured the scan's own duration, not the delay before it starts). This multi-second pre-scan delay is a real, well-documented macOS CoreMIDI client cold-start cost — paid by every fresh process's first touch of CoreMIDI. Because every prior Play spawned a brand-new `native_runtime` process (TK-039/040's original design), every Play paid this cost from scratch.

Separately, confirmed via a standalone experiment (materializer functions called directly, no wire protocol) that Tracktion's `TransportControl::stop()`/`freePlaybackContext()` do **not** reset transport position at all — reusing the same `Edit` object across a real Stop→Play cycle resumed correctly on its own. This ruled out a Tracktion-side bug and pointed at the real cause: a brand-new process means a brand-new `Edit`, which starts at 0 by construction — nothing to do with `stop()`/`freePlaybackContext()` themselves.

## Fix

- `openRealtimeOutputDevice` made idempotent (`materializer.cpp`): returns immediately, without re-invoking `DeviceManager::initialise()`, when the device manager already reports itself open and settled.
- New `PrepareDeviceCommand`/`DevicePreparedEvent` (`project.proto`, `wire_codec`, `native_runtime.cpp`): opens the device without building an `Edit`, so it can be triggered independently of any specific Play.
- `corytm.runtime.session.PlaybackSession` split into `spawn()` (fast: process spawn + authenticate only) and `prepare_device()` (slow: the device-open/settle call) — `desktop.py`'s `_run_session` spawns one `PlaybackSession` per Desktop-channel connection and backgrounds `prepare_device()` as a task immediately, before the first command is even read. Real usage (creating/opening a project, adding a track and clip) gives this background warm-up several real seconds of slack before the user can possibly reach Play.
- The playback session itself is now connection-lifetime, not per-Play: `stop()` no longer tears the process down (previously it did); only the Desktop-channel connection closing does (`kill()`).
- `native_runtime.cpp`'s `PlaySpec` handling: rebuilds the `Edit` fresh on every Play (so it always reflects any content changes made while stopped) but explicitly seeks it to the position the matching `Stop` last captured (`lastStoppedPositionSeconds`, a `main()`-scope variable, consumed and reset on every Play) when resuming the same project id — a genuinely different project (or the first Play ever) starts at 0 as before.
- Every playback-affecting Desktop-channel command (`play`/`stop`/`get_playback_position`) awaits the backgrounded warm-up task first — required because it reads/writes the same connection those commands do, and only one read can be in flight on an `asyncio.StreamReader` at a time; harmless once warm-up has already completed, which real usage always gives it time to do.

A real regression this fix's own first version introduced (caught before Close by running the full test suite, not assumed safe): eagerly spawning a session for every connection meant a connection closing before warm-up finished had to wait out the full ~5s warm-up before it could clean up — breaking two existing tests with short internal timeouts. Fixed by splitting `spawn()` (fast, always awaited directly so a real process handle exists immediately) from `prepare_device()` (slow, backgrounded and explicitly cancelled on disconnect before killing the process).

## Acceptance criteria

- A warm Play (device already open) completes in well under 500ms.
- Stop followed by Play again (no intervening explicit Stop-then-different-project) resumes from the stopped position, not 0.
- Existing Play/Stop/GetPlaybackPosition behavior (advancing position, `is_playing` semantics) unaffected.
- New deterministic regression tests for both behaviors; full `make check` passes end to end with zero new warnings.

## Evidence

- Manual smoke test against the real built `native_runtime` binary: warm Play latency **13.9ms** (vs. ~5.4s cold), confirmed via `PrepareDeviceCommand` then `PlayCommand` timing.
- `test_play_is_fast_once_the_device_is_warm` (new, `tests/integration/test_desktop_channel_session.py`): asserts warm Play completes in under 1.5s (a looser bound than the 500ms manual measurement, to absorb real CI/test-harness overhead) after sleeping 6s to let warm-up finish — passed.
- `test_stop_then_play_resumes_from_the_stopped_position` (new): stops mid-clip, plays again, confirms position resumes near the stop point rather than 0 — passed.
- Full `make check` (all five targets) passes end to end with zero new warnings — required per `docs/technical/testing.md`'s own rule that a shared `.proto` schema change invalidates 3+ subsystems at once.

**FT-030's own required human-validation evidence for this fix — a real measured click-to-audible latency and a real Stop/Play-resume click-through — remains pending**, per the fresh human-validation checklist accompanying this session's handoff.
