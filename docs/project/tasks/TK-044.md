# TK-044 — Automatic Stop at Effective Playback End

Status: done
Feature: FT-030

## Objective

Fix a real defect human validation of FT-030 found: the playhead kept advancing indefinitely past the end of the project's content until the user manually pressed Stop.

## Diagnosis

Checked empirically rather than assumed: a real Play on a 1.0s clip, left running with no explicit Stop, showed `is_playing` still `true` and position still climbing (to 1.02s and beyond) well past the clip's own duration. Confirmed directly against Tracktion's own `TransportControl::stop()`/`play()` implementation (vendored source) that nothing in the transport itself ever stops playback at the end of an Edit's content — it plays through to silence and keeps running. Tracktion's own behavior is therefore not Corytm's product contract here; something has to decide and enforce "effective end" explicitly.

## Authoritative layer (deliberate decision, not left implicit)

`CLAUDE.md` §2's architecture law — "Python knows what the project means musically, C++ knows how to make it sound" — could be read either way for this specific case, so the choice is recorded explicitly: **the Native Audio Runtime is the authoritative layer for enforcing effective-end-of-content stop**, not Python/Corytm Engine. Reasoning: "where does the already-materialized `Edit`'s last clip end" is the same purely mechanical/geometric fact `renderEdit` has always computed in C++ to know how long to render (`editEndSeconds`, computed from the live `Edit`'s own clips) — not a musical/arrangement interpretation requiring domain judgment (no fades, release tails, loop points, or other product-level arrangement semantics are in scope for Alpha's single-clip-per-track content model). Reusing that exact, already-proven computation — rather than having Python separately recompute an equivalent value and risk it drifting from what native actually materializes — keeps one single source of truth for "how long is this content" shared by both the offline-render and real-time-playback paths. `native_runtime.cpp`'s own poll loop (`waitForNextCommand`, already re-checking `isPlaying()` every 10ms while playing, per TK-039/FT-030's own fix for a related staleness bug) is the natural, already-existing place to enforce it: this makes `isPlaying()` itself authoritative for every caller — including the Desktop channel's `GetPlaybackPositionCommand`, which the frontend already polls — with no separate frontend timer needed or introduced.

## Fix

- `materializer.h`/`.cpp`: extracted `getEditEndSeconds(Edit&)` from `renderEdit`'s own inline computation (no behavior change to `renderEdit` itself — same computation, now named and reusable).
- `native_runtime.cpp`'s `waitForNextCommand`: after each poll-and-pump slice, checks `getPlaybackPositionSeconds() >= getEditEndSeconds()` (guarded against a genuinely empty Edit, where the end is `0.0`) and calls `stopPlayback()` once reached, breaking out to the plain long wait — the very next `isPlaying()` check (by any caller) then correctly reads `false`.

## Acceptance criteria

- Playback started on a project with real content stops on its own once the content's effective end is reached, without any explicit Stop command.
- `GetPlaybackPositionCommand`, polled after that point, reports `is_playing: false` — proving the transport state itself is authoritative, not a frontend-side estimate.
- No change to any existing Play/Stop/GetPlaybackPosition behavior for playback that hasn't reached the end.
- A new deterministic regression test; full `make check` passes end to end with zero new warnings.

## Evidence

- Manual smoke test against the real built `native_runtime` binary: a 1.0s clip, left playing with no Stop, correctly reported `is_playing: false` after 1.4s.
- `test_playback_stops_automatically_at_the_effective_end` (new, `tests/integration/test_desktop_channel_session.py`): plays a 0.5s clip, never sends Stop, waits 1.2s, confirms `is_playing` is `false` via `GetPlaybackPositionCommand` — passed.
- Full `make check` (all five targets) passes end to end with zero new warnings.
