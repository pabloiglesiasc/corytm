# TK-045 — Fix Playback Session Crash on Real Human Idle Gaps

Status: done
Feature: FT-030

## Objective

Fix a blocking regression human validation found after TK-043/TK-044 landed: clicking Play produced `failed to read event: early eof` in the real Desktop app. Determine the true failure mechanism across the full path (Desktop → Rust → Desktop channel → PlaybackSession → native_runtime → Tracktion/JUCE) rather than accepting the visible error as the root cause, fix it, and add regression coverage at the highest practical fidelity.

## Diagnosis (empirical, reproduced deterministically before any fix)

Traced the full path per the user's explicit request:

- **Does `native_runtime` exit or crash?** Exits deliberately (not a crash/segfault) — confirmed via its own stderr: `native_runtime: command did not arrive in time`, followed by `Cleaning up temp files..` (the `Engine` destructor, printed on normal process exit).
- **Does the Python playback/session process remain alive?** No. The dead `native_runtime` connection causes `PlaybackSession.play()`'s `_read_event()` to raise `asyncio.IncompleteReadError` (0 bytes read on 8 expected) — confirmed via the real Python traceback. This exception is **never caught**: it propagates through `_dispatch_command` → `_run_session` → `serve_desktop_channel()` → `main()`, and since `main()` calls `asyncio.run(serve_desktop_channel())` with no enclosing `try`/`except`, it crashes the entire `corytm serve` process (confirmed: real Python traceback printed to stderr, process exit code 1).
- **Does Rust lose the connection?** Yes — necessarily, since the OS process Rust's `DesktopConnection` was talking to no longer exists once `corytm serve` exits. This is what `send_command`'s `read_frame` sees as an immediate EOF, surfacing as `"failed to read event: early eof"`.
- **Which of the five candidate causes?** None of protocol framing failure, broken pipe, or native process crash (segfault) — it is `native_runtime`'s own **deliberate, self-inflicted exit** on an idle-time guess that no longer applies to its new lifecycle, compounded by an **unhandled exception** on the Python side that turns one dead subprocess into a crash of the entire Desktop-channel server.
- **Is it related to the recent message-loop/polling or device-initialization changes?** Yes, specifically to TK-043: `native_runtime.cpp`'s command-wait loop has always fallen back to a fixed `commandTimeoutMs = 5000` (5 seconds) once not playing — a defensible bound for the *original* one-shot-per-command process design (materialize/move-clip processes are always sent their one command immediately after spawning, so a multi-second gap was never expected). TK-043 made the *playback* session's process connection-lifetime instead, spawned once per Desktop-channel connection and reused across many Play/Stop cycles — but never updated this timeout, so the same process now silently exits after 5 idle seconds even though real human interaction (creating a project, adding a track, adding a clip, thinking, then clicking Play) routinely exceeds that.

## Shared root cause with the three previously reported defects?

No. Checked explicitly per the user's instruction before making any change: the latency fix, the resume-position fix, and the auto-stop-at-end fix (TK-043/TK-044) are all independently confirmed still correct (their own regression tests all still pass). This is a **new, distinct** defect introduced by TK-043's own persistent-session redesign — an unconsidered consequence of that redesign, not a shared mechanism with the other three.

## Fix

An independent `code-review` pass (high effort, four parallel finder agents) against this fix's first version caught two real problems before Close, both addressed:

1. **The fix was too broad.** `native_runtime` is one shared binary used both by the new persistent playback session *and* by every one-shot materialize/move-clip process (`corytm.runtime.session._connected_native_runtime`). A first version made the idle wait tolerant unconditionally — which would have silently turned a one-shot process's own legitimate fail-fast protection (its single expected command never arriving, e.g. from a Python-side bug or race) into a slow, silent hang instead of the fast, loud failure it correctly produced before. Fixed by tracking whether *any* command has been received yet: the very first wait keeps the original fast `firstCommandTimeoutMs = 5000` (protecting the genuine one-shot case, and the persistent session's own first command — `PrepareDeviceCommand` — which real usage always sends immediately after spawning anyway, so this never conflicts with real idle time); only the *second and later* waits — which realistically only ever have a meaningful gap for the persistent playback session — use a generous `subsequentCommandTimeoutMs` (24 hours).
2. **An initial "wait in 60-second slices" loop was both unnecessarily complex and, in one attempted one-line simplification, briefly introduced a real logic bug** (treating a hypothetical non-disconnect timeout as "a command arrived," which would have handed `decodeCommand` stale/empty bytes). Resolved by recognizing that `NativeRuntimeConnection::waitForCommand`'s underlying `condition_variable::wait_for` already wakes immediately on a real disconnect (`connectionLost()`'s own `notify_all()`), regardless of how large the requested timeout is — so a single call with the large timeout is both simpler and has no detection-latency downside a slicing loop would avoid. The original `main()` structure (an explicit "command did not arrive in time" diagnostic, reached only on a *timeout without disconnection* — now confined to the 24-hour bound, an intentionally-retained backstop against a genuinely stuck-but-still-connected peer) is otherwise unchanged.

Every new C++/Rust comment this fix's first draft added was also found, correctly, to violate `CLAUDE.md` §8's zero-comments rule (its Python-docstring exception is scoped to Python only) — removed; this record and the commit message carry that rationale instead. Deliberately did **not** paper over the original symptom by wrapping the Python exception in a friendlier message or a try/except at the dispatch level — the actual defect (the process dying for no good reason) is what's fixed.

## Regression coverage (highest practical fidelity)

A real, non-obvious lesson from writing this test: this file's usual pattern of running `serve_desktop_channel()` as an in-process `asyncio.Task` (used by every other test in `test_desktop_channel_session.py`) **cannot** reproduce this regression at all — an unhandled exception in a Task inside the *same* pytest process never closes the real OS-level socket the way a genuinely separate crashed process does. Confirmed directly: a first version of this test written that way passed even against the unfixed binary, a false negative caught before it could ship. Both new tests instead spawn `corytm serve` as a real, separate OS process:

- `test_play_survives_a_real_human_idle_gap_before_it` (Python, `tests/integration/test_desktop_channel_session.py`): spawns `corytm serve` via `python -m corytm.main serve` as a genuine subprocess, drives Create → Add Track → Add Clip, sleeps 13s (calibrated empirically — long enough to clear both the playback session's own ~5.5s background device warm-up *and* a real margin past the old 5s idle threshold once actually idle; a shorter 7s sleep was tried first and found to still intermittently overlap the warm-up itself, not reliably reproducing the bug), then sends Play. Confirmed failing (real `IncompleteReadError` traceback, process exit code 1) against the unfixed binary; passing after the fix.
- `play_survives_a_real_human_idle_gap_before_it` (Rust, `src-tauri/src/lib.rs`): the same scenario through the full real vertical path — `spawn_desktop_sidecar`'s own real subprocess spawn, the real Rust `play()` Tauri command — matching the exact layer the human's own report surfaced the symptom at.

## Evidence

- Both regression tests were re-verified against the *corrected* fix (not just the first draft): each confirmed failing against the unfixed binary (a real captured `IncompleteReadError`/process exit code 1) and passing after, matching this project's own established TDD discipline.
- `make check` (all five targets — this change invalidates `check-python`, `check-native`, `check-desktop`, and `check-transport` at once per `docs/technical/testing.md`) passes end to end with zero new warnings.
- An independent `code-review` pass (high effort, four parallel finder agents) was run against the complete fix; both real findings (the overly-broad timeout, the unnecessary/briefly-buggy slicing loop) were fixed, re-verified, and are detailed above. The zero-comments findings were also applied. Two findings were considered and deliberately not acted on: extracting the ~90-line Rust test spawn/teardown sequence (now duplicated a fifth time) into a shared helper was judged out of scope for this specific bug fix — a real, legitimate future cleanup, not required for correctness — and the 13-second sleep constant necessarily lives twice (once per test language/process; there is no cross-language constant-sharing mechanism in this repository for test-only timing).
- A genuine environment quirk surfaced while formatting the new Python test: this project's pinned `ruff` version's formatter, applied to `except (asyncio.IncompleteReadError, TimeoutError):`, rewrites it to the syntactically invalid `except asyncio.IncompleteReadError, TimeoutError:` (confirmed via `ast.parse` and by running `ruff format` directly, not just reading its diff). Worked around by naming the tuple as a module-level constant (`_TRANSPORT_FAILURE_ERRORS`) instead of an inline literal in the `except` clause, which `ruff format` handles correctly; captured in `.claude/memory/` so a future session isn't blindsided by it.
